# 事务型消息

`@Transactional` 只对**支持事务的数据库**生效，可自动回滚数据库写操作； Redis、普通 MQ 不属于数据库事务范畴，无法自动回滚，需要手动补偿或使用中间件专属事务方案。  

也就是说创建订单和发送异步消息要放在一个事务中，

如果先投送异步消息，再创建订单，

创建订单失败，原事务回滚，但是数据库消费了这个异步扣减库存的消息，

如果先创建订单，再投送异步消息，

考虑异步消息能够投送成功，因为这种情况投送必须成功

但是如果投送失败，会导致订单创建了，但是库存没减

思考：

若果使用 ：

1. 查询 Redis 库存
2. 扣减 Redis 库存
3. 数据库创建订单（开启 @Transactional 事务）
4. 最后一步：发送异步 MQ（用于异步扣DB真实库存）

（Spring 事务 + 末尾发 MQ + 手动恢复 Redis）

mq发送失败手动触发回滚后手动  恢复 Redis，

 仅能保证「请求阶段」一致，无法保证**下游消费链路**一致；  

 该方案只覆盖「发送即时失败」，无法解决**消息丢失、消费失败、异步投递无应答**等问题，生产环境高并发下有数据不一致风险。

**RocketMQ 事务消息完整流程**

1. 发送半消息（消费者暂不可见）
2. 执行本地数据库事务（如创建订单）
3. 根据本地事务结果操作：

- 本地事务提交 → 半消息转正，对外可见，允许消费者拉取
- 本地事务回滚 → 直接删除半消息，无消息产生

1. 消息被消费者正常拉取，执行消费逻辑（扣库存、更新状态等）

**边界区分**

事务消息管控范围：半消息阶段 + 本地事务 + 消息是否对外投递

事务消息管控不到：消费者拿到消息后的业务代码执行

思考：如果消费端消费失败，即扣数据库中的库存操作失败，有什么问题？如何解决？

## 为什么有用户令牌了，还是需要令牌桶实现限流？

很容易产生一个疑问：**既然有了秒杀令牌（第九章），为什么还需要 Guava 的令牌桶再做一层限流？** 两个都叫「令牌」，但干的活完全不同：

|              | **秒杀令牌 (seckill token)**          | **RateLimiter 令牌桶**            |
| ------------ | ------------------------------------- | --------------------------------- |
| **在哪**     | `/generatetoken` 接口                 | `/createorder` 接口               |
| **管什么**   | **谁能进**——有资格下单吗？            | **进多快**——现在能处理吗？        |
| **粒度**     | 业务级别，按活动/库存/用户控制        | 基础设施级别，按 QPS 控制         |
| **限制的是** | **总量**（大闸 = 库存 × 5，发完即停） | **速率**（每秒 300 个，匀速放行） |
| **类比**     | 演唱会卖了 500 张票                   | 门口每秒只放 300 人进场           |

**为什么两层都要有？** 假设库存 100 件，大闸 = 500：

```
t=0s   秒杀开始瞬间，500 个用户同时拿到秒杀令牌
       ↓
       500 个合法请求同一秒打向 /createorder
       ↓
       如果没有 RateLimiter：
       ├── 线程池只有 20 个线程在干活
       ├── 剩余 480 个请求全部堆在无界队列里
       ├── Tomcat 的 200 个工作线程全部在 Future.get() 上阻塞
       └── 服务雪崩
       如果有 RateLimiter(300)：
       ├── 第 1 秒：300 个放行，200 个直接返回「活动太火爆」
       ├── 第 2 秒：300 个放行...
       └── 匀速泄洪，系统稳定
```

**本质区别**：

大闸控制的是「一共放多少人进来」，RateLimiter 控制的是「每秒放多少人进来」。

卖 500 张票不等于 500 人同一秒到门口——但如果他们真的同一秒到了，门口就得有速率控制防止踩踏。两者缺一不可。
