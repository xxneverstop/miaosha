# 第一部分：缓存优化交易前置验证

## 改动前有什么问题？

下单时需要校验商品和用户是否存在，每次校验都走 `SELECT` 查数据库。秒杀场景下，同一件商品被成千上万人同时抢购，校验逻辑每次都打到数据库，数据库连接池很快耗尽，整个系统瘫痪。

```
每个下单请求 → ItemService.getItemById(id) → SELECT * FROM item
                → UserService.getUserById(id) → SELECT * FROM user
```

## 改动后发生了什么？

在数据库前面加一层 Redis 缓存（key = `item_validate_{id}` / `user_validate_{id}`），校验时优先查 Redis，miss 了才查数据库并把结果写入 Redis，设置 10 分钟过期。

```
请求 → Redis 有？→ 直接返回 ✅（~1ms）
           ↓ 没有
       数据库查询 → 写入 Redis → 返回（~50ms，但只用一次）
```

## 具体改动

| 文件                      | 改动                                                                                           |
| ----------------------- | -------------------------------------------------------------------------------------------- |
| `ItemService.java`      | 新增接口方法 `ItemModel getItemByIdInCache(Integer id)`                                            |
| `ItemServiceImpl.java`  | 实现上述方法：先查 `redisTemplate.opsForValue().get("item_validate_"+id)`，没有则查 DB 并回写 Redis，TTL 10 分钟 |
| `UserService.java`      | 新增接口方法 `UserModel getUserByIdInCache(Integer id)`                                            |
| `UserServiceImpl.java`  | 实现上述方法：先查 `redisTemplate.opsForValue().get("user_validate_"+id)`，没有则查 DB 并回写 Redis           |
| `OrderServiceImpl.java` | `createOrder` 中把 `getItemById` → `getItemByIdInCache`，`getUserById` → `getUserByIdInCache`   |

## 参考代码

```java
// ItemServiceImpl.java — 新增
@Override
public ItemModel getItemByIdInCache(Integer id) {
    ItemModel itemModel = (ItemModel) redisTemplate.opsForValue().get("item_validate_" + id);
    if (itemModel == null) {
        itemModel = this.getItemById(id);
        redisTemplate.opsForValue().set("item_validate_" + id, itemModel);
        redisTemplate.expire("item_validate_" + id, 10, TimeUnit.MINUTES);
    }
    return itemModel;
}
```

```java
// UserServiceImpl.java — 新增
@Override
public UserModel getUserByIdInCache(Integer id) {
    UserModel userModel = (UserModel) redisTemplate.opsForValue().get("user_validate_" + id);
    if (userModel == null) {
        userModel = this.getUserById(id);
        redisTemplate.opsForValue().set("user_validate_" + id, userModel);
        redisTemplate.expire("user_validate_" + id, 10, TimeUnit.MINUTES);
    }
    return userModel;
}
```

## 关键讲解

Redis 的 key 设计为 `item_validate_{id}`，跟前面的 `item_{id}`（商品详情缓存）区分开。这两个缓存用途不同：

- `item_{id}` → 给前端展示商品详情用
- `item_validate_{id}` → 给后端下单校验用

分开管理可以独立设置过期时间，校验缓存可以更长一点，因为商品基本信息不会频繁变化。

`UserServiceImpl` 新增 `getUserByIdInCache` 需要注入 `RedisTemplate`，你的项目当前没有注入，需要加：

```java
@Autowired
private RedisTemplate redisTemplate;
```

## 验证方式

1. 启动 Redis，启动应用
2. 先调用登录接口获取 token
3. 用 `redis-cli` 执行 `KEYS user_validate_*`，此时应该为空
4. 调用下单接口，参数带上 token、itemId、amount
5. 再次执行 `KEYS user_validate_*`，应该能看到 `user_validate_{用户ID}` 这个 key
6. 执行 `TTL user_validate_{用户ID}`，确认过期时间是 600 秒（10 分钟）
7. 用同样的方式验证 `item_validate_{商品ID}` 的 key

# 第二部分：库存缓存优化

## 改动前有什么问题？

库存存在 MySQL 的 `item_stock` 表中，每次扣库存都是一个 `UPDATE item_stock SET stock = stock - ? WHERE item_id = ? AND stock >= ?`。MySQL 的行锁在秒杀场景下成为瓶颈——同一件商品的库存行被所有请求串行竞争，TPS 极低。几千人同时抢，MySQL 行锁逐个处理，后面的请求排队超时。

## 改动后发生了什么？

活动发布时，把库存数量从 MySQL 同步到 Redis（key = `promo_item_stock_{itemId}`）。Redis 是单线程内存操作，`INCR` 命令天然原子性，扣库存从数据库行锁排队变成 Redis 内存加减，不存在锁竞争。

```
改动前：10000 个请求 → MySQL 行锁排队，串行 UPDATE → TPS ~500
改动后：10000 个请求 → Redis INCR，无锁竞争 → TPS ~50000+
```

## 具体改动

| 文件                      | 改动                                                                                                 |
| ----------------------- | -------------------------------------------------------------------------------------------------- |
| `PromoService.java`     | 新增接口方法 `void publishPromo(Integer promoId)`                                                        |
| `PromoServiceImpl.java` | 实现 `publishPromo`：查活动信息 → 查商品信息 → `redisTemplate.opsForValue().set("promo_item_stock_"+id, stock)` |
| `ItemController.java`   | 新增 `/publishpromo` 接口，调用 `promoService.publishPromo(id)`                                           |

## 参考代码

```java
// PromoServiceImpl.java — 新增
@Override
public void publishPromo(Integer promoId) {
    // 通过活动id获取活动
    PromoDO promoDO = promoDOMapper.selectByPrimaryKey(promoId);
    if (promoDO.getItemId() == null || promoDO.getItemId().intValue() == 0) {
        return;
    }
    ItemModel itemModel = itemService.getItemById(promoDO.getItemId());

    // 将库存同步到 Redis 内
    redisTemplate.opsForValue().set("promo_item_stock_" + itemModel.getId(), itemModel.getStock());
}
```

```java
// ItemController.java — 新增接口
@RequestMapping(value = "/publishpromo", method = {RequestMethod.GET})
@ResponseBody
public CommonReturnType publishpromo(@RequestParam(name = "id") Integer id) {
    promoService.publishPromo(id);
    return CommonReturnType.create(null);
}
```

## 关键讲解

这个步骤需要在秒杀活动**开始之前**手动触发。运营后台调用 `/item/publishpromo?id=1`，系统把商品库存加载到 Redis。

这就引出一个关键认知：**库存有两份**，一份在 MySQL（持久化），一份在 Redis（运行时）。Redis 负责扛高并发扣减，MySQL 负责最终数据落盘。两者之间通过 MQ 异步同步（后面第四、五部分讲）。

`PromoServiceImpl` 需要新增注入：

```java
@Autowired
private ItemService itemService;

@Autowired
private RedisTemplate redisTemplate;
```

## 验证方式

1. 确保 MySQL 中 `item_stock` 表有数据，比如商品 id=1 的 `stock=100`
2. 启动 Redis，执行 `redis-cli GET promo_item_stock_1`，应该返回 nil
3. 调用 `/item/publishpromo?id=1` 接口
4. 再次执行 `redis-cli GET promo_item_stock_1`，应该返回 `100`
5. 确认 Redis 中有了库存数据后，后续下单走的就是 Redis 扣库存逻辑

# 第三部分：扣减库存缓存优化

## 改动前有什么问题？

上一部分把库存同步到了 Redis，但扣库存的方法 `decreaseStock` 还在调 `itemStockDOMapper.decreaseStock()` 直接操作数据库。如果不改 `decreaseStock` 的逻辑，那库存同步到 Redis 就白做了，请求还是会打到 MySQL。

## 改动后发生了什么？

`decreaseStock` 改为用 Redis 的 `INCR` 命令（传负数 = 扣减）。`INCR` 是原子操作，返回扣减后的值：

- `result > 0`：扣减成功
- `result == 0`：刚好扣完，打上售罄标记
- `result < 0`：库存不够，回补（再 INCR 一个正数回去）

```
改动前：itemStockDOMapper.decreaseStock() → MySQL UPDATE，锁行
改动后：redisTemplate.opsForValue().increment(key, -amount) → Redis 内存操作，原子
```

## 具体改动

| 文件                     | 改动                                                                                                                                                        |
| ---------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ItemService.java`     | 新增 `increaseStock`、`asyncDecreaseStock` 两个接口方法                                                                                                            |
| `ItemServiceImpl.java` | `decreaseStock`：从 `itemStockDOMapper.decreaseStock` 改为 `redisTemplate.opsForValue().increment("promo_item_stock_"+id, -amount)`，同时处理 result>0、==0、<0 三种情况 |

## 参考代码

```java
// ItemServiceImpl.java — decreaseStock 改造
@Override
@Transactional
public boolean decreaseStock(Integer itemId, Integer amount) throws BusinessException {
    //int affectedRow = itemStockDOMapper.decreaseStock(itemId, amount);
    long result = redisTemplate.opsForValue().increment("promo_item_stock_" + itemId, amount.intValue() * -1);
    if (result > 0) {
        // 更新库存成功
        return true;
    } else if (result == 0) {
        // 打上库存已售罄的标识
        redisTemplate.opsForValue().set("promo_item_stock_invalid_" + itemId, "true");
        return true;
    } else {
        // 更新库存失败，回补
        increaseStock(itemId, amount);
        return false;
    }
}
```

```java
// ItemServiceImpl.java — 新增库存回补
@Override
public boolean increaseStock(Integer itemId, Integer amount) throws BusinessException {
    redisTemplate.opsForValue().increment("promo_item_stock_" + itemId, amount.intValue());
    return true;
}
```

```java
// ItemServiceImpl.java — 新增异步同步（第四部分用）
@Override
public boolean asyncDecreaseStock(Integer itemId, Integer amount) {
    boolean mqResult = mqProducer.asyncReduceStock(itemId, amount);
    return mqResult;
}
```

## 关键讲解

这里有个容易疑惑的地方：`result == 0` 表示扣减后库存刚好为 0，**最后一个成功下单的人**触发了这个分支。此时要打上售罄标记 `promo_item_stock_invalid_{itemId}`，后续请求（第七部分）会直接检查这个标记并拒绝，不再进入扣库存逻辑。

`result < 0` 表示有并发请求"超抢"了。比如库存只剩 1，但 2 个请求同时 INCR -1，Redis 单线程执行，一个成功（result=0），另一个就会得到 result=-1。此时调用 `increaseStock` 把多扣的加回去——这就是**库存回补**。

`ItemServiceImpl` 需要新增注入：

```java
@Autowired
private RedisTemplate redisTemplate;

@Autowired
private MqProducer mqProducer;
```

## 验证方式

1. 先 `publishPromo` 把库存同步到 Redis（比如库存=100）
2. 用 `redis-cli GET promo_item_stock_1` 确认是 100
3. 调用下单接口，amount=1
4. 再次 `GET promo_item_stock_1`，应该变成 99
5. 用 `redis-cli DECR promo_item_stock_1` 模拟多次扣减直到 0
6. 再次 `DECR` 会得到负数，验证售罄标记 `GET promo_item_stock_invalid_1` 是否被设置为 "true"

# 第四部分：异步同步数据库（引入 RocketMQ）

## 改动前有什么问题？

前面 Redis 扣了库存，但 MySQL 中的库存还是原来的数。如果不把 Redis 的库存变化同步回 MySQL，重启 Redis 后库存数据就丢了，数据库和 Redis 之间数据不一致。

直接在下单流程中同步写 MySQL 呢？那又回到原来的问题——数据库写操作拖慢了整个下单流程。我们需要一种**不阻塞主流程、但能可靠同步**的方式。

## 改动后发生了什么？

引入 RocketMQ 消息队列作为"缓冲"。下单成功后，Producer 发一条消息到 MQ，Consumer 收到消息后异步执行 `itemStockDOMapper.decreaseStock()` 把数据库库存也减掉。流程变成：

```
下单 → Redis 扣库存（快，同步） → 发 MQ 消息（快，同步发）
                                            ↓
                            MQ Consumer 异步消费 → MySQL 扣库存（慢，但不阻塞用户）
```

## 具体改动

| 文件                          | 改动                                                  |
| --------------------------- | --------------------------------------------------- |
| `pom.xml`                   | 新增 `rocketmq-client:4.3.0` 依赖                       |
| `application.yml`           | 新增 `mq.nameserver.addr` 和 `mq.topicname` 配置         |
| **新建** `mq/MqProducer.java` | 普通消息生产者：`asyncReduceStock` 方法发消息                    |
| **新建** `mq/MqConsumer.java` | 消息消费者：收到消息后调 `itemStockDOMapper.decreaseStock` 写数据库 |

### MqProducer.java — 新建

```java
package com.imooc.miaoshaproject.mq;

import com.alibaba.fastjson.JSON;
import com.imooc.miaoshaproject.dao.StockLogDOMapper;
import com.imooc.miaoshaproject.dataobject.StockLogDO;
import com.imooc.miaoshaproject.error.BusinessException;
import com.imooc.miaoshaproject.service.OrderService;
import org.apache.rocketmq.client.exception.MQBrokerException;
import org.apache.rocketmq.client.exception.MQClientException;
import org.apache.rocketmq.client.producer.*;
import org.apache.rocketmq.common.message.Message;
import org.apache.rocketmq.common.message.MessageExt;
import org.apache.rocketmq.remoting.exception.RemotingException;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.stereotype.Component;

import javax.annotation.PostConstruct;
import java.nio.charset.Charset;
import java.util.HashMap;
import java.util.Map;

@Component
public class MqProducer {

    private DefaultMQProducer producer;
    private TransactionMQProducer transactionMQProducer;

    @Value("${mq.nameserver.addr}")
    private String nameAddr;

    @Value("${mq.topicname}")
    private String topicName;

    @Autowired
    private OrderService orderService;

    @Autowired
    private StockLogDOMapper stockLogDOMapper;

    @PostConstruct
    public void init() throws MQClientException {
        // 普通 producer 初始化
        producer = new DefaultMQProducer("producer_group");
        producer.setNamesrvAddr(nameAddr);
        producer.start();

        // 事务型 producer 初始化
        transactionMQProducer = new TransactionMQProducer("transaction_producer_group");
        transactionMQProducer.setNamesrvAddr(nameAddr);
        transactionMQProducer.start();

        transactionMQProducer.setTransactionListener(new TransactionListener() {
            @Override
            public LocalTransactionState executeLocalTransaction(Message msg, Object arg) {
                // 执行本地事务：创建订单（详见第五部分）
                Integer itemId = (Integer) ((Map) arg).get("itemId");
                Integer promoId = (Integer) ((Map) arg).get("promoId");
                Integer userId = (Integer) ((Map) arg).get("userId");
                Integer amount = (Integer) ((Map) arg).get("amount");
                String stockLogId = (String) ((Map) arg).get("stockLogId");
                try {
                    orderService.createOrder(userId, itemId, promoId, amount, stockLogId);
                } catch (BusinessException e) {
                    e.printStackTrace();
                    // 设置对应的 stockLog 为回滚状态
                    StockLogDO stockLogDO = stockLogDOMapper.selectByPrimaryKey(stockLogId);
                    stockLogDO.setStatus(3);
                    stockLogDOMapper.updateByPrimaryKeySelective(stockLogDO);
                    return LocalTransactionState.ROLLBACK_MESSAGE;
                }
                return LocalTransactionState.COMMIT_MESSAGE;
            }

            @Override
            public LocalTransactionState checkLocalTransaction(MessageExt msg) {
                // 回查逻辑（详见第六部分）
                String jsonString = new String(msg.getBody());
                Map<String, Object> map = JSON.parseObject(jsonString, Map.class);
                String stockLogId = (String) map.get("stockLogId");
                StockLogDO stockLogDO = stockLogDOMapper.selectByPrimaryKey(stockLogId);
                if (stockLogDO == null) {
                    return LocalTransactionState.UNKNOW;
                }
                if (stockLogDO.getStatus().intValue() == 2) {
                    return LocalTransactionState.COMMIT_MESSAGE;
                } else if (stockLogDO.getStatus().intValue() == 1) {
                    return LocalTransactionState.UNKNOW;
                }
                return LocalTransactionState.ROLLBACK_MESSAGE;
            }
        });
    }

    // 事务型同步库存扣减消息（第五部分用）
    public boolean transactionAsyncReduceStock(Integer userId, Integer itemId,
            Integer promoId, Integer amount, String stockLogId) {
        Map<String, Object> bodyMap = new HashMap<>();
        bodyMap.put("itemId", itemId);
        bodyMap.put("amount", amount);
        bodyMap.put("stockLogId", stockLogId);

        Map<String, Object> argsMap = new HashMap<>();
        argsMap.put("itemId", itemId);
        argsMap.put("amount", amount);
        argsMap.put("userId", userId);
        argsMap.put("promoId", promoId);
        argsMap.put("stockLogId", stockLogId);

        Message message = new Message(topicName, "increase",
                JSON.toJSON(bodyMap).toString().getBytes(Charset.forName("UTF-8")));
        TransactionSendResult sendResult = null;
        try {
            sendResult = transactionMQProducer.sendMessageInTransaction(message, argsMap);
        } catch (MQClientException e) {
            e.printStackTrace();
            return false;
        }
        if (sendResult.getLocalTransactionState() == LocalTransactionState.ROLLBACK_MESSAGE) {
            return false;
        } else if (sendResult.getLocalTransactionState() == LocalTransactionState.COMMIT_MESSAGE) {
            return true;
        } else {
            return false;
        }
    }

    // 普通同步库存扣减消息
    public boolean asyncReduceStock(Integer itemId, Integer amount) {
        Map<String, Object> bodyMap = new HashMap<>();
        bodyMap.put("itemId", itemId);
        bodyMap.put("amount", amount);

        Message message = new Message(topicName, "increase",
                JSON.toJSON(bodyMap).toString().getBytes(Charset.forName("UTF-8")));
        try {
            producer.send(message);
        } catch (MQClientException | RemotingException | MQBrokerException | InterruptedException e) {
            e.printStackTrace();
            return false;
        }
        return true;
    }
}
```

### MqConsumer.java — 新建

```java
package com.imooc.miaoshaproject.mq;

import com.alibaba.fastjson.JSON;
import com.imooc.miaoshaproject.dao.ItemStockDOMapper;
import org.apache.rocketmq.client.consumer.DefaultMQPushConsumer;
import org.apache.rocketmq.client.consumer.listener.ConsumeConcurrentlyContext;
import org.apache.rocketmq.client.consumer.listener.ConsumeConcurrentlyStatus;
import org.apache.rocketmq.client.consumer.listener.MessageListenerConcurrently;
import org.apache.rocketmq.client.exception.MQClientException;
import org.apache.rocketmq.common.message.Message;
import org.apache.rocketmq.common.message.MessageExt;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.stereotype.Component;

import javax.annotation.PostConstruct;
import java.util.List;
import java.util.Map;

@Component
public class MqConsumer {

    private DefaultMQPushConsumer consumer;

    @Value("${mq.nameserver.addr}")
    private String nameAddr;

    @Value("${mq.topicname}")
    private String topicName;

    @Autowired
    private ItemStockDOMapper itemStockDOMapper;

    @PostConstruct
    public void init() throws MQClientException {
        consumer = new DefaultMQPushConsumer("stock_consumer_group");
        consumer.setNamesrvAddr(nameAddr);
        consumer.subscribe(topicName, "*");

        consumer.registerMessageListener(new MessageListenerConcurrently() {
            @Override
            public ConsumeConcurrentlyStatus consumeMessage(List<MessageExt> msgs,
                    ConsumeConcurrentlyContext context) {
                // 实现库存真正到数据库内扣减的逻辑
                Message msg = msgs.get(0);
                String jsonString = new String(msg.getBody());
                Map<String, Object> map = JSON.parseObject(jsonString, Map.class);
                Integer itemId = (Integer) map.get("itemId");
                Integer amount = (Integer) map.get("amount");

                itemStockDOMapper.decreaseStock(itemId, amount);
                return ConsumeConcurrentlyStatus.CONSUME_SUCCESS;
            }
        });

        consumer.start();
    }
}
```

## 关键讲解

`MqProducer` 用 `@PostConstruct` 在 Bean 初始化后启动 producer，连接到 NameServer 地址。`asyncReduceStock` 方法很简单——把 `itemId` 和 `amount` 放入 Map，JSON 序列化后发到 `TopicTest` Topic。

`MqConsumer` 也类似，启动后订阅同一个 Topic，收到消息后调 `itemStockDOMapper.decreaseStock(itemId, amount)`，真正把库存写入数据库。

MQ 在这里起到了**削峰填谷**的作用：秒杀瞬间几万条消息涌入 MQ，Consumer 按自己的节奏消费，MySQL 不会被瞬间打爆。

## 验证方式

1. 启动 RocketMQ NameServer 和 Broker
2. 启动应用
3. `redis-cli GET promo_item_stock_1` 记下 Redis 库存值
4. 用 `SELECT stock FROM item_stock WHERE item_id=1` 记下 MySQL 库存值
5. 调用下单接口
6. 确认 Redis 库存减了 1
7. 观察应用日志，Consumer 应该打印消费成功的日志
8. 再次 `SELECT stock FROM item_stock`，确认 MySQL 库存也减了 1（可能有轻微延迟）
9. 用 RocketMQ Console 查看 Topic 的消息堆积情况

# 第五部分：MQ 事务型消息实现

## 改动前有什么问题？

第四部分用的是普通消息，存在一个严重问题：**如果下单失败了怎么办？**

```
1. Redis 扣库存 INCR -1 ✅
2. 创建订单 INSERT INTO order... ❌ 失败了！
3. 发 MQ 消息通知减 MySQL 库存 ✅ 已经发了！
```

结果：Redis 扣了库存，MySQL 也减了库存，但订单没创建成功。用户钱扣了（假设），商品库存少了，但没有订单记录——**数据不一致**。

## 改动后发生了什么？

用 RocketMQ 的**事务消息**来解决：

```
1. 发一条"半消息"到 MQ（消费者暂时收不到）
2. 执行本地事务（创建订单）
3. 成功 → Commit 半消息 → Consumer 收到 → 扣 MySQL 库存
   失败 → Rollback 半消息 → Consumer 永远不会收到
```

改动前的普通消息是"先扣 Redis → 创建订单 → 发消息"，订单失败后消息收不回。
改动后的事务消息是"先发半消息 → 创建订单 → commit/rollback"，订单失败半消息就回滚，消费者永远不会去扣 MySQL。

| `MqProducer.java`      | 新增 `TransactionMQProducer`、`TransactionListener`、`transactionAsyncReduceStock` 方法      |
| `OrderController.java` | 下单入口从 `orderService.createOrder(...)` 改为 `mqProducer.transactionAsyncReduceStock(...)` |

## 参考代码

### OrderController.java — 下单入口改造

```java
// 下单入口改为事务型消息
@RequestMapping(value = "/createorder", method = {RequestMethod.POST}, consumes = {CONTENT_TYPE_FORMED})
@ResponseBody
public CommonReturnType createOrder(@RequestParam(name = "itemId") Integer itemId,
                                    @RequestParam(name = "amount") Integer amount,
                                    @RequestParam(name = "promoId", required = false) Integer promoId)
                                    throws BusinessException {

    String token = httpServletRequest.getParameterMap().get("token")[0];
    if (StringUtils.isEmpty(token)) {
        throw new BusinessException(EmBusinessError.USER_NOT_LOGIN, "用户还未登陆，不能下单");
    }
    UserModel userModel = (UserModel) redisTemplate.opsForValue().get(token);
    if (userModel == null) {
        throw new BusinessException(EmBusinessError.USER_NOT_LOGIN, "用户还未登陆，不能下单");
    }

    // 判断是否库存已售罄，若对应的售罄 key 存在，则直接返回下单失败
    if (redisTemplate.hasKey("promo_item_stock_invalid_" + itemId)) {
        throw new BusinessException(EmBusinessError.STOCK_NOT_ENOUGH);
    }

    // 加入库存流水 init 状态
    String stockLogId = itemService.initStockLog(itemId, amount);

    // 再去完成对应的下单事务型消息机制
    if (!mqProducer.transactionAsyncReduceStock(userModel.getId(), itemId, promoId, amount, stockLogId)) {
        throw new BusinessException(EmBusinessError.UNKNOWN_ERROR, "下单失败");
    }
    return CommonReturnType.create(null);
}
```

OrderController 需要新增注入：

```java

@Autowired
private ItemService itemService;
```

## 关键讲解

这是整个秒杀系统中最核心的设计。事务消息的流程分三步：

**第一步：发半消息**

```java
sendResult = transactionMQProducer.sendMessageInTransaction(message, argsMap);
```

这条消息发到 MQ 后处于"半消息"状态，消费者看不到它。

**第二步：执行本地事务**

```java
public LocalTransactionState executeLocalTransaction(Message msg, Object arg) {
    // 从 arg 中取出参数
    orderService.createOrder(userId, itemId, promoId, amount, stockLogId);
    return LocalTransactionState.COMMIT_MESSAGE;  // 或 ROLLBACK_MESSAGE
}
```

创建订单成功就返回 COMMIT，失败就返回 ROLLBACK。

**第三步：MQ 根据结果决定**

- COMMIT → 半消息变成正常消息，Consumer 收到后扣 MySQL 库存
- ROLLBACK → 半消息被删除，Consumer 永远收不到

## 验证方式

1. 启动 RocketMQ（含事务消息支持）
2. 调用下单接口，参数正确（能成功下单）
3. 观察控制台日志，应该看到 `COMMIT_MESSAGE`
4. 消费者收到消息，MySQL 库存扣减
5. 再调用下单接口，给一个不存在的 itemId（创建订单会失败）
6. 观察日志，应该看到 `ROLLBACK_MESSAGE` + `stockLog status=3`
7. 确认消费者没有收到这条消息（MySQL 库存没变化）
8. 在 RocketMQ Console 中查看消息轨迹，确认半消息的状态

# 第六部分：操作流水

## 改动前有什么问题？

事务消息有一个关键场景：**如果 `executeLocalTransaction` 执行到一半，应用挂了呢？** 比如订单已经插入了数据库，但应用在返回 COMMIT 之前宕机了，MQ 没收到 commit 确认。

这时候半消息卡住了，MQ 会不断回调 `checkLocalTransaction` 来确认状态。但问题是——MQ 回调时怎么知道这个订单到底成功了没有？

## 改动后发生了什么？

引入 `stock_log` 操作流水表。下单前先插入一条流水记录（status=1 初始化），下单成功后更新为 status=2（成功），下单失败更新为 status=3（回滚）。

`checkLocalTransaction` 被回调时，查 `stock_log` 表：

| stock_log status | 含义    | 返回值                    |
|:----------------:| ----- | ---------------------- |
| 1                | 还在处理中 | UNKNOW（MQ 稍后再查）        |
| 2                | 成功了   | COMMIT_MESSAGE（投递消息）   |
| 3                | 失败了   | ROLLBACK_MESSAGE（删除消息） |
| 不存在              | ——    | UNKNOW                 |

## 具体改动

| 文件                                              | 改动                                                            |
| ----------------------------------------------- | ------------------------------------------------------------- |
| **新建** `dataobject/StockLogDO.java`             | stock_log 表对应的 DO，4 个字段                                       |

# 第七部分：库存售罄标志位

## 改动前有什么问题？

扣库存用 Redis 的 INCR 操作，大部分请求在 Redis 层面就被处理了。但如果不做售罄标记，即使库存已经减到 0，**后续所有请求还是会走一遍完整链路**：校验登录 → 查缓存验证商品 → 初始化流水（写 stock_log）→ 发事务消息 → 扣 Redis 库存（发现负数）→ 回补。

每个请求在发现库存不足之前，已经做了很多无用功，白白消耗系统资源。

## 改动后发生了什么？

在 Redis 库存减到 0 的瞬间（`decreaseStock` 中 `result == 0`），打一个标记 `promo_item_stock_invalid_{itemId} = "true"`。

OrderController 在下单入口的**最前面**检查这个标记，如果有就直接抛异常拒绝，跳过后续所有逻辑。

```
改动前：库存=0 后，10000 个请求 → 走完整链路 → 发现库存不足 → 拒绝
改动后：库存=0 后，10000 个请求 → 检查标记 → 直接拒绝 ✅（1ms）
```

## 具体改动

| 文件                     | 改动                                                                                                               |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `ItemServiceImpl.java` | `decreaseStock` 中 `result == 0` 分支：`redisTemplate.opsForValue().set("promo_item_stock_invalid_"+itemId, "true")` |
| `OrderController.java` | 下单入口最前面：`if (redisTemplate.hasKey("promo_item_stock_invalid_"+itemId)) throw STOCK_NOT_ENOUGH`                   |

## 参考代码

```java
// ItemServiceImpl.decreaseStock() 中 — result == 0 分支
} else if (result == 0) {
    // 打上库存已售罄的标识
    redisTemplate.opsForValue().set("promo_item_stock_invalid_" + itemId, "true");
    return true;
}
```

```java
// OrderController.createOrder() 中 — 入口最前面

    throw new BusinessException(EmBusinessError.STOCK_NOT_ENOUGH);
}
```

## 关键讲解

这个改动只有两行代码，但效果巨大——它是秒杀系统最后一道防线的**快速失败**机制。售罄之后所有请求在入口处就直接被拒绝了，根本不会进入后面的 Redis 扣库存、事务消息、数据库写入等流程。

一个常见问题：售罄标记什么时候清除？在这个实现中，售罄标记会在下一次 `publishPromo`（活动发布）时被覆盖——因为 `publishPromo` 重新 SET 了 `promo_item_stock_{id}` 的值，但**没有删除** `promo_item_stock_invalid_{id}`。如果你需要清除这个标记，可以在 `publishPromo` 方法中加上：

```java
redisTemplate.delete("promo_item_stock_invalid_" + itemModel.getId());
```

## 验证方式

1. `publishPromo` 发布活动，库存设小一点（比如 5）
2. 连续调用下单接口 5 次
3. 第 6 次调用时，应该直接返回"库存不足"，不进入下单流程
4. `redis-cli GET promo_item_stock_invalid_1`，确认值为 "true"
5. 再次 `publishPromo`，确认 `promo_item_stock_1` 恢复为原始值
6. 检查售罄标记是否还存在（当前实现下不会自动清除）

# 七部分串联总结

```
秒杀开始前：运营调用 /publishpromo → 库存同步到 Redis  [第二部分]

秒杀开始：
  用户请求 → OrderController.createOrder
    ├── [第七部分] 检查售罄标记 → 售罄则秒拒绝
    ├── [第六部分] 写 stock_log (status=1) → 生成流水ID
    ├── [第五部分] 发事务半消息
    │     ├── executeLocalTransaction:
    │     │   ├── [第一部分] 缓存校验 商品/用户
    │     │   ├── [第三部分] Redis INCR 扣库存
    │     │   │     └── result==0 → [第七部分] 打售罄标记
    │     │   ├── 创建订单
    │     │   └── [第六部分] 更新 stock_log (status=2)
    │     ├── COMMIT → Consumer 收到
    │     │     └── [第四部分] MySQL 异步减库存
    │     └── ROLLBACK → Consumer 收不到
    │           └── [第六部分] stock_log (status=3)
    └── 返回结果给用户
```
