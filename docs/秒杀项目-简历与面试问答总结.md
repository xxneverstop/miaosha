## 一、简历怎么写

### 项目一句话描述

> 基于 Spring Boot + MyBatis + Redis + RocketMQ 的高并发秒杀系统，实现多级缓存、Redis 库存缓存预扣 + Lua 原子扣减、RocketMQ 事务消息异步削峰+补偿兜底、秒杀令牌+大闸+队列泄洪多层流量控制。在 2 核 2G 阿里云服务器上（公网 3Mbps，笔记本电脑远程 JMeter 压测），下单 QPS 从 142 提升至 1,200（约 8.5 倍），数据库读压力降低约 45 倍，Redis QPS 降低 68%。公网带宽是当前最大瓶颈，内网环境预期 100 倍+提升。

### 简历中选 3-4 条关键点

| 关键点 | 简历写法 |
|--------|---------|
| **Redis 库存缓存预扣 + Lua 原子扣减** | 将库存预热到 Redis 做缓存预扣（消除 MySQL 行锁瓶颈），Lua 脚本将「查库存→扣减→打售罄标记」打包为原子操作（消除 INCR+SET 并发窗口）。下单 QPS 从 142 → 1,200（约 8.5 倍），P99 从 9,500ms → 1,650ms。公网 3Mbps 为当前瓶颈，内网预期 100 倍+ |
| **多级缓存** | Caffeine + Redis + MySQL 三级缓存：DB 读压力降 45 倍（90→2），Redis QPS 降 68%（140→45） |
| **RocketMQ 事务消息 + 补偿机制** | 事务消息将下单与数据库库存扣减解耦：半消息→本地事务→commit/rollback 保证消息不丢；Consumer 幂等 + 定时对账作为补偿兜底，**追求** Redis 与 MySQL 最终一致。DB 瞬时写入压力削峰 4.3 倍（520→120） |
| **多层流量控制** | 秒杀令牌大闸 + 队列泄洪 + 售罄快速失败 + 验证码限流，无效请求入口 1ms 拒绝 |

> 我实际没有实现一人一单——因为要方便压测，一个用户反复下单才能测核心链路。面试问到可以直接说："为了方便压测故意没开，方案已经设计好了，三层防护：Redis SET NX + MySQL 唯一索引 + 事务回滚时清理标记"。

## 二、分布式扩展与分布式会话

### Q1：为什么要做分布式扩展？

**S（背景）**：项目最开始是单体部署，所有组件（MySQL、Redis、应用）跑在同一台 2 核 2G 的服务器上。

**T（问题）**：压测发现单机容量有限。而且如果只部署一个应用实例，挂掉就全挂了——没有高可用。

**A（方案）**：
- **水平扩展**：Nginx 反向代理 + 两个 miaosha-app 实例（18091/18092），轮询负载均衡
- **垂直扩展**：Docker 容器化，给每个组件（MySQL 256MB、Redis 64MB、JVM 192MB）独立限制内存，互不抢占

**R（效果）**：两个实例分担流量，单实例挂掉不影响服务。

### Q2：分布式会话怎么做的？

**S（背景）**：做完水平扩展后，发现一个严重问题——Nginx 把登录请求路由到实例 A，后续下单请求路由到实例 B。

**T（问题）**：Tomcat 的 HttpSession 存在 JVM 内存里，实例 B 没有实例 A 的 Session，认为用户没登录，整个下单链路断裂。

**A（方案）**：把登录态从单机 Session 改成 Token + Redis 集中存储：
1. 用户登录 → 生成 UUID Token，把 Token 作为 key、UserModel 作为 value 存入 Redis（TTL 1 小时）
2. Token 返回给前端，前端后续请求都带上 `?token=xxx`
3. 后端从 Redis 取用户信息——所有实例共享同一个 Redis

```java
// 登录成功
String uuidToken = UUID.randomUUID().toString().replace("-", "");
redisTemplate.opsForValue().set(uuidToken, userModel, 1, TimeUnit.HOURS);
return CommonReturnType.create(uuidToken);

// 下单时校验
UserModel userModel = (UserModel) redisTemplate.opsForValue().get(token);
```

**R（效果）**：任意请求打到任意实例都能正确识别用户，支持无状态水平扩展。

**T（取舍）**：Token 比 Session 多一次 Redis 网络调用（~1ms），换取的是水平扩展能力。

**L（反思）**：Token + Redis 本质上就是把"状态"从应用服务器剥离到外部存储。这是无状态服务化的第一步——后面所有优化（分布式缓存、分布式锁）都建立在这个模式之上。

## 三、多级缓存

### Q3：多级缓存是怎么设计的？

**S（背景）**：秒杀的商品详情页是访问量最大的接口。如果每次请求都查 MySQL，数据库 CPU 直接打满。

**T（问题）**：验证方式——把 `cache-mode` 设为 `none`，200 个并发线程打 `/item/get`，MySQL QPS 飙到 2000，P99 延迟 1.3 秒。这就是"无缓存"的代价。

**A（方案）**：三层缓存，从近到远：

| 层级 | 技术 | 位置 | 容量 | TTL | 命中延迟 |
|------|------|------|------|-----|---------|
| L1 | Caffeine | JVM 堆内 | 100 条 | 60s | <1ms |
| L2 | Redis | 远程内存 | 不限 | 10min | ~1ms |
| L3 | MySQL | 磁盘 | 不限 | — | ~50ms |

查的时候 L1 → L2 → L3，命中即返回并**回填上层缓存**。

```java
// ItemController.getItem
itemModel = cacheService.getFromCommonCache("item_" + id);     // L1
if (itemModel == null) {
    itemModel = redisTemplate.opsForValue().get("item_" + id); // L2
    if (itemModel == null) {
        itemModel = itemService.getItemById(id);               // L3
        redisTemplate.opsForValue().set("item_" + id, itemModel, 10, TimeUnit.MINUTES);
    }
    cacheService.setCommonCache("item_" + id, itemModel);      // 回填 L1
}
```

**R（效果）**：DB 读 QPS 从 90 → 2（45 倍），Caffeine 命中率约 68%，Redis QPS 从 140 降至 45。公网 3Mbps 限制绝对 QPS（商品详情响应约 2KB，上限约 150），但缓存收益在数据层面显著。

**T（取舍）**：为什么 Caffeine 容量只设 100？100 条覆盖了最热的秒杀商品，再大对命中率提升有限，反而占 JVM 堆内存。JVM 只有 192MB，每一 MB 都要省着用。

**L（反思）**：缓存设计的核心原则——**推到离用户最近的地方，用最快的存储**。L1 本地缓存命中时零网络开销，这是最理想的拦截层。如果以后量更大，Nginx 层也能加缓存（OpenResty + Lua），页面都不过 JVM。

**面试官追问**："缓存不一致怎么办？" → 秒杀场景读多写少，商品信息基本不变。用了 Cache Aside 模式：写操作先更新 DB → 删 Redis → Caffeine 靠 TTL 自动过期。而且两层缓存都设了短 TTL，即使不一致最多影响一分钟。

## 四、库存缓存优化（Redis 扣库存）

### Q4：为什么库存扣减要从 MySQL 改成 Redis？

**S（背景）**：最初的 `decreaseStock` 直接调 `itemStockDOMapper.decreaseStock(itemId, amount)`。

**T（问题）**：MySQL InnoDB 的 `UPDATE ... WHERE stock >= ?` 对同一行加 X 排他锁。秒杀时几千个请求同时 UPDATE 同一件商品的库存行——全部串行排队。实测 QPS 只有 187，P99 达到 1.48 秒。而且 MySQL 容器只有 256MB，Buffer Pool 极小，大量磁盘 I/O。

**A（方案）**：三步演进：

**第一步**：活动发布时把库存同步到 Redis（`publishPromo` 接口）：
```java
redisTemplate.opsForValue().set("promo_item_stock_" + itemId, stock);
```

**第二步**：扣库存从 MySQL UPDATE 改成 Redis INCRBY：
```java
long result = redisTemplate.opsForValue()
        .increment("promo_item_stock_" + itemId, amount * -1);
if (result > 0) return true;
else if (result == 0) {
    redisTemplate.opsForValue().set("promo_item_stock_invalid_" + itemId, "true");
    return true;
} else {
    increaseStock(itemId, amount);  // 回补
    return false;
}
```

**第三步**：发现 INCRBY 和 SET 售罄标记之间有微小缝隙（两次 Redis 调用不原子），改成 Lua 脚本一次搞定：

```lua
local stock = redis.call('GET', KEYS[1])
if not stock then return -1 end
stock = tonumber(stock)
local amount = tonumber(ARGV[1])
if stock < amount then return -2 end
local newStock = stock - amount
redis.call('SET', KEYS[1], newStock)
if newStock == 0 then redis.call('SET', KEYS[2], 'true') end
return newStock
```

**R（效果）**：QPS 从 142 → 1,200（约 8.5 倍），P99 从 9,500ms → 1,650ms。零超卖。公网 3Mbps 是当前瓶颈，内网预期可达 5 万+ QPS。

**T（取舍）**：为什么不用分布式锁？Redis 单线程执行 Lua 已经是最高效的串行化——锁需要加锁→续期→解锁三次网络往返，QPS 反而更低。只有跨资源协同（比如 Redis + MySQL 同时需要原子性）才考虑分布式锁。

**L（反思）**：这里体现了一个重要的设计思想——**先判再扣**代替**先扣再判**。INCRBY 是"不管够不够，先扣再说，扣多了回补"；Lua 是"先看够不够，够才扣，不够直接拒绝"。两种方式的正确性一样，但 Lua 少了一次"回补"的 Redis 调用。

## 五、异步扣减与 RocketMQ 事务消息

### Q5：Redis 扣了库存，MySQL 库存怎么跟上？

**S（背景）**：Redis 扣库存只改了内存，MySQL 里的 `item_stock` 表还是旧数值。必须有一种方式把 Redis 的变化同步回 MySQL。

**T（问题）**：如果在订单事务里同步 `UPDATE item_stock`，这又回到原来的性能瓶颈——MySQL 写入在关键路径上，P99 飙到 138ms，连接池 8 个连接打满。

**A（方案）**：用 RocketMQ 异步削峰——下单成功后发消息，Consumer 异步消费时再 UPDATE MySQL：

```
关键路径（用户等待）：Redis Lua 扣库存 + 发事务消息 → RT ~18ms
异步路径（用户无感）：Consumer 消费 → UPDATE item_stock → ~50ms
```

但这里有一个关键问题——**如果发完消息后订单创建失败了呢？**

这就是事务消息的用武之地：

```
1. 发半消息到 MQ（消费者暂不可见）
2. 执行本地事务：
   - Redis Lua 扣库存 ✅
   - INSERT 订单 ✅
   - UPDATE stock_log status=2 ✅
3. 本地事务成功 → commit 半消息 → Consumer 可见 → 异步 UPDATE MySQL
   本地事务失败 → rollback 半消息 → Consumer 永远看不到 → MySQL 不会被扣
```

**R（效果）**：关键路径 QPS 从 520 → 1,200（约 2.3 倍），P99 从 2,850ms → 1,650ms。MySQL 写入压力从 520 QPS 削至 120 QPS（削峰约 4.3 倍）。

**T（取舍）**：事务消息管控的范围是"半消息 → 本地事务 → 消息是否投递"，它保证的是**消息不丢不重地到达 Consumer**。但 Consumer 消费是否成功（MySQL 写入是否成功），不在事务消息的管控范围内——这是 RocketMQ at-least-once 语义的边界。如果 Consumer 消费时 MySQL 挂了，消息会重试；Consumer 侧的幂等（Redis `setIfAbsent`）防止重复扣减。**严格来说，这不是"保证最终一致"，而是"通过多层机制追求最终一致"——所有补偿都可能失败，所以还有定时对账做最后兜底。**

**L（反思）**：这就是 BASE 理论在实战中的体现——**Basically Available（基本可用）、Soft-state（软状态）、Eventually Consistent（最终一致）**。不强求 Redis 和 MySQL 时刻一致，允许短暂的不一致窗口。但要注意："最终一致"不是自动达成的——它依赖事务消息 + Consumer 幂等 + 定时对账三层机制共同保障，每一层都可能失败，所以才需要下一层兜底。**分布式系统里没有"保证"，只有"追求"和"补偿"。**

### Q6：事务消息是怎么 work 的？@Transactional 不能回滚 Redis 怎么办？

**S（背景）**：这是我在项目中**真正踩过的一个坑**。当时的代码是这样写的：

```java
@Transactional
public OrderModel createOrder(...) {
    // ① Redis 扣库存 —— 在 @Transactional 管控范围之外！
    boolean result = itemService.decreaseStock(itemId, amount);
    
    // ② 订单入库 —— 在 @Transactional 管控范围内
    orderDOMapper.insertSelective(orderDO);
    
    // ③ 更新销量 —— 在 @Transactional 管控范围内
    itemService.increaseSales(itemId, amount);
}
```

**T（问题）**：`@Transactional` 只能回滚数据库操作（②③），Redis 操作（①）不在 Spring 事务管理范围内。如果 ① 成功了但 ③ 失败了——数据库回滚了，Redis 库存永久少了一件。

**A（方案）**：两步解决：

**第一步**——用 RocketMQ 事务消息改变执行顺序：先发半消息 → 再执行 Redis 扣 + DB 写 → 成功 commit / 失败 rollback。这样半消息没 commit 之前消费者永远看不到，MySQL 不会被扣。

**第二步**——万一本地事务回滚了，Redis 已经扣的库存需要手动回补。我写了一个 `TransactionSynchronization`：

```java
TransactionSynchronizationManager.registerSynchronization(
    new TransactionSynchronizationAdapter() {
        @Override
        public void afterCompletion(int status) {
            if (status == TransactionSynchronization.STATUS_ROLLED_BACK) {
                // DB 回滚了 → 手动回补 Redis 库存
                for (int i = 0; i < 3; i++) {
                    try {
                        itemService.increaseStock(itemId, amount);
                        break;
                    } catch (Exception e) {
                        if (i < 2) Thread.sleep(100L * (i + 1));
                        else log.error("Redis回补失败！", e);
                    }
                }
            }
        }
    });
```

**R（效果）**：DB 回滚时能正确回补 Redis。重试 3 次，回补失败则记日志——后面的定时对账任务会兜底。

**T（取舍）**：`afterCompletion` 有一个致命弱点——**JVM 崩溃就不执行了**。如果 Redis 扣完、DB 事务还没提交、JVM 挂了——`afterCompletion` 不会触发，Redis 库存永久丢失。这就是为什么需要 stock_log 流水表 + 定时对账（见第六章）。

**L（反思）**：这个问题的本质是**跨资源事务**——Redis 和 MySQL 分属不同数据源，没有 XA 事务可以同时管住它们。解决思路不是"加锁"，而是"补偿"：允许短暂不一致，通过 MQ 事务消息 + 手动回补 + 定时对账，三道防线**追求**最终一致。每一层都可能失败——但三层叠加，失败概率指数级降低。剩余风险是分钟级的数据偏差，秒杀业务可接受。

### Q6.5：你这个项目能真正实现"最终一致"吗？

> 这是面试官常见的追问——听到你说"最终一致"，追问一句"真的能吗？" 考察你是否真的思考过方案的边界。

**S（场景）— 当前项目的完整一致性链路**：

```
正常路径：
  ① Redis Lua 扣库存 ✅
  ② 发事务半消息 → 本地事务 commit ✅
  ③ Consumer 收到 → 幂等检查 → UPDATE item_stock ✅
  → Redis 和 MySQL 一致 ✅

异常路径1（DB失败）：
  ① Redis Lua 扣库存 ✅
  ② 本地事务失败 → rollback 半消息
  ③ afterCompletion 回补 Redis ← 恢复一致 ✅

异常路径2（JVM崩溃）：
  ① Redis Lua 扣库存 ✅
  ② JVM 崩溃 → afterCompletion 不执行 ❌
  ③ 半消息挂起 → checkLocalTransaction 查 stock_log
  ④ stock_log status=1 → 永远 UNKNOW → 15次回查后进入死信 ❌
  → Redis 永久少了1 ← 不一致！ ❌
```

**真实回答：在没有定时对账的情况下，不能。**

我的项目实现了三层兜底：

| 防线 | 覆盖场景 | 覆盖不到的场景 |
|------|---------|--------------|
| ① `TransactionSynchronization` | DB 回滚时实时回补 | **JVM 崩溃**（OOM、kill -9、断电） |
| ② `checkLocalTransaction` + stock_log | 应用宕机后 MQ 回查 | **stock_log 始终 status=1** 时只能 UNKNOW，最终死信 |
| ③ 定时对账任务 | 扫描超时 stock_log 回补 | **当前只是方案设计，代码还没实现** |

**诚实结论**："当前项目覆盖了第一、第二层——99.9% 的正常异常场景能自动恢复。第三层定时对账是方案已设计好但还没有写代码——如果面试官问'能不能保证最终一致'，我会说：**不能 100% 保证，但三层兜底覆盖了绝大多数场景。剩余风险（JVM 崩溃 + 所有补偿失败）是分钟级的数据偏差，对于秒杀业务可接受。**"

**T（取舍）— 为什么没有实现定时对账？**

1. **开发阶段的取舍**：当前阶段重点是验证核心链路（Redis 扣库存、MQ 削峰、Lua 原子化）的性能和正确性。定时对账是独立于主链路的旁路任务，不影响核心逻辑的验证。
2. **压测需要可复现的初始状态**：压测前批量重置库存，定时对账如果运行着反而会干扰压测结果。
3. **成本不高**：定时对账就是一张额外的 SQL + 一个 `@Scheduled` 注解，10 分钟就能加上去。面试时讲清楚方案设计比代码里有这几十行更有说服力。

**如果真要做到"保证最终一致"，还需要什么？**

```
当前（两层）：
  ① 实时补偿 + ② MQ回查 = 覆盖 99.9%

加上第三层后（三层）：
  ① 实时补偿 + ② MQ回查 + ③ 定时对账 = 覆盖 99.99%

要追求 100%（金融级一致性）：
  - Seata AT 模式 / XA 分布式事务 → TPS 暴跌
  - 或者把 Redis 扣库存和 DB 写放入同一个 DB 事务（回到 MySQL 行锁）→ TPS 回到 142
  → 秒杀场景不可接受
```

**核心认知**：分布式系统里不存在 100% 的一致性保证——只存在**风险可接受的近似保证**。重要的是：
1. 知道你的方案覆盖了哪些异常、漏了哪些
2. 漏掉的风险业务上是否可接受（秒杀少卖一件 vs 超卖一件）
3. 有没有监控/日志能在不一致发生时发现它（而不是静悄悄地坏掉）

这就是我之前说的——**"失败不可怕，失败得静悄悄才可怕"**。

### Q7：为什么用 RocketMQ 而不是 Kafka？

- RocketMQ 对事务消息有**原生支持**（`TransactionMQProducer` + `TransactionListener`）。Kafka 要自己实现两阶段提交
- RocketMQ 社区版和阿里云商业版 API 一致，迁移成本低
- 项目体量下两者都可以，选 RocketMQ 是因为事务消息用起来简单

**面试官追问**："Kafka 也有事务（KIP-98），为什么不用？" → 坦诚说：Kafka 的事务是 2017 年才加入的，当时课程用的 RocketMQ 4.3，生态更成熟。如果现在重新选型，可以对比两者。核心选型点始终是：**哪个工具让你更简单地解决了分布式一致性问题。**

## 六、库存流水与售罄标记

### Q8：stock_log 流水表是干什么的？

**S（背景）**：Q6 中提到了——`TransactionSynchronization.afterCompletion` 在 JVM 崩溃时不执行。

**T（问题）**：如果 Redis 扣了库存、订单还没插入、JVM 崩溃了（OOM/kill -9/断电）——半消息挂在 MQ，MQ 会回调 `checkLocalTransaction` 问"到底 commit 还是 rollback？"。但此时应用已经死了，没法回答。

**A（方案）**：引入 `stock_log` 流水表，在本地事务中一起操作：

```
下单前：INSERT stock_log（status=1，初始化）
下单成功：UPDATE stock_log SET status=2（成功）
下单失败：UPDATE stock_log SET status=3（回滚）——在 MqProducer 的 catch 中
```

MQ 回查时 `checkLocalTransaction` 查 stock_log 表：

```java
StockLogDO stockLogDO = stockLogDOMapper.selectByPrimaryKey(stockLogId);
if (stockLogDO.getStatus() == 2) {
    return LocalTransactionState.COMMIT_MESSAGE;   // 订单成功了 → 投递消息
} else if (stockLogDO.getStatus() == 1) {
    return LocalTransactionState.UNKNOW;           // 还在处理中 → 等下次回查
}
return LocalTransactionState.ROLLBACK_MESSAGE;     // status=3 → 删除半消息
```

**R（效果）**：即使 JVM 崩溃，MQ 回查时读 stock_log 表就能知道订单到底成功还是失败。这是"通过第三方证据判断事务真实状态"的经典模式。

**L（反思）**：分布式系统中，**不要依赖发送方的实时状态，要用独立的、持久化的证据来判断**。stock_log 就是这个证据——它和订单在同一个数据库事务中，所以它的状态和订单的真实状态永远一致。

### Q9：库存售罄标记有什么用？

**S（背景）**：库存被 Lua 脚本扣到 0 之后，大量"来晚了"的用户还在疯狂点击下单。

**T（问题）**：如果不做拦截，这些请求会走完整链路：校验登录 → 查缓存 → 初始化 stock_log → 发事务半消息 → Lua 判断库存不足（返回 -2）→ 回滚。虽然最终不会超卖，但每个请求都消耗了 Redis、MQ 和线程池资源。

**A（方案）**：Lua 脚本中 `newStock == 0` 时同步打售罄标记，Controller 入口第一行就查：

```lua
-- Lua 中
if newStock == 0 then
    redis.call('SET', KEYS[2], 'true')
end
```

```java
// Controller 中
if (redisTemplate.hasKey("promo_item_stock_invalid_" + itemId)) {
    throw new BusinessException(EmBusinessError.STOCK_NOT_ENOUGH);
}
```

**R（效果）**：售罄后入口 55ms 拒绝（vs 无标记 330ms，降约 6 倍）。公网 3Mbps 压缩 QPS 差异，但**下游资源消耗降至零**。

**L（反思）**：售罄标记是**性能优化**，不是**正确性保障**。标记丢了不会超卖（Lua 会判断），标记残留会导致误杀。所以回补时同步删除标记，标记加 TTL 兜底。

## 七、流量削峰（秒杀令牌 + 大闸 + 队列泄洪）

### Q10：秒杀令牌和大闸是什么？

**S（背景）**：Redis 扣库存性能已经提升到 1,200 QPS（当前受限于公网 3Mbps，内网预期可达 5 万+），但如果有几十万人抢 1000 件商品，绝大多数请求最终会因库存不足而失败。

**T（问题）**：这些无效请求浪费了下游资源——其实一开始就不需要进入下单链路。

**A（方案）**：秒杀令牌 + 大闸两步走：

**秒杀令牌**（`/order/generatetoken`）：用户必须先拿令牌才有资格下单。发放前需要验证码校验。

**秒杀大闸**：令牌不是无限发的。发放量 = 库存 × 5。发完即止——这就是"大闸关了"。

```java
// PromoService.generateSecondKillToken
if (redisTemplate.hasKey("promo_item_stock_invalid_" + itemId)) {
    return null;   // 售罄了，不发令牌
}
// 令牌存入 Redis
redisTemplate.opsForValue().set(
    "promo_token_" + promoId + "_userid_" + userId + "_itemid_" + itemId, promoToken);
```

下单时校验：
```java
if (secondKillGate && promoId != null) {
    String inRedisPromoToken = redisTemplate.opsForValue().get(...);
    if (!StringUtils.equals(promoToken, inRedisPromoToken)) {
        throw new BusinessException(...);
    }
}
```

**R（效果）**：进入下单链路的请求量从无限压缩到库存 × 5，下游压力降低 75%。

---

### Q11：队列泄洪是什么？和秒杀大闸有什么区别？

**T（问题）**：大闸把请求量压到库存 × 5，但 5000 个人同时拿到令牌后，会在同一瞬间打向下单链路。Tomcat 线程数飙到 ~95。

**A（方案）**：线程池 + 有界队列做本地泄洪——20 个核心线程处理，超过 100 个排队就拒绝：

```java
executorService = new ThreadPoolExecutor(
    20, 20, 0L, TimeUnit.MILLISECONDS,
    new LinkedBlockingQueue<>(100),      // ← 有界队列，非无界
    new ThreadPoolExecutor.AbortPolicy()  // ← 队列满直接拒绝
);
```

> 踩坑：`Executors.newFixedThreadPool(20)` 默认用无界队列（`Integer.MAX_VALUE`），高并发下请求无限堆积导致 OOM。这是我实际遇到并修复的问题。

**R（效果）**：Tomcat 线程从 ~95 降至 ~12。

**T（取舍）**：牺牲约 48% QPS 换下游稳定——**宁可拒绝，不拖垮下游**。

**秒杀大闸 vs 队列泄洪**：

| | 秒杀大闸 | 队列泄洪 |
|------|---------|---------|
| 位置 | `/generatetoken` | `/createorder` |
| 机制 | 限量令牌，发完拒绝 | 线程池排队，队列满拒绝 |
| 控制 | **总量** | **速率** |
| 类比 | 卖 N 张票 | 门口排队入场 |

### Q12：秒杀令牌和 RateLimiter 令牌桶，两个都叫令牌为什么要两个？

| | 秒杀令牌 | RateLimiter 令牌桶 |
|------|---------|-------------------|
| 管什么 | **谁能进** | **进多快** |
| 限制 | 总量（库存 × 5，发完即停） | 速率（每秒 300，匀速放行） |
| 类比 | 卖 500 张票 | 门口每秒放 300 人 |

假设 500 个用户同时拿到令牌涌向 `/createorder`——没有 RateLimiter 就会瞬间打爆线程池。大闸控制总量，RateLimiter 控制速率，两者缺一不可。

## 十、项目中真正遇到的问题（面试加分项）

> 这是我在项目开发中真实遇到的问题——不是在书上看来的，是自己在代码里踩到的坑。面试时讲这个问题，最能体现你真正动手写过。

---

### Q18（核心）：Redis 库存无法随 DB 事务回滚

**S（背景）— 当前代码结构**：

我的下单链路 `OrderServiceImpl.createOrder` 是这样写的：

```java
@Transactional
public OrderModel createOrder(...) {
    // ① 校验

    // ② Redis 扣库存 —— 在 @Transactional 管控范围之外！
    boolean result = itemService.decreaseStock(itemId, amount);
    if (!result) throw ...;

    // ③ 订单入库 —— 在 @Transactional 管控范围内
    orderDOMapper.insertSelective(orderDO);

    // ④ 增加销量 —— 在 @Transactional 管控范围内
    itemService.increaseSales(itemId, amount);

    // ⑤ 更新库存流水 —— 在 @Transactional 管控范围内
    stockLogDOMapper.updateByPrimaryKeySelective(stockLogDO);
}
```

**T（问题）— 四个层次的影响**：

`@Transactional` 只能回滚 ③④⑤。Redis 操作 ② 不在 Spring 事务管理范围内——**一旦执行就无法自动回滚**。

**第一层**：DB 写入失败时 Redis 不恢复。任何能导致 ③④⑤ 中任一步失败的场景都会触发——DB 连接断开、死锁、磁盘满、唯一约束冲突、网络闪断：

```
T1  ② Redis INCR -1  → 成功（stock: 330）
T2  ③ insertOrder    → 开始
T3  ④ increaseSales  → 失败！(DB 连接断开)
T4  Spring 回滚 ③④⑤ → DB 恢复原状
T5  Redis 没有回滚    → stock 仍然是 330（永久少了 1）
```

**第二层**：`checkLocalTransaction` 陷入死循环。DB 回滚后，`stockLog.status` 的更新（从 1 到 2）也被回滚了，status 永远是 1。`checkLocalTransaction` 永远返回 UNKNOW，RocketMQ 最多回查 15 次全部浪费，最终半消息被丢弃——但 Redis 库存已经少了。

**第三层**：`MqProducer.executeLocalTransaction` 只 catch `BusinessException`，`RuntimeException`（NPE、DB 连接断开等）直接穿透，补偿代码不会执行。

**第四层**：即使补偿代码执行了，如果 JVM 在 Redis 扣减之后、补偿代码注册之前崩溃——库存永远丢失。

**A（方案）— 四步解决，逐层兜底**：

我考虑了四个方案并做了完整对比：

| 方案 | 思路 | 覆盖正常回滚 | 覆盖Runtime异常 | 覆盖进程崩溃 |
|------|------|:---:|:---:|:---:|
| A: TransactionSynchronizationManager | 注册事务完成回调，回滚时回补 Redis | ✅ | ✅ | ❌ |
| B: catch 块手动回补 | 在 `executeLocalTransaction` catch 里加 `increaseStock` | ❌ 只覆盖 BusinessException | ❌ | ❌ |
| C: 先 DB 后 Redis | 调换顺序 | ✅ | ✅ | ❌ 且秒杀不适用 |
| D: 定时对账 | 扫描超时 status=1 的 stockLog，回补 Redis | — | — | ✅ |

**方案 C 被秒杀场景否决**——库存扣减必须前置（先扣 Redis 做快速过滤），否则先写 DB 再扣 Redis 在高并发下会超卖。

**方案 B 太脆弱**——只覆盖 `BusinessException`，实际线上异常大多是 `RuntimeException`。

**最终选择：A + D 组合**。

**第一步（A：实时补偿）**——`TransactionSynchronizationManager`：

```java
// 在 decreaseStock 成功后、DB 操作之前注册
TransactionSynchronizationManager.registerSynchronization(
    new TransactionSynchronizationAdapter() {
        @Override
        public void afterCompletion(int status) {
            if (status == TransactionSynchronization.STATUS_ROLLED_BACK) {
                // DB 回滚了 → Redis 回补，重试 3 次
                for (int i = 0; i < 3; i++) {
                    try {
                        itemService.increaseStock(itemId, amount);
                        return;   // 成功
                    } catch (Exception e) {
                        if (i < 2) Thread.sleep(100L * (i + 1));
                        else log.error("Redis回补失败！itemId={}, amount={}", itemId, amount, e);
                    }
                }
            }
        }
    });
```

选择这个方案的原因：
- Spring 原生机制，与 `@Transactional` 天然契合
- `afterCompletion(status)` 自动感知 commit/rollback，覆盖所有异常类型
- 只在 Redis 扣减成功后才注册回调——与 `decreaseStock` 内部（库存不足时）的回补**互斥**，不会重复回补

**第二步（D：最终兜底）**——定时对账任务：

```sql
-- 扫描 status=1 且超过 5 分钟未更新的悬空记录
SELECT stock_log_id, item_id, amount FROM stock_log
WHERE status = 1 AND create_time < NOW() - INTERVAL 5 MINUTE;
```

对每条记录回补 Redis 库存，然后标记 status=3。这覆盖了 JVM 崩溃等极端场景。

**补偿本身也会失败怎么办？**——三层兜底：

```
① 重试（秒级）→ increaseStock 重试 3 次
② 告警（分钟级）→ 3 次都失败打 ERROR 日志，监控告警通知
③ 对账（分钟级）→ 定时任务扫 stock_log，自动修复
```

核心原则：**补偿可以失败，但不能失败得静悄悄。**

**R（效果）**：
- 正常回滚：Redis 库存毫秒级恢复
- 极端崩溃：定时对账分钟级修复
- 不会多回补：两个回补路径互斥，加减一一对应
- 不影响性能：不改变 Redis 先扣的快速过滤路径

**T（取舍）**：为什么没有用 Seata 或 XA 分布式事务？太重了——Seata 需要额外部署 TC Server，XA 性能差。对于秒杀这类高并发场景，**补偿比协调更合适**（BASE 优于 ACID）。

**L（反思）— 五条核心收获**：

1. **`@Transactional` 只保护 DB**——标注了 `@Transactional` 不代表方法里所有操作都受保护。要画图搞清楚每个资源在不在事务边界内。

2. **跨存储系统没有免费的分布式事务**——Redis + MySQL 之间没有 XA 协调。任何跨存储的写操作都必须配套补偿逻辑。

3. **补偿逻辑要写在不漏的地方**。catch 块只抓声明类型的异常，`TransactionSynchronizationManager.afterCompletion` 覆盖所有回滚场景。**写补偿代码时，要问自己"什么情况下这段代码不会执行"。**

4. **补偿本身也会失败**——分布式系统里不存在 100% 成功的补偿。做法不是消灭失败，而是让失败可控：重试 → 告警 → 定时对账兜底。

5. **极端情况用异步任务兜底**——实时补偿再完善，进程崩溃都是盲区，最终一致性需要定时对账保证。

**面试官可能的追问**：
- "为什么不用 Seata/分布式事务？" → 太重了，秒杀场景需要极低延迟，补偿模式更合适
- "会不会回补多了？" → 不会，`decreaseStock` 返回 false 时不注册回调，两条回补路径互斥
- "回补本身失败怎么办？" → 重试 3 次 → 记日志告警 → 定时对账兜底，三层保证

### Q18.5（核心）：JMeter 压测发现 Redis 与 DB 库存不一致——DB 多扣了 4 个

> 这是我在项目中**最有价值的一次排障经历**。不是代码 review 发现的，是 JMeter 500 线程压测后对比数据发现的——Redis 扣了 56，DB 扣了 60。同一个订单扣一次 Redis、扣一次 DB，数字对不上，一定有 bug。

**S（背景）— 测试环境与现象**：

测试条件：
- 2 核 2G 服务器，MySQL + Redis + RocketMQ 全部跑在同一台机器，已连续运行 40+ 小时
- JMeter：500 线程，10 秒 Ramp-Up，1 次循环，RateLimiter(5)
- 测试前：Redis 和 DB 库存都是 331

测试后：
- Redis 库存：331 → 275（扣了 56）
- DB 库存：331 → 271（扣了 60）
- **DB 比 Redis 多扣了 4 个**

**T（问题）— 三步定位根因**：

**第一步：方向判断**。DB 多扣 → 不是 Redis 回滚问题（那种方向上应该是 Redis 多扣），而是 **MQ Consumer 多处理了消息**。

**第二步：代码审查 MqConsumer**。修复前的代码：

```java
// 修复前
consumer.registerMessageListener((msgs, context) -> {
    Message msg = msgs.get(0);              // ⚠️ 问题1：只取第一条，跳过的消息RMQ会重投
    Map<String, Object> map = JSON.parseObject(...);
    // String stockLogId = map.get("stockLogId");  // ⚠️ 问题2：消息体里有 stockLogId，完全没用到
    itemStockDOMapper.decreaseStock(itemId, amount);  // ⚠️ 问题3：零幂等保护，每次重投都再扣一次
    return CONSUME_SUCCESS;
});
```

三个致命问题：
1. `msgs.get(0)` 只取第一条——RocketMQ 一次可能推多条，跳过的消息会重投
2. 消息体里的 `stockLogId`（UUID，全局唯一）明明存在，Consumer 完全忽略
3. 零幂等——RocketMQ 的 at-least-once 语义下，重投是必然的，但 Consumer 每次照单全收

**第三步：环境还原——RocketMQ 重投是怎么触发的**。服务器 2G 内存同时跑 JVM + MySQL + Redis + RocketMQ Broker，Broker 堆外内存不够被 OOM Killer 杀掉：

```
① Broker OOM 崩溃 → 重启
② topic 路由丢失（autoCreateTopicEnable=false）
③ 重建 topic → offset 归零
④ Consumer rebalance → CommitLog 残留消息被重扫入队
⑤ Consumer 零幂等 → 每条重投消息都再扣一次 DB
⑥ 不止一轮——Broker 不稳定反复挂掉重启 → 多轮重投
→ 最终 DB 多扣了 4 个
```

**A（方案）— Redis `setIfAbsent` 幂等锁**：

```java
// 修复后
for (MessageExt msg : msgs) {                              // 逐条处理
    Map<String, Object> map = JSON.parseObject(...);
    String stockLogId = (String) map.get("stockLogId");    // 取 stockLogId

    // 幂等检查：setIfAbsent 是原子操作
    String lockKey = "stock_log_synced_" + stockLogId;
    Boolean firstTime = redisTemplate.opsForValue().setIfAbsent(lockKey, "1");
    if (Boolean.FALSE.equals(firstTime)) {
        continue;   // 已处理过，跳过
    }
    redisTemplate.expire(lockKey, 1, TimeUnit.HOURS);

    itemStockDOMapper.decreaseStock(itemId, amount);
}
```

**为什么用 Redis 而不是查 stock_log 表？** Consumer 已经要写 DB 了，再多一次 `SELECT` 增加 DB 压力。Redis `setIfAbsent` 极快（<1ms），秒杀场景下减少 DB 查询很关键。TTL 设 1 小时远超 RocketMQ 最大重试窗口（约 15 分钟），不会漏判。

**为什么用 `stockLogId`？** 它是 Producer 在本地事务里用 UUID 生成的全局唯一标识——天然适合做去重 key，零额外设计成本。

**R（效果）**：
- 重置库存重跑 JMeter，Redis 和 DB 扣减数一致（相差 0）
- 不再有重复扣减

**L（反思）— 五条核心收获**：

1. **MQ Consumer 必须有幂等**。消息队列承诺 at-least-once，不是 exactly-once。重投在 rebalance、超时、Broker 崩溃恢复等场景下**必然发生**——不是 bug，是分布式消息队列的正常行为。

2. **幂等要利用已有的业务标识**。`stockLogId` 在 Producer 端用 UUID 生成，天然唯一，直接复用。如果消息体里没有唯一 ID，应该在 Producer 端加上。

3. **批量消息要逐条处理**。`msgs.get(0)` 只取第一条就 ACK 全部——被跳过的消息 RocketMQ 会一直重试，既丢数据又浪费资源。

4. **低资源环境下中间件的稳定性是真实问题**。2G 内存同时跑 4 个中间件，Broker 的 mmap 堆外内存不够就 OOM → 崩溃 → 丢 offset → 重投。生产环境 Broker 至少留 2GB+ 堆外。**你没法假设中间件永远稳定——Consumer 要自己保护自己。**

5. **压测后一定要对比多个数据源**。如果我只看了 Redis 或者只看了 DB，永远不会发现差了 4 个。跨存储系统的压测验证必须看**两份数据是否一致**。

**面试官可能的追问**：
- "RocketMQ 不是有事务消息吗？为什么还会重投？" → 事务消息保证 Producer 端的半消息不丢不重，但不保证 Consumer 端不重投。Consumer rebalance、超时、Broker 恢复都可能触发重投——at-least-once 是 MQ 的设计语义，不是 bug
- "为什么不用数据库唯一约束？" → 可以，但要多一张「扣减流水表」，设计成本更高。Redis `setIfAbsent` 用已有的 stockLogId，改动最小
- "TTL 1 小时够吗？万一消息在 1 小时后才重投？" → RocketMQ 最大重试窗口约 15 分钟。如果 1 小时后才重投，说明系统有更严重的问题，不是幂等能解决的了

### 对这个幂等方案的进一步反思：Redis Key 数量膨胀

**S（隐患）**：当前每个成功的订单都会在 Redis 中留下一个 `stock_log_synced_{uuid}` 幂等 Key，TTL 1 小时。在高并发下 Key 数量会爆炸。

**T（定量分析）**：

| 场景 | 订单量 | Redis Key 数 | 内存占用 |
|------|:---:|:---:|:---:|
| 压测（库存 1 万） | 10,000 | 10,000 | ~0.9 MB |
| 压测（库存 5 万） | 50,000 | 50,000 | ~4.5 MB |
| Consumer 满负荷 1 小时 | 180 QPS × 3600s = 648,000 | 648,000 | **~58 MB** |

> 单 Key ≈ 90 bytes（key 字符串 50 bytes + Redis dictEntry 等内部 overhead 40 bytes）。Redis 容器只有 **64MB**——648,000 个 Key 就打满了。

**A（方案）**：三种改进方向：

| 方案 | 做法 | 内存节省 | 代价 |
|------|------|:---:|------|
| A. 缩短 TTL | 改为 15 分钟 | 75% | 一行代码 |
| B. 改用 DB 查 stock_log | `SELECT WHERE stock_log_id=? AND status=2` | 100%（零 Redis 占用） | 每次多一次主键查询（~1ms） |
| C. Redis → DB 降级 | Consumer 先查 Redis，不可用则降级查 DB | — | 代码复杂 |

**当前状态**：TTL 1 小时，库存 < 5 万的压测场景完全安全（< 5 MB）。面试时被问到，能把这个定量分析和三个改进方向讲清楚，比方案本身更有说服力——**展示你对方案局限性的清醒认知**。

**T（取舍）**：为什么没有直接改用方案 B 查 stock_log 表？因为 Consumer 每秒只消费 ~180 条消息，多 180 次主键查询对 MySQL 是九牛一毛。但当前方案也完全够用——**技术选型不追求完美，追求"当前场景下最合适"**。如果库存量级上去或者 Redis 内存吃紧，方案 B 随时可以切。

### Q19：无界队列 OOM 风险

**S（背景）**：队列泄洪用的线程池，最初是 `Executors.newFixedThreadPool(20)`。

**T（问题）**：它的底层是 `new LinkedBlockingQueue()`（无参构造），容量是 `Integer.MAX_VALUE`。秒杀高峰时所有请求都排进队列不拒绝，内存无限堆积，最终 OOM。

**A（方案）**：改成有界队列 + 拒绝策略：

```java
new ThreadPoolExecutor(20, 20, 0L, TimeUnit.MILLISECONDS,
    new LinkedBlockingQueue<>(100),      // ← 有界，最多 100 个排队
    new ThreadPoolExecutor.AbortPolicy()  // ← 满了直接抛异常拒绝
);
```

**L（反思）**：`Executors` 工具类的默认行为不一定是安全的——要读源码，搞清楚底层做了什么。
