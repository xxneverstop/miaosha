# 订单回滚问题修复、第二步的面试价值与本机环境验收评估

本文回答三个问题：当前问题怎样修、哪些改造值得作为面试和简历专题，以及本机运行指南覆盖了 Roadmap 第 0～1 步的哪些要求。依据是当前源码、[Roadmap](../roadmap/roadmap.md)、[本机开发运行指南](../develop/本机开发运行指南-Windows后端与Docker依赖.md)和你提供的故障实验结果。本轮只做分析与文档整理，没有实施下面的修复，也没有重新运行业务测试。

先给结论：**当前受检异常不回滚，核心修复可以是一行事务配置；它本身是常规 bug，但定位过程适合用来解释事务边界。第 2 步更值得形成简历专题的是消费幂等、事务消息的未知状态和回补重试。运行指南已经提供本机开发入口，但还不足以把第 0～1 步整体标成验收完成。**

## 一、当前问题如何修复

### 1. 在订单事务上明确异常回滚规则

当前 [OrderServiceImpl.createOrder()](../../src/main/java/com/imooc/miaoshaproject/service/impl/OrderServiceImpl.java) 使用默认 `@Transactional`。这个方法负责写订单、加销量和更新流水，这些修改应一起成功或一起撤销。

建议只将该方法原有的 `@Transactional` 替换为下面这一行，保留完整的原方法体：

```java
@Transactional(rollbackFor = Exception.class)
```

这句话的意思是：“这个订单方法向外抛出 Exception 或其子类时，数据库事务按回滚处理。”因此它覆盖 `BusinessException`，运行时异常也仍然回滚。Spring 对 Error 的默认回滚规则仍保留。[Spring 5.0.9 注解说明](https://docs.spring.io/spring-framework/docs/5.0.9.RELEASE/javadoc-api/org/springframework/transaction/annotation/Transactional.html#rollbackFor--)

针对当前这个异常，写成 `rollbackFor = BusinessException.class` 也能解决。这里建议使用 `Exception.class`，是因为这次订单方法的业务约定就是异常退出时撤销整笔数据库修改。

修改位置应在真正承载数据库操作的 Service 方法上。单独给 Controller 加注解，覆盖不了已经切到线程池工作线程里的事务。也不需要为了这一个问题，把全项目的 `BusinessException` 改成 `RuntimeException`。

### 2. 修复后，Producer仍然可以catch，但顺序变正确了

你关心的 `MqProducer.catch(BusinessException e)` 可以保留。它仍然能捕获业务异常，只是接到异常之前，Spring已经将订单事务回滚。

```text
订单Service抛出BusinessException
    ↓
Spring根据rollbackFor规则回滚数据库
    ↓
订单不保存、销量不增加、流水状态2的更新被撤销
    ↓
Spring调用afterCompletion(STATUS_ROLLED_BACK)
    ↓
现有回补逻辑尝试把Redis预扣库存加回
    ↓
异常继续抛给Producer
    ↓
Producer把原有流水状态1改成3，返回ROLLBACK_MESSAGE
    ↓
半消息回滚，接口最终返回fail
```

这里的状态1流水是在 `initStockLog()` 的独立事务里先保存的，所以订单事务回滚后它仍然存在。Producer随后将它标记为3，是记录这次处理失败，符合这条明确回滚路径的实际结果。

Redis回补仍依赖现有 `afterCompletion()` 和 `increaseStock()`，前提是Redis操作成功。**加上回滚规则，并没有顺便修好回补局部失败、消息重复消费或进程退出后的恢复。** 这些是第2步的其他任务。

### 3. 用原来的故障点复测，按本轮增量判断

先保留你加入的临时 `BusinessException`，只改事务注解，重启后端，再提交一笔购买1件的订单。不要在这个时候删除异常，否则只能测试正常路径，无法证明失败回滚已修复。

你上一轮结束时的数据是：MySQL库存68、销量145、活动订单数6、Redis库存67。旧实验已经造成差异，修改注解不会自动修复旧数据。**若环境此后没有变化，修复后再做一次失败实验，这四个值应仍然是68、145、6、67。** 重点是本轮失败请求没有再增加订单或改变库存，不是要求Redis自动从67恢复到最初的68。

| 检查项 | 修复前这次故障的变化 | 修复后同一故障应有的变化 |
| --- | --- | --- |
| 接口业务结果 | fail | fail |
| 订单数 | +1 | 0 |
| 销量 | +1 | 0 |
| Redis库存 | -1 | 先预扣、成功回补后净变化0 |
| MySQL库存 | 0 | 0 |
| 本次新增流水最终状态 | 3，但与已提交订单冲突 | 3，与订单事务已回滚一致 |

每轮都重新记录基线和本次 `stockLogId`。不要把旧流水、旧订单算成本轮新增，也不要通过重复发布活动覆盖Redis库存来“做平”实验结果。

这轮通过后，删除临时异常并重启，再补一笔正常成功单。在无其他请求、无旧在途消息干扰且消费正常完成时，应看到订单+1、销量+1、Redis库存-1、MySQL库存-1，本次流水为2。正常成功单仍按增量核对；历史差异要另外核查。

### 4. 运行时异常还要单独测，不能因此宣称第2步全部修完

Roadmap还要求测试 `RuntimeException`。在相同位置暂时换成运行时异常，订单数据库修改本来就应该回滚；在Redis正常时，现有回补应恢复本轮预扣。

但当前Producer只捕获 `BusinessException`。运行时异常会继续到RocketMQ客户端，客户端会保留本地事务结果为 `UNKNOW`，而不是走当前catch把流水改成3。原先状态1的流水可能继续让回查返回未知。这个行为来自项目所用 [RocketMQ 4.3.0 的事务消息实现](https://github.com/apache/rocketmq/blob/rocketmq-all-4.3.0/client/src/main/java/org/apache/rocketmq/client/impl/producer/DefaultMQProducerImpl.java#L1010)，还需要按第2步第4项完善。

所以要分别验收“数据库是否回滚”和“MQ最终状态是否得到正确处理”。不要直接改成 `catch (Exception)` 后一律写状态3、返回MQ回滚：数据库提交结果不明确的异常，可能需要保留未知状态并核查，不能猜测它已经回滚。正常事务代理返回成功时，也无需每单再查一次数据库证明提交。

后续自动测试应通过Spring管理的Service代理调用，并从数据库核对实际结果；只用 `new OrderServiceImpl()` 或把Mapper全部Mock掉，不能证明事务注解真的产生了回滚。测试自身自动回滚，也不能代替核对被测订单事务的提交结果。

## 二、这些问题有没有研究、面试和简历价值

### 1. 先区分三个不同层次的价值

**作为常规bug：** 少写一个回滚规则，是常见事务配置错误。修改本身难度不高，不适合单独写成“攻克分布式事务难题”。

**作为工程学习和面试案例：** 有价值。你已经拿到“接口失败、订单却提交、流水随后改3、Redis少1、MySQL库存不变”的实际证据。能说明白这些数据为什么同时出现，说明你理解了异常传播、Spring事务代理、MQ半消息和库存补偿之间的关系。这比背一句“加rollbackFor”更有内容。

**作为学术研究：** 当前这些任务运用的是成熟工程方法，没有显示新的算法或协议创新。可以开展有价值的工程实验，例如故障注入和修复前后对照；现阶段不应把它包装成学术创新。这里的故障注入，就是在指定步骤人为制造一次失败，观察系统留下了什么数据。

下面的高、中、低，是按本项目能形成的技术追问深度和验证证据判断，不代表某种招聘评分标准，也不代表高价值任务已经完成。

### 2. 第2步七项任务分别怎么看

| Roadmap任务 | 问题本质 | 单独写简历的价值 | 应该怎样呈现 |
| --- | --- | --- | --- |
| 1. 受检异常回滚规则 | 常规事务配置bug | 低；完整定位过程有中等面试价值 | 作为交易可靠性改造中的一个故障案例 |
| 2. 消费去重记录与扣库放入同一DB事务 | 重复消费和中途失败下的原子性 | 高 | 说明唯一键、事务边界和重复投递实验，作为专题主线 |
| 3. 检查SQL影响行数 | 基础业务正确性 | 单独低；与第2项结合后更有价值 | 讲清“没有SQL异常”为什么不等于“库存已扣成功” |
| 4. 区分订单提交、库存同步和UNKNOWN | 多个资源之间的状态与不确定性 | 高 | 讲消息决定丢失、回查依据，以及哪些结果只能待核查 |
| 5. 限定合法库存模式及扣减/回补职责 | 防止配置组合造成重复扣减或错误回补 | 低到中 | 作为可靠性完整性的配套，给出模式矩阵和启动校验 |
| 6. 回补去重、局部失败与响应未知 | 补偿重试也可能破坏库存 | 高 | 用故障实验说明为什么重试不等于安全，以及如何防重复补偿 |
| 7. 验证订单号唯一性、长度和锁等待 | 正确性及并发性能核查 | 取决于实际发现 | 先测；发现真实问题或瓶颈后，再讲修复及对照结果 |

价值排序不等于可跳过任务。Roadmap将这七项都列为必做；简单错误也必须修，否则后续复杂实验的结论不可靠。

### 3. 最值得深入的三组问题

**第一组是第2＋3项：让数据库库存消费在重投和失败时仍然正确。** “幂等”在这里的意思是：同一 `stockLogId` 的消息重复处理，数据库扣减效果仍然只有一次。

当前Consumer先写Redis去重标记，再扣MySQL库存。两个动作分离，写标记后失败可能导致后续重试被跳过；标记过期后又可能重复扣。改造重点是把消费记录和库存扣减放在同一个MySQL事务里，用唯一键裁决同一流水的重复处理，并通过独立Spring Bean使事务代理生效。SQL更新0行必须进入明确失败或待处理路径，不能当成消费成功；暂时错误和永久错误也要分别决定重试或人工处理边界。

有说服力的证据是：同一流水顺序、并发重投100次只扣一次；写去重记录后或扣库后抛异常，两者一起回滚；更新0行不会留下“已成功消费”的记录。承诺范围是数据库扣减效果幂等，不是消息只投递一次，也不是用户重复点下单只生成一单。

**第二组是第4项：面对不确定结果，系统怎样作决定。** 本地订单提交、Broker允许消息投递、Consumer完成库存同步，是三个不同事实。比如数据库已经提交，随后通知Broker的网络请求出了问题，不能因为客户端看到异常，就认定订单失败并立刻加回库存。

这组问题适合研究每个故障窗口：在哪一步退出、丢了哪次响应、数据库事实是什么、回查凭什么决定提交或回滚。值得讲的是有依据地分类，而不是多加几层catch。没有确切结果时应保留待核查证据；流水2也不能直接解释成“异步库存已经同步”。

**第三组是第6项：补偿为什么也需要防重复。** 现在回补先 `INCR` 加库存，再删除售罄标记。如果第一步成功、第二步失败，整体重试会再加一次库存。响应丢失时，也可能是Redis已经执行、客户端却不知道结果。

Lua可以把多个Redis操作放在一次原子执行中，但仅有Lua并不能防止同一补偿执行两次。还需要基于 `stockLogId` 记录同一次回补是否已执行，并将去重、加库存、清除售罄标记一起原子处理。在证据与执行条件都明确时，重复请求同一补偿可以不重复加库存；无法确认的情况仍需留下核查依据。不能因此声称已经实现完整预留机制或预扣后进程退出的自动恢复。

这三组问题都适合用“失败发生在两个动作之间，会留下什么数据”来开展工程实验。实验的价值来自可解释、可复现和修复前后对照，而不是使用了多少中间件。

第5项是配套约束：例如当前 `mysql` 模式已经扣了DB，后续分支再扣就可能重复扣减；回滚时也不该凭空增加没有预扣过的Redis库存。第7项则要坚持先验证：序列SQL已有 `FOR UPDATE`，私有方法的 `REQUIRES_NEW` 不生效，并不能直接推出订单号一定重复，更不需要为了增加亮点就立即换成另一套发号系统。

### 4. 当前能怎么写，完成后再怎么写

你现在已经完成的是故障复现和原因定位，适合在项目记录或面试中表述为：

> 搭建本机秒杀系统运行环境，通过业务异常注入复现下单失败后订单仍提交的问题，对照订单、销量、Redis库存和数据库流水定位事务回滚规则与MQ状态处理的边界。

这句话是对已发生工作的描述；目前还不能把它写成“已修复并验证”。正式简历篇幅有限，这个案例适合作为后续可靠性改造条目中的追问素材。

等第2＋3项实际实现、实验通过后，可以再写：

> 将库存消费记录与数据库扣减纳入同一事务，通过唯一键实现基于库存流水的消费幂等，并以重复投递、中途异常和更新零行实验验证失败处理。

等第6项实现并有记录后，再增加按流水去重回补、原子操作和未知结果核查的内容。不要提前写“无条件最终一致”“消息恰好一次”“HTTP超时重试不重复下单”“预扣后宕机自动恢复”，也不要引用当前版本尚未复现的历史QPS。

## 三、本机运行指南是否达到了Roadmap第0～1步

### 1. 当前判断：本机入口具备，整体验收尚未完成

运行指南解决了“怎样在这台Windows电脑上启动和操作项目”。它包含JDK8、Docker依赖、前端、IDEA和纯命令行两种后端运行方式；追加的第12节也覆盖了Maven与JAR运行、日志、停止和端口排查。

Roadmap第0～1步还要求资源登记、测试数据隔离与重置、持久化和恢复、带超时的就绪检查，以及最小CI的实际证据。因此，“指南内容基本能照着运行”和“第0～1步全部验收完成”，是两个层次。

你已经按指南正常启动，并完成了本轮故障复现，可以继续当前第2步的修复。**但现有对话记录没有一份正常成功订单的完整库存收敛记录，不能拿失败实验替代第1步的正常下单验收。** 如果你此前已保存过正常成功单记录，可以直接作为证据；否则应补一次。CI可以并行补，云端CD可以后置。

本轮没有检查运行中的Docker配置；若你已额外补过Redis/MQ卷或恢复记录，应按实际证据更新判断。当前仓库可见的Java自动测试主要是配置解析测试，不能据此宣称订单事务、消息消费和补偿已通过集成验收。

“隔离”也不要求你现在立即复制第二套完整环境。如果当前容器和数据确实是可重建的专用测试资源，可以先串行使用；重点是明确不会影响其他业务数据，并能把测试恢复到可解释的初始状态。

### 4. 怎样把第0～1步收尾，同时继续第2步

建议先把已有成果保留下来：环境选择、启动入口和本轮故障证据已经有了。下一次先完成当前回滚修复与故障复测，再补一笔正常成功单记录；不要为补CI或云部署停止正在进行的交易修复。

正常单记录至少包含：代码版本与关键配置、本轮购买数量、订单号、流水号、接口业务状态，以及消费收敛前后的Redis库存、MySQL库存、销量和订单购买数量增量。`stock_log=2`只能说明本地订单路径成功，库存是否同步仍要查MySQL事实。

随后补一张不含凭据的资源登记表，并为选定入口加入带超时的就绪检查，明确测试数据的重置和恢复办法。Redis/MQ若需要保留状态，补持久化卷和一次重建恢复实验；最小CI在此期间并行推进，保存JDK8构建、测试与无密钥工件的实际结果。现有`package.bat`会复制.env到部署目录，不能把该目录直接作为公开CI工件。

按Roadmap的原有边界，**最小CI是基础版必做项，但不阻塞开始第2步；云端CD是增强项，可以后置。** 当前应记录为“本机开发路径已具备，第0～1步部分验收与证据待补”，而不是整体勾选完成。
