# Redis 与数据库库存不一致问题排查与修复

> 问题发现于 JMeter 500 线程并发测试，修复于 MqConsumer 幂等改造

---

## 一、怎么发现这个问题的

### 测试环境

| 组件   | 说明                                         |
| ---- | ------------------------------------------ |
| 应用   | Spring Boot 2.0.5，秒杀项目                     |
| 缓存   | Redis（库存 key: `promo_item_stock_{itemId}`） |
| 数据库  | MySQL（库存字段: `item_stock.stock`）            |
| 消息队列 | RocketMQ（topic: `stock_topic`）             |
| 限流   | Guava RateLimiter(5)，每秒放行 5 个请求            |

### 测试步骤

1. 通过浏览器正常下一单，拿到登录 token 和秒杀令牌 promoToken
2. 确认测试前状态：
   - 数据库 `item_stock.stock` = **331**
   - Redis `promo_item_stock_{itemId}` = **331**
3. 配置 JMeter：
   
   ```
   线程数：500
   Ramp-Up：10 秒（10 秒内逐步启动全部线程）
   循环次数：1
   请求：POST /order/createorder，携带 token + promoToken
   ```
4. 运行 JMeter 测试
5. 测试结束后查看：
   - Redis：`GET promo_item_stock_{itemId}` → **275**（扣了 56）
   - 数据库：`SELECT stock FROM item_stock WHERE id = {itemId}` → **271**（扣了 60）

### 差距

|       | 起始  | 结束  | 扣减数 | 差异                 |
| ----- | --- | --- | --- | ------------------ |
| Redis | 331 | 275 | 56  | —                  |
| DB    | 331 | 271 | 60  | **比 Redis 多扣 4 个** |

**数据库比 Redis 多扣了 4 个库存。同一个订单，理论上扣一次 Redis、扣一次 DB，两边数量应该一致。不一致说明有 bug。**

### JMeter 结果观察

- 大量请求返回 `errCode=30003`「活动太火爆」（被 RateLimiter 拦截）
- 少数请求返回「下单成功」
- 部分请求返回「下单失败」（令牌失效、库存不足等原因）

## 二、怎么分析这个问题的

### 第一步：理清库存扣减的链路

一个下单请求的完整路径：

```
OrderController.createorder()
    │
    ├─ RateLimiter.tryAcquire()          ← 限流，不过则返回"太火爆"
    │
    └─ executorService.submit(Callable)
        │
        ├─ itemService.initStockLog()    ← ① DB: 写 stock_log (status=1)
        │
        └─ mqProducer.transactionAsyncReduceStock()
            │
            ├─ 发 MQ 半消息
            │
            ├─ executeLocalTransaction()
            │   └─ orderService.createOrder()
            │       ├─ ② Redis: decreaseStock (INCR -1)    ← 不在 @Transactional 里！
            │       ├─ ③ DB: orderDOMapper.insertSelective  ← 在 @Transactional 里
            │       ├─ ④ DB: increaseSales                 ← 在 @Transactional 里
            │       └─ ⑤ DB: update stock_log (status=2)   ← 在 @Transactional 里
            │       → 成功返回 COMMIT_MESSAGE
            │       → 失败返回 ROLLBACK_MESSAGE
            │
            └─ MQ commit → Consumer 收到
                └─ ⑥ DB: itemStockDOMapper.decreaseStock    ← 数据库库存真正扣减
```

**关键发现**：第②步 Redis 扣减和第③④⑤步 DB 操作不在同一个事务边界内。`@Transactional` 只能回滚 DB 操作，Redis 的 `INCR -1` 一旦执行就无法回滚。

### 第二步：分析"DB 比 Redis 多扣 4 个"的方向

Redis 和 DB 不一致有两个可能方向：

| 方向            | 表现        | 可能原因                 |
| ------------- | --------- | -------------------- |
| Redis > DB 扣减 | Redis 多扣了 | DB 事务回滚但 Redis 没回滚   |
| DB > Redis 扣减 | DB 多扣了    | **MQ Consumer 重复消费** |

我们观察到的是 DB 多扣了（60 > 56），属于第二种情况。

### 第三步：定位 MqConsumer 的代码问题

看 `MqConsumer.java` 的消费逻辑：

```java
// 修复前
consumer.registerMessageListener(new MessageListenerConcurrently() {
    public ConsumeConcurrentlyStatus consumeMessage(List<MessageExt> msgs, ...) {
        Message msg = msgs.get(0);              // ⚠️ 问题1：只取第一条
        Map<String, Object> map = JSON.parseObject(...);
        Integer itemId = (Integer) map.get("itemId");
        Integer amount = (Integer) map.get("amount");
        // String stockLogId = (String) map.get("stockLogId");  // ⚠️ 问题2：明明传了 stockLogId，却完全没用到

        itemStockDOMapper.decreaseStock(itemId, amount);  // ⚠️ 问题3：直接扣，不做任何重复检查
        return ConsumeConcurrentlyStatus.CONSUME_SUCCESS;
    }
});
```

**三个具体问题**：

1. **`msgs.get(0)` 丢消息**：RocketMQ Push Consumer 一次可能推送多条消息，只取第一条就 ACK 全部。被跳过的消息 RocketMQ 认为没消费成功 → 重投 → 但 Consumer 依然没有幂等保护。

2. **消息体里有 `stockLogId` 但没用到**：`MqProducer.transactionAsyncReduceStock` 在消息体里塞了 `stockLogId`（全局唯一的 UUID），设计意图就是给 Consumer 做幂等用的，但 Consumer 完全忽略了这个字段。

3. **零幂等保护**：RocketMQ 在以下场景会重投消息：
   
   - Consumer 挂了重新启动
   - Group rebalance（你测试期间出现的 NameServer 报错就会触发）
   - Consumer 处理超时
   
   每次重投，Consumer 都照单全收再扣一次 `item_stock.stock`，导致数据库库存被重复扣减。

### 第三步附：RocketMQ 重投是怎么触发的——你的服务器场景

上面说了「重投会导致重复扣减」，但重投到底是怎么发生的？你的服务器场景给出了完整的答案。

#### 你的环境

| 项目 | 配置 |
|------|------|
| CPU | 2 核 |
| 内存 | 2 GB |
| 运行时长 | 已持续运行 40+ 小时 |
| 中间件 | MySQL + Redis + RocketMQ NameServer + RocketMQ Broker 全部跑在同一台机器上 |

2GB 内存同时跑 JVM 应用 + MySQL + Redis + RocketMQ，每个进程都要堆内存，操作系统还要留 page cache。任何一个进程内存超标，OOM Killer 就会下手。

#### 触发链路（6 步推演）

```
① RocketMQ Broker  OOM 崩溃
   └─ 2GB 内存被多个中间件瓜分，Broker 堆内存不够，被 Linux OOM Killer 杀掉
      或者 JVM 自身 OutOfMemoryError 崩溃

② topic 数据丢失
   └─ RocketMQ Broker 重启后，之前创建的 stock_topic 丢失
      原因：Broker 默认 autoCreateTopicEnable=false（生产环境标准配置）
      且 topic 的路由信息没有持久化到磁盘（或持久化文件损坏）
      → NameServer 查不到 stock_topic 的路由
      → 你在日志中看到：CODE: 17  DESC: No topic route info in name server for the topic: stock_topic

③ 你手动重建了 topic（或 Broker 自动创建）
   └─ stock_topic 重新出现在 NameServer 的路由表中
      但此时它是一个"全新的 topic"——消费位点（offset）归零

④ Consumer Group rebalance
   └─ Consumer 重新连上 NameServer，发现 stock_topic 存在
      但之前消费的位点已经丢失（旧的 CommitLog 里可能有残留数据，也可能没有）
      → 触发 rebalance：Consumer 重新分配 MessageQueue

⑤ 残留消息被重新拉取
   └─ RocketMQ 的 CommitLog 是持久化到磁盘的
      如果 Broker 崩溃前 CommitLog 里还有未清理的旧消息
      Broker 重启后会扫描 CommitLog 重建 ConsumeQueue
      → 之前已经投递过、Consumer 已处理过的消息，再次出现在队列里
      → Consumer 收到"新"消息（实际是旧的），不加辨别地再扣一次 DB 库存

⑥ 不止一轮，是多轮
   └─ 你测试期间 NameServer 日志持续报错：
      "No topic route info" → "updateTopicRouteInfoFromNameServer Exception"
      这说明 Broker 不稳定，可能在反复挂掉重启
      → 每一次 rebalance 都可能触发一轮重投
      → 4 条重复 = 至少 4 次重投成功穿透了 Consumer
```

#### 一张图概括

```
时间线
───────
t0  RocketMQ 正常运行，topic 存在，offset=56（已处理 56 条）
     │
t1  Broker OOM 崩溃（2GB 内存耗尽）
     │
t2  Broker 重启，topic 数据丢失（NameServer 里查不到路由）
     │
t3  你重建 topic，offset 归零
     │
t4  Consumer rebalance，扫描 CommitLog
     └─ 发现 4 条已提交但 offset 丢失的消息（实际之前已消费过）
     └─ 重新投递给 Consumer
     └─ Consumer 没有任何去重判断 → 又扣了 4 次 DB 库存
     │
t5  结果：Redis 扣 56，DB 扣 60
     那 4 条就是 Broker 崩溃恢复后重投的"幽灵消息"
```

#### 为什么不是每条消息都被重投？

只有部分消息被重投（4 条而不是全部 56 条），说明：

- Broker 崩溃时，大部分消息的 ConsumeQueue 索引已经正常刷盘，只有最后几条的索引没来得及持久化
- 或者 CommitLog 里有几条消息的清理标记丢失了（RocketMQ 不会物理删除消息，只标记已消费）
- Broker 重启扫描 CommitLog 时，这几条被当作"未消费"重新入队

#### 为什么说幂等是唯一的解法？

RocketMQ 的设计哲学是 **at least once**（至少投递一次）——不是 exactly once。以下场景**必然**会重投：

| 场景 | 为什么 |
|------|--------|
| Broker 崩溃重启 | offset 可能丢失，CommitLog 重扫 |
| Consumer rebalance | 队列重新分配，旧 offset 失效 |
| Consumer 处理超时 | RocketMQ 认为消费失败，重新入队 |
| 网络抖动 | Producer 认为失败重发，实际 Broker 已收到 |

**这些不是 bug，是分布式消息队列的正常行为。** 所以不是「怎么防止重投」，而是「假设重投必然发生，Consumer 如何不重复扣库存」。这就是幂等。

### 第四步：确认不是 Redis 回滚的问题

反过来想，有没有可能是 Redis 扣减成功但 DB 事务回滚，而 MQ 消息又被提交了？

`MqProducer.executeLocalTransaction` 的逻辑：

```java
try {
    orderService.createOrder(userId, itemId, promoId, amount, stockLogId);
} catch (BusinessException e) {
    // 订单创建失败 → 回滚 MQ 消息
    stockLogDO.setStatus(3);
    return LocalTransactionState.ROLLBACK_MESSAGE;  // ← MQ 不会投递，Consumer 收不到
}
return LocalTransactionState.COMMIT_MESSAGE;
```

如果 `createOrder` 抛异常 → `ROLLBACK_MESSAGE` → Consumer 不投递 → DB 库存不会扣。所以这个方向不会导致 DB 多扣。

**结论：根因是 Consumer 没有幂等，RocketMQ 重投导致重复扣 DB 库存。**

## 三、怎么解决这个问题的

### 修复方案：Redis 幂等锁

利用消息体里已有的 `stockLogId`（全局唯一），在 Consumer 处理前用 Redis `setIfAbsent` 做去重：

```
消息到达 → setIfAbsent("stock_log_synced_" + stockLogId, "1")
              │
              ├─ true  → 第一次处理，扣 DB 库存
              │
              └─ false → 已处理过，跳过（幂等）
```

### 修复代码

```java
for (MessageExt msg : msgs) {                              // 逐条处理，不丢消息
    Map<String, Object> map = JSON.parseObject(...);
    String stockLogId = (String) map.get("stockLogId");    // 取 stockLogId

    // 幂等检查
    String lockKey = "stock_log_synced_" + stockLogId;
    Boolean firstTime = redisTemplate.opsForValue().setIfAbsent(lockKey, "1");
    if (Boolean.FALSE.equals(firstTime)) {
        continue;   // 已处理，跳过
    }
    redisTemplate.expire(lockKey, 1, TimeUnit.HOURS);      // 1 小时后自动清理

    itemStockDOMapper.decreaseStock(itemId, amount);       // 真正扣减
}
```

### 为什么用 Redis 而不是查 stock_log 表？

| 方案                        | 优点           | 缺点                                     |
| ------------------------- | ------------ | -------------------------------------- |
| 查 `stock_log` 表（status=2） | 不需要额外存储      | 多一次 DB 查询，增加 DB 压力                     |
| Redis `setIfAbsent`       | 极快，不增加 DB 负担 | 极端情况下 key 过期可能漏判（1 小时远超 RocketMQ 重试窗口） |

秒杀场景下 Consumer 已经要写 DB 了，减一次读 DB 是一次，选 Redis。

### 其他改动

| 改动       | 修复前                 | 修复后                                              |
| -------- | ------------------- | ------------------------------------------------ |
| 消息遍历     | `msgs.get(0)` 只取第一条 | `for (MessageExt msg : msgs)` 逐条处理               |
| Redis 注入 | 未注入                 | `@Autowired private RedisTemplate redisTemplate` |

## 六、面试级总结

### 问题是什么？

JMeter 500 线程并发测试秒杀下单后，Redis 库存扣了 56，数据库库存扣了 60——DB 比 Redis 多扣 4 个。同一个订单理论上扣一次 Redis、扣一次 DB，两边数量应该一致。

### 怎么发现的？

压测后对比 Redis `GET promo_item_stock_{id}` 和 MySQL `SELECT stock FROM item_stock`，发现差 4。进一步抓 RocketMQ 日志看到大量 `No topic route info` 报错，推断 MQ 链路出过问题。

### 会导致什么后果？

数据库库存被多扣，秒杀结束时 DB 显示库存比实际少，可能提前停止售卖——明明有货却显示卖完了。

### 怎么定位根因？

三步定位法：

1. **方向判断**：DB 多扣 → 不是 Redis 回滚问题（那种方向上应该是 Redis 多扣），而是 MQ Consumer 多处理了消息
2. **代码审查**：看 `MqConsumer` 发现三个致命问题——`msgs.get(0)` 丢消息、消息体里的 `stockLogId` 完全没用、没有任何重复消费检查
3. **环境还原**：服务器 2C2G，RocketMQ 长期运行 OOM 崩溃 → 重启后 topic 路由丢失 → 重建 topic 后 offset 归零 → Consumer rebalance → CommitLog 残留消息被重扫入队 → Consumer 照单全收再扣一次

### 为什么 RocketMQ 会重投？

RocketMQ 的设计语义是 **at least once**（至少投递一次），以下场景必然触发重投：

| 场景 | 机制 |
|------|------|
| Broker 崩溃重启 | CommitLog 重扫，已消费但索引未持久化的消息重新入队 |
| Consumer rebalance | 队列重新分配，旧 offset 可能失效 |
| Consumer 处理超时 | RocketMQ 认为消费失败，重新投递 |
| 网络抖动 | Producer 超时重发，Broker 可能收到两条 |

**这不是 bug，是分布式消息队列的正常行为**——所以不是「怎么防止重投」，而是「假设重投必然发生，Consumer 怎么不重复处理」。

### 有哪些解决方案？

| 方案 | 思路 | 优缺点 |
|------|------|--------|
| Redis `setIfAbsent` | 用消息体里的 `stockLogId` 做幂等锁 | ✅ 极快，不增加 DB 压力；❌ 极端情况 key 过期可能漏 |
| 查 stock_log 表 | 先查 DB 看这个 stockLogId 是否已处理 | ✅ 不需要额外存储；❌ 多一次 DB 查询 |
| 唯一约束 | 在 item_stock 表建一个「扣减流水」表，stockLogId 做唯一键 | ✅ DB 原生保证；❌ 多一张表 |
| 消费端业务幂等 | 让 `decreaseStock` SQL 带上版本号 | ✅ 不依赖外部存储；❌ 需要改表结构 |

### 最终选择什么？为什么？

**Redis `setIfAbsent`**。原因：

- `stockLogId` 是 Producer 在本地事务里用 UUID 生成的全局唯一 ID，天然适合做去重 key——零额外设计成本
- Redis 操作极快（< 1ms），不增加 DB 压力——秒杀场景下 Consumer 已经要写 DB 了，减少 DB 查询很关键
- key 设 1 小时过期，远超 RocketMQ 的最大重试窗口（默认 15 次回查 × 约 1 分钟间隔 ≈ 15 分钟），不会出现「key 过期了消息才重投」的漏判
- 顺便修了 `msgs.get(0)` → `for` 循环，不再丢批量消息

### 解决效果？

- **正常流程**：每条消息 `setIfAbsent` 成功 → 扣 DB，不会有遗漏
- **重投场景**：`setIfAbsent` 返回 false → 跳过，不会重复扣
- **极端场景**：Broker 再次崩溃 → 恢复后重投，幂等依然有效
- **验证**：重置库存重跑 JMeter，Redis 和 DB 扣减数一致

### 核心教训

1. **MQ Consumer 必须有幂等**。消息队列承诺 at least once，不是 exactly once。事务消息保证了 Producer 端不丢不重，但 Consumer 端重投在 rebalance、超时、Broker 崩溃恢复等场景下**必然发生**——不是 bug，是分布式消息队列的正常行为

2. **幂等要利用已有的业务标识**。`stockLogId` 是 Producer 在本地事务里用 UUID 生成的，天然唯一，直接复用——不需要额外设计，成本极低。如果消息体里没有唯一 ID，**应该在 Producer 端加上**

3. **批量消息要逐条处理**。`msgs.get(0)` 只取第一条就 ACK 全部，被跳过的消息 RocketMQ 会一直重试，既丢数据又浪费资源

4. **低资源环境下中间件的稳定性**。2GB 内存同时跑 JVM + MySQL + Redis + RocketMQ，每个进程的堆内存都很拮据。RocketMQ Broker 依赖 mmap 写 CommitLog，堆外内存不够就会 OOM → 崩溃 → 丢 offset → 重投。生产环境 Broker 至少留 2GB+ 堆外

## 七、当前方案的隐患与改进

### 7.1 隐患：Redis 幂等 Key 数量膨胀

当前方案每处理一条成功的下单消息，就在 Redis 中写入一个 `stock_log_synced_{uuid}` key。**在高并发压测或大库存场景下，Key 数量会剧烈膨胀**。

#### 定量分析

| 场景 | 订单量 | Redis Key 数量 | 单 Key 内存 | 总内存占用 |
|------|:---:|:---:|:---:|:---:|
| 压测（库存 10000） | 10,000 | 10,000 | ~90 bytes | **~0.9 MB** |
| 压测（库存 50000） | 50,000 | 50,000 | ~90 bytes | **~4.5 MB** |
| 大库存（库存 100,000） | 100,000 | 100,000 | ~90 bytes | **~9 MB** |

> 单 Key 内存 = key 字符串 `stock_log_synced_` (18) + UUID (32) ≈ 50 bytes + Redis 内部 overhead（dictEntry、jemalloc 对齐等）≈ 40 bytes = **~90 bytes/key**。

在当前 64MB 的 Redis 容器中，10 万 Key 占 ~9 MB（约 14% 内存）。**可接受，但不容忽视**。如果：
- 同时运行多个秒杀活动（多商品），Key 数量按活动数翻倍
- TTL 设为 1 小时后过期——高峰期 Key 数 = QPS × 3600。Consumer 消费速率约 180 QPS，1 小时内最多 648,000 个 Key（~58 MB），**会打满 64MB Redis**

#### 风险评估

| 条件 | 风险 |
|------|------|
| 单活动、库存 < 10 万 | 低——几 MB，安全 |
| 单活动、Consumer 180 QPS 持续满负荷 | **高**——1 小时可产生 64 万 Key ≈ 58 MB，内存吃紧 |
| 多活动并发 | **高**——Key 按活动数翻倍 |
| TTL 设为 1 小时 | 中等——Key 会在 1 小时后自动清理，但峰值期的内存压力仍在 |

**注意**：压测库存通常不会设到 50 万，更多是 5000-50000。在这个量级下，当前方案是完全安全的。但作为技术方案，应该讨论清楚边界和优化方向。

---

### 7.2 改进方案

#### 方案 A：缩短 TTL（最简单）

将 TTL 从 1 小时缩短到 15 分钟：

```java
redisTemplate.expire(lockKey, 15, TimeUnit.MINUTES);
```

- RocketMQ 最大重试窗口约 15 分钟（15 次回查 × 约 1 分钟间隔）
- 15 分钟 TTL 刚好覆盖窗口，内存占用降为原来的 1/4
- **极限**：Consumer 180 QPS × 900 秒 = 162,000 Key ≈ 14 MB

| 优点 | 缺点 |
|------|------|
| 一行代码，零风险 | 如果 RocketMQ 回查间隔配置异常大（自建集群可能调参），有微小漏判可能 |

#### 方案 B：改用 DB 查 `stock_log` 表做幂等

不用 Redis Key，改为查 `stock_log` 表判断是否已处理：

```java
// 替代 Redis setIfAbsent
StockLogDO stockLogDO = stockLogDOMapper.selectByPrimaryKey(stockLogId);
if (stockLogDO != null && stockLogDO.getStatus() == 2) {
    continue;  // 已处理过，跳过
}
itemStockDOMapper.decreaseStock(itemId, amount);
```

- `stock_log_id` 是主键，查询走聚簇索引，一次查询 ~1ms
- Consumer 消费速率 180 QPS，每秒多 180 次主键查询——**MySQL 完全扛得住**
- 零额外 Redis 内存占用

| 优点 | 缺点 |
|------|------|
| 零 Redis 内存开销 | 每次消费多一次 DB 查询（但主键查询极快） |
| 与现有表复用，不引入新组件 | Consumer 已经有 `stockLogDOMapper` 注入，改动极小 |
| 天然持久化——不存在过期问题 | — |

#### 方案 C：Redis → DB 降级（稳健但复杂）

Consumer 先查 Redis（`setIfAbsent`），如果 Redis 不可用（连接超时、OOM）则降级查 stock_log 表。这覆盖了 Redis 故障场景，但增加了代码复杂度。**当前阶段不需要**。

### 7.3 建议

| 场景 | 推荐方案 |
|------|---------|
| 当前压测（库存 < 5 万） | **保持现状**：Redis 幂等，TTL 1h。内存占用 < 5 MB，安全 |
| 库存放大到 10 万+ | **A+B 组合**：TTL 缩短到 15 分钟 + 保留 Redis。不改代码结构 |
| 追求最简架构 | **方案 B**：改用 stock_log 查 DB。删掉 Redis 幂等 Key，零额外内存 |
| 生产环境 | **方案 B 或 C**。生产环境 Redis 内存宝贵，不应被幂等 Key 占用；DB 主键查询足够快 |

> 当前项目采用的是方案 A（TTL 1 小时），在库存 < 5 万的压测场景下完全安全。面试时如果被问到"Redis Key 会不会太多"，你可以直接给出上述定量分析——**展示你对方案局限性的清醒认知**，比方案本身更重要。

5. **Broker 崩溃后 topic 可能丢失**。`autoCreateTopicEnable=false`（生产标准配置）时，topic 路由信息不一定持久化。Broker 挂了重启后要找运维脚本自动重建 topic、校验 offset——不要手忙脚乱
