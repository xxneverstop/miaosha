## 一、两种压测模式

| | 模式 A：不实现一人一单 | 模式 B：实现一人一单 |
|------|------|------|
| 测试账号 | 1 个 | N 个（如 500 个） |
| Token 准备 | 1 个 token 即可 | 需要提前生成 N 个 token |
| 请求方式 | 同一用户连续发 N 个请求 | N 个用户各发 1 个请求 |
| 测试重点 | Redis Lua 库存扣减、MQ 削峰、数据库写入 | 同上 + 一人一单的 Redis SET NX 拦截能力 |
| 优势 | 极简配置，5 分钟开测 | 模拟真实业务场景 |
| 劣势 | 不符合真实用户行为 | 需要提前准备批量 token |
| 适用阶段 | 开发自测、快速回归 | 交付前验证、面试演示 |

**建议**：先用模式 A 验证核心链路性能和正确性，模式 B 在面试前或演示前跑一次即可。

## 二、模式 A：不实现一人一单 — 单用户多请求

### 2.1 原理

不开启一人一单，同一个 `user_id + token` 可以无限次下单。只用 1 个测试账号循环发请求，把所有并发压力都打在下单核心链路上。

```
1 个用户 × 50000 次请求 → 全部走完 Lua 扣库存 + 事务消息 + MySQL 写入
```

### 2.2 Token 准备

只需一步：

```bash
curl -X POST "http://localhost:8090/user/login" \
  -H "Content-Type: application/x-www-form-urlencoded" \
  -d "telphone=18000805030&password=Qpf0SxOVUjUkWySXOZ16kw=="
```

拿到返回的 `uuidToken`，记下来。JMeter 中所有线程都用这个 token。

### 2.3 JMeter 配置

不需要 CSV 文件，直接把 token 写死在 HTTP 请求参数里：

```
线程组: 1000 线程, Ramp-Up 10 秒, 循环 50 次

HTTP 请求 (POST /order/createorder):
  itemId      = 6
  amount      = 1
  promoId     = 1
  promoToken  = {先调 /order/generatetoken 拿到}
  token       = abc123def456...  ← 固定值，写死
```

### 2.4 注意

因为你用的是同一个 token，不需要调 `/order/generatetoken` 拿多个令牌——秒杀令牌也是**同一个**（只要秒杀令牌还没过期，同一个用户用同一个令牌反复下单是可以的）。

但如果你实现的秒杀令牌是**一次性**的（用一次就删），那每次循环前要先拿新令牌。在你的当前实现中，秒杀令牌是存在 Redis 里的且没有用完就删，所以写死也可以。

### 2.5 正确性验证

```sql
-- 压测结束后验证
-- Redis 剩余库存
redis-cli GET promo_item_stock_6

-- MySQL 订单数
SELECT COUNT(*) FROM order_info WHERE user_id = 23 AND promo_id = 1;

-- 公式: 初始库存 - Redis 剩余 = 总下单数 = MySQL 订单数
-- 如果三数一致 → 无超卖
```

## 三、模式 B：实现一人一单 — 多用户各一单

### 3.1 原理

开启一人一单后，同一个用户只能成功下一次单。需要准备 N 个测试用户，每个用户登录后拿到各自的 token，存到 CSV 文件里，让 JMeter 每个线程用不同的 token。

```
500 个用户 × 各 100 次请求 → 500 次成功（第一次） + 49500 次被 SET NX 拦截
```

这就是为什么**开发阶段不用开启一人一单**——99% 的请求都被第一层拦截了，测不到后面的 Lua 扣库存和 MQ。

### 3.2 批量注册用户

一次性在数据库中插入测试用户：

```sql
-- 批量插入 500 个测试用户到 user_info
-- 手机号: test13800000001 ~ test13800000500
-- 密码统一用: 4QrcOUm6Wau+VuBX8g+IPg== (即 "ic2assCE")

-- 1. 批量插入 user_info
DELIMITER $$
CREATE PROCEDURE batch_insert_users(IN total INT)
BEGIN
    DECLARE i INT DEFAULT 1;
    WHILE i <= total DO
        INSERT INTO user_info (name, gender, age, telphone, register_mode, third_party_id)
        VALUES (CONCAT('testuser', i), 1, 20, CONCAT('138', LPAD(i, 8, '0')), 'byphone', '');
        SET i = i + 1;
    END WHILE;
END$$
DELIMITER ;

CALL batch_insert_users(500);

-- 2. 批量插入 user_password
INSERT INTO user_password (encrpt_password, user_id)
SELECT '4QrcOUm6Wau+VuBX8g+IPg==', id
FROM user_info
WHERE telphone LIKE '138%';
```

### 3.3 批量获取 Token

写一个脚本，循环调用登录接口，把 token 写入 CSV：

用 JMeter 本身来做这个事：

```
线程组: Token 预热（跑一次即可）
  线程数: 1
  Ramp-Up: 1 秒
  循环次数: 500

  CSV Data Set Config: 读取手机号列表 (phones.csv)
  HTTP Request: POST /user/login
    telphone = ${phone}
    password = Qpf0SxOVUjUkWySXOZ16kw==

  后置处理器: Regular Expression Extractor
    提取 uuidToken

  后置处理器: BeanShell PostProcessor
    把 ${uuidToken} 追加写入 tokens.csv
```

或者用命令行脚本更快：

```bash
#!/bin/bash
# generate_tokens.sh

> tokens.csv
for i in $(seq 1 500); do
    phone="138$(printf "%08d" $i)"
    resp=$(curl -s -X POST "http://localhost:8090/user/login" \
      -H "Content-Type: application/x-www-form-urlencoded" \
      -d "telphone=$phone&password=QpfrcOUm6Wau+VuBX8g+IPg==")
    token=$(echo "$resp" | jq -r '.data')
    echo "$token" >> tokens.csv
done
echo "Generated $(wc -l < tokens.csv) tokens"
```

### 3.4 也要批量拿秒杀令牌

每个用户还需要自己的秒杀令牌（一人一单一令牌）：

```bash
#!/bin/bash
# generate_promo_tokens.sh

> promo_tokens.csv
while IFS= read -r token; do
    resp=$(curl -s -X POST "http://localhost:8090/order/generatetoken" \
      -H "Content-Type: application/x-www-form-urlencoded" \
      -d "itemId=6&promoId=1&verifyCode=42&token=$token")
    promo_token=$(echo "$resp" | jq -r '.data')
    echo "$promo_token" >> promo_tokens.csv
done < tokens.csv
echo "Generated $(wc -l < promo_tokens.csv) promo tokens"
```

### 3.5 JMeter 配置

```
线程组: 500 线程, Ramp-Up 10 秒, 循环 100 次

CSV Data Set Config 1: 读取 tokens.csv → 赋值给变量 ${token}
CSV Data Set Config 2: 读取 promo_tokens.csv → 赋值给变量 ${promoToken}
  两个 CSV 行数相同，每行对应同一个用户

HTTP Request (POST /order/createorder):
  itemId      = 6
  amount      = 1
  promoId     = 1
  promoToken  = ${promoToken}
  token       = ${token}
```

### 3.6 验证一人一单是否生效

```sql
-- 每个用户应该最多只有 1 条该 promo 的订单
SELECT user_id, COUNT(*) AS cnt
FROM order_info
WHERE promo_id = 1
GROUP BY user_id
HAVING cnt > 1;

-- 如果返回 0 行 → 一人一单生效
-- 如果返回任何行 → 一人一单被突破了
```

## 四、JMeter 测试计划配置

### 4.1 完整测试计划结构

```
测试计划: miaosha-load-test
│
├── [setUp 线程组] Token 预热 — 只跑一次
│   ├── CSV Data Set Config → phones.csv
│   ├── POST /user/login
│   ├── Regular Expression Extractor → 提取 token
│   └── Simple Data Writer → 写入 tokens.csv
│
├── [线程组 1] 商品详情缓存压测
│   ├── HTTP Request: GET /item/get?id=6
│   └── 参数: token=${token} (可从 CSV 读，也可写死)
│
├── [线程组 2] 下单全链路 ★ 核心
│   ├── CSV Data Set Config → tokens.csv + promo_tokens.csv
│   ├── HTTP Request: POST /order/createorder
│   └── 参数: 见上文
│
├── [线程组 3] 秒杀令牌压测
│   ├── CSV Data Set Config → tokens.csv
│   ├── HTTP Request: POST /order/generatetoken
│   └── 参数: itemId=6, promoId=1, verifyCode=42, token=${token}
│
└── 监听器:
    ├── 聚合报告 (Aggregate Report)
    ├── 汇总图 (Summary Report)
    ├── 响应时间图 (Response Time Graph)
    ├── 用表格查看结果 (View Results in Table)
    └── 后端监听器 (Backend Listener) → 对接 Prometheus/Grafana
```

### 4.2 关键 JMeter 配置项

```properties
# jmeter.properties 调优（大并发时必须改）

# 关闭 GUI 模式下的结果树监听器（太吃内存）
jmeter.save.saveservice.output_format=csv
jmeter.save.saveservice.response_data=false
jmeter.save.saveservice.samplerData=false

# 增加 JMeter 自己的堆内存
# 启动前: export HEAP="-Xms1g -Xmx4g" && jmeter
```

### 4.3 命令行跑压测（推荐，优于 GUI）

```bash
# GUI 只用来编辑测试计划，真正压测时用命令行
jmeter -n -t miaosha-load-test.jmx -l result.jtl -e -o ./report/

# 参数说明:
# -n  非 GUI 模式（省资源，压测必须用这个）
# -t  测试计划 .jmx 文件
# -l  输出原始结果 .jtl 文件
# -e  压测结束后自动生成 HTML 报告
# -o  报告输出目录（必须为空或不存在）
```

## 五、可视化监控配套：Grafana + Prometheus

JMeter 告诉你"请求侧"的数据（QPS、RT、错误率），但看不到"服务端"发生了什么（Redis CPU 打满了吗？数据库连接池用完了吗？JVM GC 频繁吗？）。Grafana + Prometheus 补全这一半。

### 5.1 架构

```
Spring Boot 应用 ──暴露 /actuator/prometheus──▶ Prometheus ──▶ Grafana
        │                                            │
Redis ──┼── Redis Exporter ──────────────────────────┘
        │
MySQL ──┼── MySQL Exporter ──────────────────────────┘
        │
JMeter ─┼── Backend Listener ────────────────────────┘
```

### 5.2 Spring Boot 暴露指标

**pom.xml**：

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-actuator</artifactId>
</dependency>
<dependency>
    <groupId>io.micrometer</groupId>
    <artifactId>micrometer-registry-prometheus</artifactId>
</dependency>
```

**application.yml**：

```yaml
management:
  endpoints:
    web:
      exposure:
        include: health,info,prometheus
  metrics:
    export:
      prometheus:
        enabled: true
```

启动后访问 `http://localhost:8090/actuator/prometheus` 就能看到 JVM 内存、GC 次数、Tomcat 线程数、HTTP 请求数等指标。

### 5.3 Docker Compose 一键启动监控栈

在 `docker-compose.yml` 中加入（或在 `scripts/` 目录下新建 `docker-compose-monitoring.yml`）：

```yaml
version: '3.8'
services:
  prometheus:
    image: prom/prometheus:latest
    container_name: prometheus
    ports:
      - "9090:9090"
    volumes:
      - ./prometheus.yml:/etc/prometheus/prometheus.yml
      - prometheus_data:/prometheus

  grafana:
    image: grafana/grafana:latest
    container_name: grafana
    ports:
      - "3000:3000"
    environment:
      - GF_SECURITY_ADMIN_PASSWORD=admin
    volumes:
      - grafana_data:/var/lib/grafana

  redis-exporter:
    image: oliver006/redis_exporter:latest
    container_name: redis-exporter
    ports:
      - "9121:9121"
    environment:
      - REDIS_ADDR=host.docker.internal:6379

  mysql-exporter:
    image: prom/mysqld-exporter:latest
    container_name: mysql-exporter
    ports:
      - "9104:9104"
    environment:
      - DATA_SOURCE_NAME=root:123123@(host.docker.internal:13306)/

volumes:
  prometheus_data:
  grafana_data:
```

**prometheus.yml**（和 docker-compose 放在同一目录）：

```yaml
global:
  scrape_interval: 5s

scrape_configs:
  - job_name: 'spring-boot'
    metrics_path: '/actuator/prometheus'
    static_configs:
      - targets: ['host.docker.internal:8090']

  - job_name: 'redis'
    static_configs:
      - targets: ['redis-exporter:9121']

  - job_name: 'mysql'
    static_configs:
      - targets: ['mysql-exporter:9104']
```

启动：

```bash
docker-compose -f docker-compose-monitoring.yml up -d
# Grafana: http://localhost:3000 (admin/admin)
# Prometheus: http://localhost:9090
```

### 5.4 Grafana 大屏配置

Grafana 启动后，导入社区做好的仪表板（不用自己一个个配）：

| 仪表板 | Grafana ID | 用途 |
|--------|-----------|------|
| Spring Boot 2.x Statistics | 10254 | JVM 内存、GC、HTTP 请求、Tomcat 线程 |
| Redis Dashboard | 12776 | Redis QPS、内存、连接数、命中率 |
| MySQL Overview | 7362 | MySQL QPS、连接数、慢查询、InnoDB 行锁 |
| JMeter Dashboard | 4026 | JMeter 发过来的实时 TPS 和 RT |

导入方式：Grafana → "+" → Import → 输入仪表板 ID → Load → 选择 Prometheus 数据源 → Import。

### 5.5 JMeter 对接 Prometheus

在 JMeter 测试计划中加入 **Backend Listener**：

```
Backend Listener 实现: org.apache.jmeter.visualizers.backend.graphite.GraphiteBackendListenerClient
  graphiteHost: localhost
  graphitePort: 2003   ← Prometheus 不直接收 Graphite 协议，需要中间层

或者用 JMeter Prometheus Plugin：
Backend Listener 实现: org.apache.jmeter.visualizers.backend.prometheus.PrometheusBackendListenerClient
  prometheus.port: 9270
```

实际上，最简单的方式是用 **InfluxDB + Grafana** 替代 Prometheus 接收 JMeter 数据：

```
JMeter Backend Listener
  → InfluxDB (时序数据库)
  → Grafana 导入 JMeter Dashboard (ID: 4026)
  → 实时看到 TPS 曲线、RT 分布
```

但这个链路需要额外启动 InfluxDB，只为了压测看实时数据有点重。**入门阶段建议直接用 JMeter 自带的 HTML 报告就够了，Grafana 实时大屏是锦上添花。**

## 六、其他可观测工具

除了 JMeter + Grafana/Prometheus 组合，还有以下工具可以辅助观察：

### 6.1 压测期间必看的几个实时窗口

不需要额外安装，压测时同时开着：

| 窗口 | 命令 / 地址 | 看什么 |
|------|-----------|--------|
| Redis 实时 QPS | `redis-cli --stat` | 每秒处理多少命令，CPU 有没有打满 |
| Redis 库存实时值 | `watch -n 1 'redis-cli GET promo_item_stock_6'` | 库存以什么速度在减少 |
| MySQL 连接数 | `watch -n 1 'mysql -e "SHOW PROCESSLIST"'` | 连接数有没有打满 |
| 应用日志 | `tail -f logs/app.log` | 有没有异常、RejectedExecutionException、库存回补日志 |
| RocketMQ Console | `http://localhost:8080`（RocketMQ 自带） | 消息堆积、消费延迟 |

### 6.2 Arthas — 在线诊断

阿里开源的 Java 诊断工具，压测时可以 attach 到应用进程，实时看：

```bash
# 下载启动
curl -O https://arthas.aliyun.com/arthas-boot.jar
java -jar arthas-boot.jar

# 选择你的应用进程后：

# 看哪个方法最耗时
trace com.imooc.miaoshaproject.service.impl.ItemServiceImpl decreaseStock

# 看 Redis 调用耗时分布
monitor -c 5 com.imooc.miaoshaproject.service.impl.ItemServiceImpl decreaseStock

# 看当前所有线程在干嘛（找瓶颈）
thread -n 5
```

Arthas 不需要改任何代码，压测时发现问题可以直接定位到具体方法和行号。

### 6.3 Redis Slow Log

看 Lua 脚本有没有慢查询：

```bash
redis-cli SLOWLOG GET 10
# 如果有超过 10ms 的命令会显示出来
```

### 6.4 MySQL 慢查询

```sql
-- 临时打开慢查询日志（压测期间）
SET GLOBAL slow_query_log = 'ON';
SET GLOBAL long_query_time = 0.1;  -- 超过 100ms 就记录

-- 压测后查看
SELECT * FROM mysql.slow_log ORDER BY query_time DESC LIMIT 10;
```

## 七、压测 Checklist

压测前逐项确认：

- [ ] Redis 正常运行，库存已发布（`publishPromo`）
- [ ] MySQL 正常运行，商品和库存数据正确
- [ ] RocketMQ NameServer + Broker 正常运行
- [ ] 应用以非 Debug 模式启动（JVM 参数调好）
- [ ] 关闭不必要的日志（Spring 日志级别设为 WARN）
- [ ] 数据库连接池大小确认（默认 20，压大并发需调大）
- [ ] JMeter 用命令行模式运行（非 GUI）
- [ ] `result.jtl` 和报告目录已确认
- [ ] 压测结束后第一时间验证超卖

压测中观察：

- [ ] Redis CPU 使用率（`redis-cli INFO CPU`）
- [ ] 应用日志异常数（`grep ERROR`）
- [ ] JMeter 错误率（聚合报告 Error%）
- [ ] MQ 消息堆积（RocketMQ Console）

压测后必做：

- [ ] 超卖验证（Redis 库存 + MySQL 订单数 对比）
- [ ] stock_log 是否有 status=1 的悬空记录
- [ ] 售罄标记是否正确触发
- [ ] 记录本轮 QPS、P99 RT、错误率 → 填入压测报告

## 八、基于课程原版章节代码的压测策略

### 9.1 你有什么版本可用

课程原始项目的章节结构：

```
dianshangmiaosha-master/dianshangmiaosha/
├── 第二章.秒杀回顾/miaoshaStable/        ← V0: 基准版本
├── 第四章.分布式扩展/miaoshaStable/        ← V1: Token+Redis Session
├── 第五六章.查询优化/miaoshaStable/        ← V2: 多级缓存
├── 第七八章.交易优化/miaoshaStable/        ← V3: Redis库存 + MQ事务消息
├── 第九章.流量削峰技术/miaoshaStable/      ← V4: 秒杀令牌 + 限流 + 线程池泄洪
└── 第十章.防刷限流技术/miaoshaStable/      ← V5: 验证码 + 增强限流
```

每个版本的差异性汇总：

| 版本 | 库存扣减 | 缓存 | 登录态 | MQ | 秒杀令牌 | 验证码 | 限流 | 线程池 |
|------|---------|------|--------|-----|---------|--------|------|--------|
| V0 第二章 | MySQL | 无 | Session | 无 | 无 | 无 | 无 | 无 |
| V1 第四章 | MySQL | 无 | Token+Redis | 无 | 无 | 无 | 无 | 无 |
| V2 第五六章 | MySQL | 多级 | Token+Redis | 无 | 无 | 无 | 无 | 无 |
| V3 第七八章 | Redis INCR | 多级 | Token+Redis | 有 | 无 | 无 | 无 | 无 |
| V4 第九章 | Redis INCR | 多级 | Token+Redis | 有 | 有 | 无 | RateLimiter 300 | 20线程+100队列 |
| V5 第十章 | Redis INCR | 多级 | Token+Redis | 有 | 有 | 有 | 增强 | 同上 |

### 9.2 建议压测哪几个版本 — 只测四个关键对比

不需要每个版本都测。只测这四个版本的**对比**就能覆盖简历上所有亮点：

| 对比编号 | 升级路径 | 测什么 | 简历价值 |
|---------|---------|--------|---------|
| **对比 A** | V2 → V3 | MySQL库存 vs Redis库存 + MQ | ⭐⭐⭐⭐⭐ 最大数字 |
| **对比 B** | V0 → V2 | 无缓存 vs 多级缓存 | ⭐⭐⭐⭐ |
| **对比 C** | V3 → V4 | 无令牌/无限流 vs 秒杀令牌+泄洪 | ⭐⭐⭐ |
| **对比 D** | V4 → V5 | 无限流 vs 增强限流+验证码入口 | ⭐⭐ |

> **对比 A 是最核心的，一定要测。** 这是你简历上 TPS 500→50000+ 的来源。B、C、D 按时间选做。

### 9.4 HTML 页面问题如何处理

课程章节中，htmlStable 的 HTML 文件**不需要和 miaoshaStable 版本严格匹配**。压测走的是 HTTP 接口，不是浏览器页面：

```
JMeter → HTTP POST /order/createorder?token=xxx&itemId=6&amount=1&promoId=1
       → 后端 Controller 处理
       → 返回 JSON
```

JMeter 不经过 HTML 页面。HTML 只影响手工从浏览器测试的体验，不影响压测。

**你只需要保证后端接口的 URL 路径、参数名前后一致即可。** 各版本的 `/order/createorder` 接口路径和参数名基本相同，跨版本兼容，JMeter 测试计划可以复用。

### 9.5 验证码怎么绕过 — 压测的关键技巧

验证码（V5 第十章）把 JMeter 自动测试挡住了，因为验证码是图片，需要人工识别。

**方案：在 JMeter 测试计划中模拟验证码校验**

第十章验证码的实现逻辑是：

```
1. 调 /order/generateverifycode → 后端生成答案，存入 Redis: verify_code_{userId}
2. 用户看图片输入答案
3. 调 /order/generatetoken → 传 verifyCode 参数 → 后端从 Redis 取答案比对
```

**绕过方法**：JMeter 中直接调 Redis 写入一个已知答案，然后传这个已知答案：

```
JMeter 线程组中的步骤：

第1步：BeanShell PreProcessor
  → 用 Jedis 连 Redis 直接 SET verify_code_{userId} "42"
  （或者用 Redis 的 EVAL 命令，或者一个简单的 HTTP 请求到自定义接口）

第2步：HTTP Request: POST /order/generatetoken
  参数: itemId=6, promoId=1, verifyCode=42, token=${token}
```

甚至更简单——**在应用中临时加一个"压测模式"开关**：

```java
// application.yml
miaosha:
  test-mode: true   # true=跳过验证码校验
```

```java
// OrderController.generatetoken
if (!testMode) {
    // 正式验证码逻辑
    String redisVerifyCode = redisTemplate.opsForValue().get("verify_code_" + userModel.getId());
    if (!redisVerifyCode.equalsIgnoreCase(verifyCode)) {
        throw new BusinessException(...);
    }
}
// testMode=true 直接跳过验证码校验
```

或者更直接一点——**只测 V3/V4（没验证码的版本）**。验证码主要是前端交互的优化，对后端性能的影响极小（多了一次 Redis GET），**压测对比可以不包含验证码**。面试时讲方案就行。

### 9.1 要测哪些对比？按重要程度排序

你的秒杀系统一路从"原始版本"演进到"优化版本"，中间经历了多层改造。简历上最有说服力的就是这些"改前 vs 改后"的数据对比：

| # | 对比项 | 改前 | 改后 | 简历价值 | 切换难度 |
|---|--------|------|------|---------|---------|
| 1 | 库存扣减方式 | MySQL UPDATE 行锁 | Redis Lua 原子脚本 | ⭐⭐⭐⭐⭐ | 中 |
| 2 | 数据库同步方式 | 事务内同步写 MySQL | MQ 异步削峰 | ⭐⭐⭐⭐⭐ | 高 |
| 3 | 商品查询缓存 | 每次都查 MySQL | Caffeine → Redis → MySQL | ⭐⭐⭐⭐ | 低 |
| 4 | 售罄后请求处理 | 走完整链路才返回失败 | 标记拦截 1ms 返回 | ⭐⭐⭐ | 低 |
| 5 | Redis INCR → Lua | INCR + 分离 SET | Lua 原子脚本 | ⭐⭐⭐ | 低 |
| 6 | 秒杀大闸 | 无 | 令牌限量发放 | ⭐⭐⭐ | 低 |

| 8 | 用户登录态 | Tomcat Session | Token + Redis | ⭐⭐ | 中 |

### 9.2 两种切换方式

不是所有对比都需要改代码然后重新编译。分两种情况：

| 方式 | 适用场景 | 怎么做 | 优缺点 |
|------|---------|--------|--------|
| **配置开关** | 同一段逻辑的不同实现，代码改动范围小 | `application.yml` 加开关 + 代码里 `if/else` 分支 | 一份代码，改配置重启即可，不混 git |
| **Git 分支/标签** | 架构级改动，涉及多个文件和多层逻辑 | `git tag` 标记旧版本 → `git checkout` 切换 | 干净，但需要维护两个版本 |

**推荐策略**：能用配置开关的优先用配置开关，架构级改动（如 MQ 的引入）用 Git 标签。

### 9.3 对比 1：MySQL 行锁 vs Redis Lua — 用配置开关

这是最核心的对比，简历上最大的数字（TPS 500 → 50000+）就来自这里。

**配置开关设计**：

`application.yml` 新增：

```yaml
miaosha:
  stock:
    # 扣库存模式: mysql | redis | lua
    mode: lua
```

**代码改造**（`ItemServiceImpl.decreaseStock`）：

```java
@Value("${miaosha.stock.mode:lua}")
private String stockMode;

@Override
@Transactional
public boolean decreaseStock(Integer itemId, Integer amount) throws BusinessException {
    switch (stockMode) {
        case "mysql":
            // === 改前：MySQL 行锁扣库存 ===
            int affectedRow = itemStockDOMapper.decreaseStock(itemId, amount);
            return affectedRow > 0;

        case "redis":
            // === 中间版本：Redis INCR 扣库存 ===
            long result = redisTemplate.opsForValue()
                    .increment("promo_item_stock_" + itemId, amount.intValue() * -1);
            if (result >= 0) {
                if (result == 0) {
                    redisTemplate.opsForValue().set("promo_item_stock_invalid_" + itemId, "true");
                }
                return true;
            } else {
                increaseStock(itemId, amount);
                return false;
            }

        case "lua":
            // === 最终版：Redis Lua 原子扣库存 ===
            // （你当前的 Lua 脚本逻辑）
            List<String> keys = Arrays.asList(
                "promo_item_stock_" + itemId,
                "promo_item_stock_invalid_" + itemId
            );
            Long luaResult = (Long) redisTemplate.execute(decreaseStockScript, keys, amount);
            if (luaResult == -1) throw new BusinessException(EmBusinessError.UNKNOWN_ERROR, "库存未初始化");
            if (luaResult == -2) return false;
            return true;

        default:
            throw new BusinessException(EmBusinessError.UNKNOWN_ERROR, "未知的库存扣减模式");
    }
}
```

**注意**：`mysql` 模式下不需要 `publishPromo`（没有 Redis 库存同步这一步），且不需要 MQ 异步同步（MySQL 已经同步扣了）。所以 `mysql` 模式的测试实际上需要一个更原始的代码版本——这就是为什么"对比 1"和"对比 2"通常一起测。

**压测方法**：

```bash
# 第 1 轮：MySQL 模式
# 1. 改配置 miaosha.stock.mode=mysql
# 2. 重启应用（publishPromo 这一步在 mysql 模式下不需要）
# 3. JMeter 跑 500 线程 × 20 循环

# 第 2 轮：Lua 模式
# 1. 改配置 miaosha.stock.mode=lua
# 2. 重启应用，调 /item/publishpromo?id=1
# 3. 同样的 JMeter 参数
```

**预期差异**：

| 指标 | MySQL 模式 | Lua 模式 |
|------|-----------|---------|
| 库存扣减 TPS | ~500-1000 | ~50000+ |
| 平均 RT | ~50-100ms | ~5-10ms |
| MySQL 行锁等待 | 大量 | 无 |
| 超卖 | 无 | 无 |

### 9.4 对比 2：同步写 MySQL vs MQ 异步削峰 — 用 Git 标签

这是第二大核心对比，证明 MQ 引入的价值。

**问题：为什么不能简单用配置开关？**

MQ 引入了大量新代码：
- `MqProducer.java`（事务消息生产者）
- `MqConsumer.java`（消息消费者）
- `OrderController.createOrder` 的整个流程改造（从直接调 `orderService.createOrder` 变成 `mqProducer.transactionAsyncReduceStock`）
- `OrderServiceImpl.createOrder` 的方法签名变了（加了 `stockLogId` 参数）
- `stock_log` 表的引入

这些改动跨越 Controller → Service → 新建类，不是改一个 `if/else` 能覆盖的。

**方案：用 Git 标签标记里程碑版本**


**压测方法**：

**预期差异**：

### 9.5 对比 3：无缓存 → Redis → 多级缓存 — 用配置开关

这个对比只需要测 `/item/get` 接口，不涉及下单链路。

`application.yml` 新增：

```yaml
miaosha:
  stock:
    mode: lua
  cache:
    # 缓存模式: none | redis-only | multi-level
    mode: multi-level
```

在 `ItemController.getItem` 中加分支：

```java
@Value("${miaosha.cache.mode:multi-level}")
private String cacheMode;

public CommonReturnType getItem(@RequestParam("id") Integer id) {
    ItemModel itemModel;

    switch (cacheMode) {
        case "none":
            // 无缓存：直接查 MySQL
            itemModel = itemService.getItemById(id);
            break;

        case "redis-only":
            // 仅 Redis 缓存
            itemModel = (ItemModel) redisTemplate.opsForValue().get("item_" + id);
            if (itemModel == null) {
                itemModel = itemService.getItemById(id);
                redisTemplate.opsForValue().set("item_" + id, itemModel, 10, TimeUnit.MINUTES);
            }
            break;

        case "multi-level":
            // 多级缓存（当前逻辑）
            itemModel = (ItemModel) cacheService.getFromCommonCache("item_" + id);
            if (itemModel == null) {
                itemModel = (ItemModel) redisTemplate.opsForValue().get("item_" + id);
                if (itemModel == null) {
                    itemModel = itemService.getItemById(id);
                    redisTemplate.opsForValue().set("item_" + id, itemModel, 10, TimeUnit.MINUTES);
                }
                cacheService.setCommonCache("item_" + id, itemModel);
            }
            break;
    }
    // ...
}
```

**压测三轮**：

```bash
# none → redis-only → multi-level
# 每轮改配置重启，跑 500 线程循环 /item/get
```

**预期差异**：

| 指标 | none（查库） | redis-only | multi-level |
|------|------------|-----------|-------------|
| 平均 RT | ~50ms | ~2ms | ~0.5ms |
| MySQL 读 QPS | 高 | 极低 | 极低 |
| Redis QPS | 0 | 高 | 低（70% 被本地缓存拦截） |

### 9.7 对比 5：Redis INCR → Lua 脚本 — 用配置开关

这个在前面的 `miaosha.stock.mode` 中已经有 `redis` 和 `lua` 两个选项了：

```bash
# mode=redis  → INCR + 分离 SET
# mode=lua    → Lua 原子脚本
```

**预期差异**：QPS 差异不大（都是单命令/Lua，延迟接近），主要验证的是**并发下售罄标记无竞态**：

- `redis` 模式：高并发库存归零时，可能出现 INCR + SET 窗口导致售罄标记漏打或重复打
- `lua` 模式：整段原子，售罄标记精确触发

验证方法：跑完压测后，对比两个模式下 `stock_log` 有没有异常状态，Redis 库存+售罄标记的状态是否与预期一致。

```yaml
  stock-mode: lua

  cache-mode: multi-level
```

|-----------|-----------|-----------|--------------|---------------|------|
| MySQL vs Lua | mysql → lua | multi-level | true | true(仅lua用) | 核心对比 |

| 大闸开闭 | lua | multi-level | true | true | 令牌量=库存×5 vs 不限量 |

### 9.9 MQ 对比的特殊处理

MQ 的对比（事务内同步 vs 异步）涉及架构改动，不能纯靠配置开关。给你一个**折中方案**：在 `application.yml` 中加 `mq-async-sync`，在 `OrderServiceImpl.createOrder` 中分两条路径：

```java
@Value("${miaosha.mq-async-sync:true}")
private boolean mqAsyncSync;

// 在 createOrder 中：
if (mqAsyncSync) {
    // 当前逻辑：Redis 扣库存后，发 MQ 异步同步 MySQL
    boolean mqResult = mqProducer.asyncReduceStock(itemId, amount);
} else {
    // 对比逻辑：Redis 扣库存后，同步 UPDATE item_stock（不经过 MQ）
    itemStockDOMapper.decreaseStock(itemId, amount);
}
```

> **注意**：`mq-async-sync=false` 时，`asyncDecreaseStock` 改为在事务内同步调 `itemStockDOMapper.decreaseStock`。不需要启动 RocketMQ，也不需要 `MqConsumer`。但仍然需要有 Redis 库存（因为 Redis 扣库存是另一个维度）。

这样 MQ 的对比就可以用配置开关完成了——不用切分支。

### 9.11 实操建议

1. **不要同时测所有对比**。按优先级来：先测对比 1（MySQL vs Lua），这是简历上最大的数字。然后测对比 2（同步 vs MQ），再测对比 3（缓存），最后测 4、5、6。

2. **每一轮只改一个变量**。比如测"mysql vs lua"时，保持其他配置一致（cache 都用 multi-level，sold-out-flag 都开）。

3. **git tag 标记每个测试版本**：`git tag test-mysql-baseline` → `git tag test-redis-incr` → `git tag test-lua-final`，方便回溯。

4. **MQ 比较用配置开关的折中方案即可**（8.9 节），不需要真的切回"完全没有 Redis 也没有 MQ"的原始版本测——那个版本太老了，而且"同步 MySQL"的路径在配置开关里就能模拟。

5. **结果截图**：JMeter 聚合报告、Grafana 仪表板、Redis `--stat` 输出、MySQL `SHOW PROCESSLIST` 截图，贴到压测报告里，面试时有图有真相。

### 9.1 对比一：MySQL 行锁 vs Redis INCR vs Redis Lua

**目的**：验证库存扣减方案的演进效果，获得简历核心数据。

### 9.6 对比六：事务内同步写 MySQL vs MQ 异步
