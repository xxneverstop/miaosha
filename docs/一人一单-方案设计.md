# 一人一单 — 方案设计（STAR-L 框架）

---

## S (Situation)：背景

### 项目状态

这是一个基于 Spring Boot + MyBatis + Redis + RocketMQ 的高并发秒杀系统。当前已实现：多级缓存商品查询、Redis Lua 脚本原子扣库存、RocketMQ 事务消息保证最终一致性、秒杀令牌+大闸流量管控、队列泄洪削峰、验证码+限流防刷。

### 当前订单表结构

```sql
CREATE TABLE order_info (
  id        VARCHAR(32) NOT NULL PRIMARY KEY,
  user_id   INT(11)     NOT NULL DEFAULT 0,
  item_id   INT(11)     NOT NULL DEFAULT 0,
  promo_id  INT(11)     NOT NULL DEFAULT 0,
  item_price   DOUBLE   NOT NULL DEFAULT 0,
  amount       INT(11)  NOT NULL DEFAULT 0,
  order_price  DOUBLE   NOT NULL DEFAULT 0
) ENGINE=InnoDB DEFAULT CHARSET=utf8;
```

注意：`(user_id, promo_id)` 上**没有唯一约束**。

### 现有数据暴露的问题

```sql
SELECT user_id, promo_id, COUNT(*) FROM order_info GROUP BY user_id, promo_id;

-- user_id=23, promo_id=1 → 2 条记录  ← 同一用户在同一秒杀活动中下了 2 单
-- user_id=23, promo_id=0 → 2 条记录
```

用户 23 已经对 `promo_id=1` 买了 2 次。如果不加限制，刷单成本为零 — 一个账号可以买空所有库存。

---

## T (Task)：问题

### 核心问题

实现 **"一人一单"**：同一用户在同一个秒杀活动中只能成功下一单。

### 约束与挑战

| # | 挑战 | 为什么难 |
|---|------|---------|
| 1 | **并发重复请求** | 用户同时打开两个页面、或者快速双击提交按钮，两个请求几乎同时到达服务器 |
| 2 | **不能误杀重试** | 用户第一次下单失败（库存不足、网络超时），应该允许再次尝试 |
| 3 | **JVM 崩溃残留** | Redis 标记写入后如果 JVM 崩溃，标记永远留在 Redis，用户再也无法下单 |
| 4 | **不能浪费下游资源** | 检查要尽可能前置——不能在 Redis 已扣库存、MQ 已发消息之后才发现是重复订单 |
| 5 | **最终兜底** | 任何 Redis 层面的漏洞，数据库层面必须能兜住，不能出现两条重复记录 |

### 决策分析：为什么不在纯数据库层面解决？

最直接的想法是给 `(user_id, promo_id)` 加唯一索引：

```sql
ALTER TABLE order_info ADD UNIQUE INDEX idx_user_promo (user_id, promo_id);
```

但这发生在 INSERT 那一刻——此时 Redis 库存已经扣了、MQ 半消息已经发了。如果唯一索引冲突导致事务回滚，这些昂贵操作白白浪费了。

**结论：Redis 做快速拦截（99.9% 的场景），MySQL 做最后兜底（极端场景）。**

## A (Action)：方案

### 架构概览：三层防护

```
用户请求 createOrder
    │
    ▼
┌──────────────────────────────────────────────┐
│ 第一层：Redis SET NX                          │
│ 位置：OrderController.createOrder             │
│ 时机：秒杀令牌校验通过后，售罄检查之前            │
│ 作用：拦截 99.9% 的重复请求，耗时 ~1ms          │
│ 失败：直接拒绝"已参与过"或"订单处理中"            │
└──────────────────────────────────────────────┘
    │ 通过
    ▼
┌──────────────────────────────────────────────┐
│ 第二层：事务回滚时清除标记                       │
│ 位置：OrderServiceImpl.createOrder             │
│ 时机：TransactionSynchronization 回调          │
│ 作用：下单失败时删除 Redis 标记，允许用户重试      │
└──────────────────────────────────────────────┘
    │ 通过
    ▼
┌──────────────────────────────────────────────┐
│ 第三层：MySQL 唯一索引                         │
│ 位置：order_info 表                           │
│ 时机：INSERT 订单时                            │
│ 作用：极端情况下兜底，发现重复则抛异常回滚事务      │
└──────────────────────────────────────────────┘
```

### 第一层：Redis SET NX 快速拦截

**Redis Key 设计**：

```
Key:   order_user_promo_{promoId}_{userId}
Value: "processing"  → 订单正在处理中
       "1"           → 已成功下单
TTL:   1 小时（覆盖秒杀活动的有效窗口）
```

**为什么用 `SET NX` 而不是 `GET + 判断 + SET`？**

```
同一用户的两个并发请求：

❌ GET + IF + SET（不原子）：
  请求A: GET key → nil
  请求B: GET key → nil      ← 也读到了 nil！
  请求A: SET key "processing"
  请求B: SET key "processing"  ← 两个都通过了！

✅ SET NX（原子）：
  请求A: SET NX key "processing" → OK
  请求B: SET NX key "processing" → nil（失败） ← 只有一个能成功
```

**代码位置**：`OrderController.createOrder`，在秒杀令牌校验通过之后、售罄检查之前。

```java
// OrderController.createOrder — 新增代码块
// 位置：promoToken 校验通过后（约第 174 行），售罄检查之前（约第 181 行）

if (promoId != null) {
    String orderKey = "order_user_promo_" + promoId + "_" + userModel.getId();

    // SET NX：仅在 key 不存在时才设置成功，原子操作
    Boolean isFirstRequest = redisTemplate.opsForValue()
            .setIfAbsent(orderKey, "processing", 1, TimeUnit.HOURS);

    if (Boolean.FALSE.equals(isFirstRequest)) {
        // key 已存在 → 该用户已经有过一次请求
        String existingValue = (String) redisTemplate.opsForValue().get(orderKey);

        if ("1".equals(existingValue)) {
            // 已经成功下过单了 → 直接拒绝
            throw new BusinessException(
                EmBusinessError.USER_ALREADY_ORDERED,
                "您已经参与过本次秒杀，每个用户限购一单"
            );
        } else {
            // "processing" 状态 → 上一次请求可能还在处理中
            // 保守处理：拒绝，提示稍后重试
            throw new BusinessException(
                EmBusinessError.USER_ALREADY_ORDERED,
                "您有一个订单正在处理中，请稍后再试"
            );
        }
    }
}
```

**思考：为什么 `processing` 状态下不让重试？**

如果在 `processing` 时允许重试，会出现这种情况：

```
请求A: SET NX "processing" → 成功 → 进入下单
请求B: SET NX → 失败 → 读到 "processing"
       如果此时允许请求B重试（比如删掉标记重新 SET NX）
       → 请求B 也进入下单
       → 请求A 和 请求B 都扣了库存
```

两个请求同时竞争，就违背了"一人一单"的设计初衷。

保守处理（直接拒绝）是安全的。用户可以等几秒重试——如果请求A 成功了，标记变成 "1"，用户能看到"已下单"；如果请求A 失败了，标记会被第二层防护清除，用户下次请求就能通过了。

### 第二层：事务回滚时清除标记

**场景**：用户请求通过了第一层检查 → Redis 扣了库存 → 但订单创建失败（比如 MySQL INSERT 时参数校验不通过）→ 事务回滚。

此时应该清除 Redis 标记，允许用户重试。否则标记留在 Redis，用户永远无法再下单。

**代码位置**：`OrderServiceImpl.createOrder`，扩展现有的 `TransactionSynchronization` 回调。

你当前已有回补 Redis 库存的回调逻辑，在它旁边加入标记清除：

```java
// OrderServiceImpl.createOrder — 在现有的 TransactionSynchronization 中扩展

// 当前已有的回补逻辑（保留）：
TransactionSynchronizationManager.registerSynchronization(
    new TransactionSynchronizationAdapter() {
        @Override
        public void afterCompletion(int status) {
            if (status == TransactionSynchronization.STATUS_ROLLED_BACK) {
                // === 原有：回补 Redis 库存 ===
                for (int i = 0; i < 3; i++) {
                    try {
                        itemService.increaseStock(itemId, amount);
                        break;
                    } catch (Exception e) {
                        if (i == 2) {
                            log.error("Redis回补失败！itemId={}, amount={}",
                                    itemId, amount, e);
                        } else {
                            try { Thread.sleep(100L * (i + 1)); }
                            catch (InterruptedException ignored) {}
                        }
                    }
                }

                // === 新增：清除"一人一单"标记，允许用户重试 ===
                if (promoId != null) {
                    String orderKey = "order_user_promo_" + promoId + "_" + userId;
                    redisTemplate.delete(orderKey);
                    log.info("订单回滚，清除一人一单标记: key={}", orderKey);
                }
            }
        }
    });
```

**下单成功时更新标记**：事务正常提交后，把标记从 `"processing"` 更新为 `"1"`（表示已完成），这个写在 `createOrder` 方法中 stock_log 更新之后、return 之前：

```java
// 设置库存流水状态为成功（已有代码）
StockLogDO stockLogDO = stockLogDOMapper.selectByPrimaryKey(stockLogId);
if (stockLogDO == null) {
    throw new BusinessException(EmBusinessError.UNKNOWN_ERROR);
}
stockLogDO.setStatus(2);
stockLogDOMapper.updateByPrimaryKeySelective(stockLogDO);

// === 新增：一人一单标记改为"已完成" ===
if (promoId != null) {
    String orderKey = "order_user_promo_" + promoId + "_" + userId;
    redisTemplate.opsForValue().set(orderKey, "1", 24, TimeUnit.HOURS);
    // TTL 改为 24 小时，保证活动结束后标记自动清除
}
```

### 第三层：MySQL 唯一索引兜底

**场景**：Redis 主从切换导致标记丢失、或 Redis 标记被误删等极端情况下，依赖数据库唯一索引做最后保障。

```sql
-- 添加唯一索引
-- 注意：如果表中已有重复数据，需要先清理
ALTER TABLE order_info ADD UNIQUE INDEX idx_user_promo (user_id, promo_id);
```

**历史数据处理**：当前表中 `user_id=23, promo_id=1` 有 2 条记录，加索引前需要处理。如果这些是测试数据，直接删除即可：

```sql
-- 保留最早的一条，删除重复的
DELETE o1 FROM order_info o1
INNER JOIN order_info o2
WHERE o1.user_id = o2.user_id
  AND o1.promo_id = o2.promo_id
  AND o1.id > o2.id;
```

**代码层面 catch 唯一索引冲突**：在 `OrderServiceImpl.createOrder` 的 INSERT 处：

```java
try {
    orderDOMapper.insertSelective(orderDO);
} catch (DuplicateKeyException e) {
    // 极端情况：Redis 标记失效但 MySQL 唯一索引兜住了
    throw new BusinessException(
        EmBusinessError.USER_ALREADY_ORDERED,
        "您已经参与过本次秒杀，每个用户限购一单"
    );
}
```

需要的额外 import：

```java
import org.springframework.dao.DuplicateKeyException;
```

## R (Result)：效果

### 正常场景

| 场景 | 改前 | 改后 |
|------|------|------|
| 同一用户单次点击 | 下单成功 | 下单成功 |
| 同一用户连续点击两次 | 生成 2 个订单 | 第 1 个成功，第 2 个被 Redis SET NX 拦截（~1ms 返回） |
| 同一用户双开页面同时点击 | 2 个请求都通过，生成 2 个订单 | SET NX 原子保证只有 1 个通过，另一个被拦截 |
| 下单失败后重试 | 可以重试 | 可以重试（回滚时清除标记） |
| 下单成功后再次点击 | 生成第 2 个订单 | 标记为 "1"，直接拒绝 |
| Redis 标记丢失 + 重复请求 | — | MySQL 唯一索引兜底，抛 DuplicateKeyException |

### 量化指标

| 指标 | 数值 |
|------|------|
| 第一层拦截延迟 | ~1ms（一次 `SET NX` 或 `SET NX` + `GET`） |
| 拦截比例 | 99.9%+（并发请求中只有第一个能拿到 SET NX） |
| 第二层清除延迟 | 0（与事务回滚同步触发） |
| 额外 Redis 调用 | 成功路径 +1 次（SET NX），失败重试 +0（第二层清除） |
| 对 TPS 影响 | 可忽略（单次 SET NX 耗时 <0.5ms） |

## L (Learn)：反思

### 做的好的地方

1. **SET NX 的原子性利用**：用 Redis 单命令解决并发竞态，比加分布式锁轻量得多。一个 `setIfAbsent` 就替代了 `GET + IF + SET` 三步操作，代码简洁且无窗口期。

2. **状态机设计**：标记用 `"processing"` 和 `"1"` 两个状态，而不是二元（存在/不存在）。`"processing"` 状态让系统能区分"正在处理中"和"已完成"，对并发请求做不同处理。

3. **"拦截前置"原则**：把一人一单检查放在 Redis 扣库存和 MQ 事务消息之前。如果放在之后，拦截的意义就大打折扣了——下游资源已经消耗了。

4. **多层防御**：Redis 做快速拦截，MySQL 做最终兜底。每一层独立起作用，任何单层失效都不会导致数据被破坏。

### 可以改进的地方

1. **`processing` 状态的处理过于保守**

   当前方案中，遇到 `processing` 直接拒绝。但如果 SET NX 成功后 JVM 立即崩溃（第一层和第二层之间），标记永远是 `processing`，在 TTL 到期前用户都无法重试。

   **改进方向**（后续迭代）：在 `processing` 状态上加"超时容忍"——如果 TTL 剩余时间 < 55 分钟（说明标记已存在 > 5 分钟），大概率是残留标记。结合 `stock_log` 表查询——如果对应的 stock_log 没有 status=1 的悬空记录，就可以安全删除标记并允许重试。

2. **TTL 的合理性**

   当前硬编码 1 小时。更优的做法是根据秒杀活动的实际结束时间动态计算 TTL。活动结束后标记自动清除，不占用 Redis 内存。

   ```java
   long ttlSeconds = (promoModel.getEndDate().getMillis() - System.currentTimeMillis()) / 1000;
   if (ttlSeconds < 3600) ttlSeconds = 3600;  // 最少 1 小时
   redisTemplate.opsForValue().setIfAbsent(orderKey, "processing", ttlSeconds, TimeUnit.SECONDS);
   ```

3. **定时对账**

   与之前的"Redis 库存对账"保持一致的思路：加一个定时任务，扫描 TTL 很短的 `order_user_promo_*` 标记，结合 `stock_log` 和 `order_info` 表判断是否是残留，自动清理。这样就不需要在 `processing` 分支中加入复杂的超时容忍逻辑——定时任务统一处理。

### 核心认知

1. **并发控制的层级选择**：能用原子命令就不用锁，能用 Redis 原子就不用 Lua 脚本，能用 Lua 就不用分布式锁。`SET NX` 一行代码解决的问题，不应该引入 Redisson 的 `RLock`。

2. **"失败可重试"是好的用户体验**：`processing` + `1` 的双状态设计，配合第二层的事务回滚清除，保证了用户不会因为一次偶然的失败就被永久拉黑。

3. **兜底永远在数据库**：Redis 是缓存，是加速层，不是 truth source。任何 Redis 层面的逻辑都要假设它可能失效，在 MySQL 层面用唯一索引做出最终的、不可绕过的保证。
