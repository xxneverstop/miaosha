# 线程池有界队列改造

> 将队列泄洪的线程池从无界队列改为有界队列 + 拒绝策略

---

## 一、为什么要改？

### 当前代码

`OrderController.java` 第 60 行：

```java
executorService = Executors.newFixedThreadPool(20);
```

`Executors.newFixedThreadPool(20)` 的底层实现：

```java
new ThreadPoolExecutor(20, 20, 0L, TimeUnit.MILLISECONDS,
                       new LinkedBlockingQueue<Runnable>());  // ← 无参构造 = 无界队列！
```

`LinkedBlockingQueue` 无参构造的容量是 `Integer.MAX_VALUE`（约 21 亿），等于无界。

### 有什么问题？

秒杀场景下请求链路是这样的：

```
用户请求
  │
  ├─ [验证码]    ──失败──▶ 拒绝
  ├─ [秒杀令牌]  ──失败──▶ 拒绝（大闸关闭 / 售罄）
  ├─ [RateLimiter] ──失败──▶ "活动太火爆"
  │
  └─ [线程池 submit]  ← 到这里时，已经过了前面三道防线
       │
       ├─ 20 个线程在处理
       └─ 剩余请求 → 无界队列 → 无限堆积 → OOM
```

**前面三道防线没有 100% 拦截率**：
- 大闸倍数可能设大了（令牌发多了）
- RateLimiter 放行的请求速率可能超过线程池处理速率
- 即使每个请求都被正确过滤，极端并发下进入线程池的任务数仍然可能远超 20

无界队列的后果：

```
t=0s     20 个请求在处理
t=1s     20 个在处理，100 个在队列里等着
t=2s     20 个在处理，200 个在队列里等着
t=10s    20 个在处理，1000 个在队列里等着
         ↑
         队列里的每个 Future 都关联着一个阻塞的 Tomcat 线程
         Tomcat 线程池 + 队列对象 → 内存持续增长 → OOM
```

**队列泄洪的初衷是用队列「缓冲」流量，但无界队列 = 没有上限 = 失去了「闸」的意义。**

### 改后的效果

有界队列（容量 100）+ AbortPolicy：

```
t=0s    20 线程忙，队列有 100 个空位
t=1s    20 线程忙，队列 100 个满
        第 121 个请求 → submit() 抛 RejectedExecutionException
        → 返回 "活动太火爆，请稍后再试"
```

队列容量 = 100 意味着在最坏情况下（20 个在处理 + 100 个在排队），只有 120 个请求同时在等待，第 121 个被直接拒绝——不会无限增长。

## 二、怎么改？

### 改哪里

**文件**：`OrderController.java`

**位置 1**：`@PostConstruct init()` 方法——改线程池创建方式

```java
// 改前
executorService = Executors.newFixedThreadPool(20);

// 改后
executorService = new ThreadPoolExecutor(
        20, 20,                             // 核心线程 = 最大线程 = 20
        0L, TimeUnit.MILLISECONDS,           // 空闲线程存活时间（不适用，因为 core=max）
        new LinkedBlockingQueue<>(100),      // 有界队列，容量 100
        new ThreadPoolExecutor.AbortPolicy() // 队列满时抛异常，不静默丢弃
);
```

**位置 2**：`createOrder` 方法——加 `RejectedExecutionException` 处理

```java
// 改前：只 catch InterruptedException 和 ExecutionException
try {
    future.get();
} catch (InterruptedException e) {
    throw new BusinessException(EmBusinessError.UNKNOWN_ERROR);
} catch (ExecutionException e) {
    throw new BusinessException(EmBusinessError.UNKNOWN_ERROR);
}

// 改后：把 submit 也包进 try，加 RejectedExecutionException
try {
    Future<Object> future = executorService.submit(new Callable<Object>() {
        @Override
        public Object call() throws Exception {
            String stockLogId = itemService.initStockLog(itemId, amount);
            if (!mqProducer.transactionAsyncReduceStock(
                    userModel.getId(), itemId, promoId, amount, stockLogId)) {
                throw new BusinessException(EmBusinessError.UNKNOWN_ERROR, "下单失败");
            }
            return null;
        }
    });
    future.get();
} catch (RejectedExecutionException e) {
    // 线程池队列满了，拒绝新任务
    throw new BusinessException(EmBusinessError.RATELIMIT);
} catch (InterruptedException e) {
    throw new BusinessException(EmBusinessError.UNKNOWN_ERROR);
} catch (ExecutionException e) {
    throw new BusinessException(EmBusinessError.UNKNOWN_ERROR);
}
```

> `RejectedExecutionException` 在 `submit()` 时抛出（不是 `get()` 时），所以 `submit()` 也要在 try 块内。

## 三、为什么选 AbortPolicy？

四种内置拒绝策略：

| 策略 | 行为 | 适合队列泄洪？ |
|------|------|:---:|
| **AbortPolicy**（默认） | 抛 `RejectedExecutionException` | ✅ 明确拒绝，用户立即得到反馈 |
| CallerRunsPolicy | 由调用者线程（Tomcat 线程）执行任务 | ❌ Tomcat 线程被拖去执行下单，会阻塞更多请求 |
| DiscardPolicy | 静默丢弃新任务 | ❌ 用户请求挂起无响应 |
| DiscardOldestPolicy | 丢弃队列中最老的任务 | ❌ 先来的用户被插队，不可接受 |

**AbortPolicy 最合适**——队列满了就明确拒绝，用户看到 "活动太火爆"，和我们已有的 `RATELIMIT` 语义一致。

### 为什么不是 CallerRunsPolicy？

`CallerRunsPolicy` 会让 Tomcat 线程直接执行 `Callable` 里的下单逻辑：

```
线程池满了 → Tomcat 线程自己跑下单 → 这个 Tomcat 线程被长时间占用
→ 其他用户的正常请求（如查看商品详情）没线程可用 → 整个服务假死
```

CallerRunsPolicy 适合**可快速完成**的轻量任务，下单包含 DB 写操作，不适合。

## 四、队列容量为什么是 100？

```
队列容量 = RateLimiter 放行速率 × 单个任务最大处理时间 × 安全系数

按当前配置：RateLimiter = 5 QPS，单任务最长约 5s（含 MQ 超时）
  5 × 5 × 4 = 100
```

- 5 QPS × 5 秒 = RateLimiter 在 5 秒内最多放行 25 个请求（极端情况）
- 实际中很多请求会被令牌和售罄过滤，100 够用且有盈余
- 如果 RateLimiter 开到 300 QPS，队列容量需要相应调到 500+

**容量不是固定值，要根据 RateLimiter 配置和单任务耗时调。** 太小——正常流量被拒；太大——起不到保护作用。

## 五、四层防护的最终形态

改完后，整个下单链路的防护层次：

```
第一次请求：POST /order/generatetoken（获取入场券）
  │
  ├─ [第一层] 验证码            → 防脚本，拉长请求间隔
  │     └─ 失败 → "验证码错误"
  │
  └─ [第二层] 秒杀令牌 + 大闸   → 总量控制，最多发 stock×5 个令牌
        └─ 失败 → "生成令牌失败"（大闸关闭 / 售罄 / 活动未开始）

拿到令牌后，第二次请求：POST /order/createorder（真正下单）
  │
  ├─ [第三层] RateLimiter       → 速率控制，每秒最多放行 N 个
  │     └─ 失败 → "活动太火爆" (errCode=30003)
  │
  ├─ [第四层] 令牌校验           → 防绕过，Redis 比对 promoToken
  │     └─ 失败 → "秒杀令牌校验失败"
  │
  └─ [第五层] 线程池有界队列     → 并发度控制，20 线程 + 100 队列
        ├─ 20 线程并行处理
        ├─ 100 容量队列缓冲
        └─ 满了 → AbortPolicy → "活动太火爆" (errCode=30003)
```

| 防护层 | 所在接口 | 限制维度 | 失败了返回什么 |
|--------|----------|----------|---------------|
| 验证码 | `/generatetoken` | 人机识别 | 验证码错误 |
| 令牌+大闸 | `/generatetoken` | 总量（stock × 5） | 生成令牌失败 |
| RateLimiter | `/createorder` | 速率（N QPS） | 活动太火爆 (30003) |
| 令牌校验 | `/createorder` | 安全（防伪造绕过） | 秒杀令牌校验失败 |
| 线程池有界队列 | `/createorder` | 并发度（20+100） | 活动太火爆 (30003) |

**五层之间是递进关系，每一层拦不住的由下一层兜底。** 改动前，第五层队列无界——等于没有限制，前四层漏过来的请求全部堆积不拒绝。改动后，第五层也有限制，整条链路「总量 → 速率 → 并发度」全部可控。

## 六、验证方法

### 6.1 正常流量：不应触发拒绝

1. RateLimiter 临时设大（如 100）
2. 浏览器手动下单 5 次
3. 预期：全部成功，没有 `RejectedExecutionException`

### 6.2 超限流量：应触发拒绝

1. RateLimiter 临时设大（如 500），让大量请求冲过限流
2. 线程数临时改小（如 2），队列容量改小（如 5），更容易触发满
3. JMeter 500 线程并发
4. 预期：
   - 有些请求成功
   - 有些请求返回 errCode=30003（被 AbortPolicy 拒绝）
   - 应用日志能搜到 `RejectedExecutionException`

### 6.3 恢复后正常

1. 限流恢复后，线程池队列逐渐消化
2. 新的请求正常进入队列
3. 不会因为之前满了就一直不可用

## 七、面试级总结

### 问题是什么？

`Executors.newFixedThreadPool(20)` 底层用无界 `LinkedBlockingQueue`，队列泄洪失去上限，极端并发下任务无限堆积导致 OOM。

### 怎么发现的？

读 JDK 源码发现 `Executors.newFixedThreadPool` → `new LinkedBlockingQueue<Runnable>()` 无参构造容量为 `Integer.MAX_VALUE`。

### 怎么解决的？

改用 `new ThreadPoolExecutor(20, 20, 0L, ..., new LinkedBlockingQueue<>(100), new AbortPolicy())`——显式指定队列容量 100 + 满了抛异常。

### 为什么选 100？

RateLimiter(5 QPS) × 最长处理时间(~5s) × 安全系数(4) = 100。容量不是固定值，要根据上游放行速率和下游处理能力调。

### 为什么选 AbortPolicy？

- `AbortPolicy`：抛异常 → 用户立即反馈，不浪费资源
- `CallerRunsPolicy`：Tomcat 线程被阻塞执行下单 → 影响其他接口
- `DiscardPolicy` / `DiscardOldestPolicy`：静默丢弃 → 用户请求无响应

### 核心教训

1. **`Executors` 工厂方法的默认队列都是无界的**——`newFixedThreadPool` 用 `LinkedBlockingQueue` 无界，`newCachedThreadPool` 用 `SynchronousQueue` 有界但线程数无界。两种都有坑，生产代码推荐直接用 `new ThreadPoolExecutor` 显式指定所有参数

2. **队列泄洪的关键是「有界」**——无界队列等于没有闸，和没做队列泄洪效果一样

3. **四层防护必须层层有上限**——防御体系最弱的一环决定整体效果，无界队列让前三层防线自废武功
