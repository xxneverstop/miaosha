## 1，秒杀项目的下单链路
用户点击秒杀后：

**拿令牌、下单、创建订单**



第一步是拿秒杀令牌。

系统先检查活动和商品状态，

然后扣减 Redis 里的大闸数量。

大闸控制能发多少个令牌，大闸用完了，后面的用户就拿不到下单资格。  



第二步是用户真正下单。

用户带着令牌进入下单接口，系统先用RateLimiter 限流，

再校验令牌和售罄标记（快速失败）。

（redis取出和用户的比对，防止有人绕过令牌接口直接调下单）

通过以后，请求进入有界线程池做队列泄洪，

控制同时处理的下单数量，队列满了就直接拒绝。



第三步是创建订单。

系统先创建库存流水，再发送 mq 事务半消息（消费者此时看不到）。

在本地事务里，用 Redis Lua 原子扣库存，

然后写订单、加销量，并把库存流水改成成功。

如果订单失败则数据库事务回滚，

并且通过回调 回补 Redis 库存；

如果本地事务成功，

commit事务消息，消费者再去扣 MySQL 库存，把库存流水改成成功状态。

本地事务失败就，回滚消息，消费者永远收不到



消费者那边做了幂等，用 Redis 的 SETNX 防止重复消费，因为 RocketMQ 是至少一次投递。







## 2，库存一致性怎么保证？


  所以一致性是怎么保证的？

  1. Lua 原子脚本：Redis 内部的"判断+扣减+设售罄标记"是一步完成的，Redis 层面不会出现超卖。

  2. 事务消息：本地事务成功消息才投递，失败就回滚，保证 Redis 扣了、DB 一定会同步。

  3. stock_log 流水表：充当了"事务日志"的角色，回查和补偿都靠它来判断状态。

stock_log 状态有三个值：1 初始化、2 成功、3 失败。

  4. 回滚补偿 + 重试：DB 事务失败时 Redis 自动回补，3 次重试加日志兜底。

这一步因为 redis 操作不受数据库事务控制，需要手动实现回调实现redis回补，		而补一次不可靠，就重试 3次；全失败就记日志，让定时对账兜底。



  一句话：做不到实时强一致，但通过事务消息 + 流水表 + 回滚补偿，保证了最终一致性。秒杀场景下，Redis

  扛住并发是第一优先级，DB 跟上就行。

## 8，压测数据怎么来的？
压测对比的是同一台机器、同一个场景，500 并发抢 100 件商品。

压测环境很弱——阿里云 2 核 2G、公网 3Mbps，在这种受限条件下用 JMeter 压的。

  最终结果：下单 QPS 从 142 提到 1200，大概 8.5 倍；P99 延迟从 9500 毫秒降到 1650 毫秒。

  拆开来看的话，三块优化各自贡献了一部分：

  

**多级缓存**：

加了 Caffeine 本地缓存 + Redis + MySQL 三级查询之后，

数据库读压力从 90 降到 2，Redis QPS 从 140 降到  45，降了 68%。

读路径不再是瓶颈，数据库连接池和 Redis 带宽都腾出来给写操作了。

  

**Redis Lua 原子扣库存**：

这是最大的收益来源。

改之前库存扣减走 MySQL 行锁，几百个请求同时 UPDATE  同一行，全部串行排队等锁，数据库连接池瞬间打满。

P99 延迟 9500 毫秒——用户等 9 秒多，基本是不可用状态。

改成 Redis  预热库存 + Lua 原子扣减之后，扣库存这个操作从磁盘行锁变成了内存原子操作，单机 QPS 从 142 直接拉到 1200，P99 降到 1650  毫秒。

  

**RocketMQ 事务消息异步同步**：订单创建后，MySQL 库存同步走 MQ 异步消费，数据库的瞬时写入压力降了约 4.3 倍。



  一句话：142 → 1200，核心是把库存扣减从 MySQL 行锁串行变成了 Redis Lua 内存原子操作，其余缓存和异步优化是辅助。环境只有  2 核 2G，如果机器配置好一点，数字还能往上走。

## 10，库存流水有什么作用？


库存流水是数据库里的一张 stock_log 流水表，

每条记录有唯一 ID

状态字段 有三个值：1 初始化、2 成功、3 失败。



**1，下单前，先写流水。** 

请求进入线程池后，第一件事不是扣库存，而是往 stock_log 表插入一条记录，状态为

  1（初始化），返回这个 UUID。

通过这个 ID 查到这笔操作的状态。



**2，事务消息里，流水充当本地事务与 MQ 之间的桥梁。**

 RocketMQ  发的是事务消息（半消息），然后执行本地事务。

本地事务是加 @Transactional 的——Redis Lua  扣库存、插订单、更新销量、把流水状态从 1 改为 2，这几个操作在同一个数据库事务里，要么全成功，要么全回滚。



如果本地事务抛异常了：MQ 回调里把流水状态标为 3（失败），然后返回 ROLLBACK，消息作废。

如果本地事务成功了：返回 COMMIT，消息投递给消费者。

****

**3，宕机恢复靠回查流水。 **

如果本地事务执行成功了，但 COMMIT 消息发出去之前服务宕机了，怎么办？

 RocketMQ 收不到 COMMIT，会回调 checkLocalTransaction。

这时候唯一可靠的依据就是数据库。

它拿 stockLogId  去查流水状态：

状态是 2，说明本地事务已经提交了，补一个 COMMIT；

状态是 1，说明还在处理中，返回 UNKNOW 等下次再查；

状态是 3，说明失败了，ROLLBACK。



**4，消费者幂等也靠流水。** 

消费者收到消息后，用 stock_log_synced_{stockLogId} 做 SETNX 去重——同一个流水 ID  只处理（扣数据库的库存）一次。

主要针对mq的多次投递做处理，保证幂等



## 11，事务消息怎么保证只消费一次？
消费者收到消息后，先从消息体里拿出 stockLogId（这是下单时生成的库存流水 UUID，全局唯一），

拼一个key：stock_log_synced_{stockLogId}。然后调 Redis 的 setIfAbsent，把 key 设为 "1"。

+ 第一次来：setIfAbsent 返回 true，说明这个 key 不存在，是首次处理。继续往下走，真正扣数据库库存，key 设 1 小时过期。
+ 重复投递：setIfAbsent 返回 false，说明这个 key 已经存在，之前处理过了。直接跳过，不做任何操作。

 本质上就是把"是否已消费"这个状态外化到 Redis 里，用 stockLogId 的唯一性来保证同一条流水只被处理一次。

  一句话：at-least-once 投递 + 消费端幂等 = 效果上只消费一次。

## 5，harness的理解
在harness 这个词之前，就有claude code和codex，他们是不是harness？



可以分技术层面和产品层面。

从技术层面看，Claude Code 和 Codex 都包含完整的 Agent Harness。

它们都需要组织上下文、驱动模型和工具之间的循环、执行文件和命令操作、维护任务状态，并对权限和执行环境进行控制，所以可以把它们看成成熟的 Coding Agent Harness 实现。



但从产品层面看，它们又不只是 Harness。

完整产品一般还包含模型、Harness、沙箱或者运行环境、CLI 或 IDE 交互、云端服务、账号系统以及代码审查等产品能力。

因此，更准确的表达是：

Claude Code 和 Codex 是构建在 Agent Harness 之上的完整 Coding Agent 产品，

Harness 是它们内部负责 Agent Loop 和执行控制的核心部分。

Harness 这个词流行得比产品晚也不矛盾。

很多系统可能先被实现出来，后来行业才用一个更统一的术语来总结它们共有的工程层。

## 9，了解skill吗？skill和mcp有什么区别？
skill写成一个mcp tool不是一样的吗？



MCP 和 Skill 不是完全互斥的，两者解决的是不同层次的问题。



MCP 更像 Agent 连接外部能力的标准协议，

MCP Tool 主要描述 Agent 可以调用什么能力，

比如查询数据库、读取代码或者执行测试。



Skill 更像一套可复用的任务方法，

它会告诉 Agent 面对某类任务时应该按照什么流程判断、调用哪些工具，以及如何检查最终结果。



Skill 里的要求当然可以写进 MCP Tool。



假如只是写到 Tool 的 description 里，

它更多是在提示模型怎么使用工具，

不能保证整套流程稳定执行；

假如直接把整套流程实现到 MCP Server 内部，

得到类似的业务结果，但这时流程变成了一个服务端黑盒，Agent 的灵活编排能力会下降，所以两者仍然不是同一种抽象。



我一般会把可复用的工作流、经验和工具选择放在 Skill 中，把查询、执行、文件操作等能力放在 MCP Tool 中；

安全校验、权限控制、幂等之类的硬约束则放到 MCP Server 内部强制保证。

所以可以简单概括为：MCP 提供能力，Skill 组织能力，服务端保证约束。





## 10，function calling和tool calling有什么区别和联系？
 Function Calling 和 Tool Calling 底层流程是高度一致的，

很多场景下这两个词也会混用。



更准确地说，Tool Calling 是一个更宽泛的概念，

表示模型能够选择并调用外部能力；

Function Calling 是其中一种具体形式，

通常是开发者通过函数名称、描述和 JSON Schema，把

自己的 Java 或 Python 函数声明给模型。



它们的执行流程基本都是：先把工具定义传给模型，模型根据用户意图生成工具名称和参数；模型本身通常不直接执行代码，而是由应用程序校验参数、进行权限判断并真正执行，再把执行结果返回给模型，模型基于结果继续回答。



两者的主要区别是范围。

Function Calling 主要面向自定义函数，

而 Tool Calling 除了 Function，

还可以包括 Web Search、文件检索、代码执行、Computer Use，以及 MCP Server 暴露的工具。

所以可以概括为：Function Calling 是 Tool Calling 的一种；只讨论自定义函数时，两者基本可以认为是同一套调用机制。

## 16，秒杀项目中的多级缓存讲一下？


为什么要多级缓存？只要redis或者caffeine行不行？



为什么要多级缓存？为什么这么设计？

秒杀场景中，同一个热门商品会被大量用户反复查看。

读多写少、热点集中的。

所有请求都查 MySQL，磁盘慢，

每次会占用数据库连接，执行 SQL，解析结果并进行对象组装。高并发下连接池和数据库 CPU 会先成为瓶颈，

商品详情这种非核心读取还可能拖慢下单事务。



加 Redis 后，大部分请求不再访问 MySQL，缓解压力。

但 Redis 要跨网络访问，还要占用连接池，进行序列化和反序列化。

一个热点 key 被几十万次读取时，Redis 节点、网卡和连接数也会承受压力。



所以再加 Caffeine。

热门商品直接存在当前 JVM 中，同一实例收到的重复请求可以在进程内完成读取。

它把热点流量在入口处分散到各个应用节点，

而不是全部汇聚到一个 Redis 集群。



不过多一级缓存也会增加代价：数据副本更多，更新和失效更复杂；每个 JVM 的本地缓存互相不知道对方的状态；监控和容量规划也更难。因此，多级缓存适合热点明显、读多写少、允许短时间最终一致的商品详情数据，不应无差别地给所有业务数据都加本地缓存。



我对这个设计的总结是：多级缓存是在性能、成本和一致性之间做分层取舍。越靠前越快，但容量更小、共享性更差；越靠后越权威，但访问成本越高。
