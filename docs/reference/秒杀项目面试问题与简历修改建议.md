## 二、这些问题实际在考什么

这些追问并不是让候选人机械背诵 Redis、Lua 和 RocketMQ。面试官主要在验证五件事：能否按真实执行顺序讲清链路；能否说明每个中间件解决的具体问题；能否识别一致性方案的边界；能否用业务成功率而不是只用 HTTP 吞吐包装压测结果；以及项目中哪些能力已经实现、哪些仍是设计方案。

当前简历已经覆盖多级缓存、Lua 和事务消息，技术关键词足够，但对“流量治理完整链路”“实际排障过程”“一致性边界”和“压测统计口径”交代不足。面试中恰好反复追问的也是这四块，因此简历应从“罗列技术方案”调整为“问题—实现—验证—边界”。

## 三、当前简历描述中需要立即修改的内容

### 1. 删除“定时对账补偿机制已实现”的表述

当前简历写的是“结合库存流水状态机、Consumer 幂等和定时对账补偿机制，保证 Redis 缓存库存与 MySQL 库存的最终一致”。这与源码不符。

项目中已经实现的是：`stock_log` 初始化；本地事务成功后把状态更新为 2；RocketMQ 根据流水状态进行事务回查；数据库事务回滚后通过 `afterCompletion` 回补 Redis，并最多重试 3 次（`src/main/java/com/imooc/miaoshaproject/service/impl/ItemServiceImpl.java:175`、`src/main/java/com/imooc/miaoshaproject/service/impl/OrderServiceImpl.java:101`、`src/main/java/com/imooc/miaoshaproject/mq/MqProducer.java:81`）。

但是项目没有 `@Scheduled` 对账任务，面经也明确写了“目前代码对账脚本还没落地”（`docs/reference/面经.md:301`）。因此应改成“设计了定时对账方案作为后续兜底”，不能写成已经实现。更不能直接写“保证最终一致”，建议改成“覆盖正常提交、事务回滚、消息回查和重复投递等主要异常路径，追求 Redis 与 MySQL 的最终一致”。

### 2. 把“异步下单”改成“异步同步数据库库存”

当前 HTTP 下单接口把任务提交到线程池后立即调用 `future.get()`，请求线程仍会同步等待本地事务完成（`src/main/java/com/imooc/miaoshaproject/controller/OrderController.java:224`）。因此项目不是“请求提交后立即返回”的完全异步下单。

真正异步的是：本地订单事务成功后，RocketMQ Consumer 再异步扣减 MySQL 库存（`src/main/java/com/imooc/miaoshaproject/mq/MqConsumer.java:73`）。简历应使用“事务消息异步同步 MySQL 库存”“削平数据库库存写入峰值”，避免面试官沿着“异步下单如何返回订单结果”继续追问时出现口径冲突。

### 3. 不要把 `stock_log` 过度包装成完整状态机

代码确实使用 1、2、3 三种状态，并用它们支持 RocketMQ 事务回查。但当前实现主要是状态字段和分支判断，没有统一的状态迁移约束、非法迁移校验或补偿调度器。写“库存流水状态记录与事务回查”比写“库存流水状态机”更准确，也更容易守住追问。

### 4. 重新核验 1200 QPS 的统计口径

这是当前简历风险最高的一点。当前代码在进入下单逻辑前执行 `tryAcquire()`，而限流器被硬编码为每秒 5 个许可（`src/main/java/com/imooc/miaoshaproject/controller/OrderController.java:71`、`src/main/java/com/imooc/miaoshaproject/controller/OrderController.java:157`）。在这份代码不变的情况下，不可能同时得到“每秒 1200 个业务成功订单”。

JMeter 的 Throughput 会统计所有 HTTP 响应；如果没有对响应体中的业务状态做断言，被限流、库存不足、令牌失败的响应也可能计入吞吐。面经中“压测数据怎么考虑失败请求”正是在质疑这一点（`docs/reference/面经.md:360`）。虽然现有压测报告写了 0% 错误率（`docs/秒杀系统压测结果报告.md:68`），但仓库中没有保留对应的 `.jmx`、`.jtl` 和 HTML 原始报告，且这一结果与当前 `RateLimiter(5)` 无法互相印证。

在继续使用 142 → 1200 前，至少需要做到：把限流速率改为可配置并记录每轮配置；JMeter 对业务成功码做响应断言；分别统计接口吞吐、业务成功 QPS、限流 QPS、库存不足 QPS；用新增订单数和 Redis/MySQL 库存差值做二次核验；保存 `.jmx`、`.jtl` 和报告。补齐之前，简历中不建议直接写“下单 QPS 1200”，最多写成“接口吞吐达到 1200 QPS”，并明确它不是成功订单 QPS。

### 5. 给 45 倍和 68% 补上范围与来源

“数据库读压力降低约 45 倍”来自 MySQL 读 QPS 约 90 → 2；“Redis QPS 降低 68%”来自 Redis-only 与多级缓存两种模式下 Redis QPS 约 140 → 45 的差值推算（`docs/秒杀系统压测结果报告.md:104`）。这两个指标可以保留，但简历最好直接写原始值，避免“压力”含义模糊。

还需注意，同一份压测报告后半部分又出现 Redis QPS 1900 → 720、Caffeine 推算命中率 62% 的另一组数据（`docs/秒杀系统压测结果报告.md:467`、`docs/秒杀系统压测结果报告.md:497`）。投递简历前应统一报告口径，只保留同一轮、同一参数下的一组结果。

### 6. 增加面试中反复被问到的流量治理链路

当前简历没有体现验证码、秒杀大闸、令牌校验、售罄标记、RateLimiter 和有界线程池，但这恰好是面试第一问的核心。代码已实现库存 × 5 的大闸、用户维度秒杀令牌、售罄快速失败、限流和 20 线程 + 100 容量有界队列（`src/main/java/com/imooc/miaoshaproject/service/impl/PromoServiceImpl.java:40`、`src/main/java/com/imooc/miaoshaproject/service/impl/PromoServiceImpl.java:115`、`src/main/java/com/imooc/miaoshaproject/controller/OrderController.java:71`、`src/main/java/com/imooc/miaoshaproject/controller/OrderController.java:149`）。建议增加一条“流量治理”描述，让简历与面试中的完整下单链路对齐。

### 7. 不要把“一人一单”写成已实现

面经中给出了 Redis `SETNX` + 数据库联合唯一索引的设计答案，但当前令牌生成逻辑里没有 `promo_user_ordered_*` 占位，`order_info` 表也只有订单主键，没有 `(user_id, promo_id)` 联合唯一索引（`src/main/java/com/imooc/miaoshaproject/service/impl/PromoServiceImpl.java:40`、`sql/miaosha.sql:62`）。这项能力可以作为“如果继续完善会怎么做”的回答，不能放进已完成成果。

### 8. 消费幂等要说明边界，避免使用“严格保证只消费一次”

Consumer 当前先写 `stock_log_synced_{stockLogId}`，再扣 MySQL 库存，而且 `SETNX` 与设置一小时 TTL 是两个命令（`src/main/java/com/imooc/miaoshaproject/mq/MqConsumer.java:61`）。如果占位成功后数据库更新失败，消息重投会因为幂等 key 已存在而跳过；一小时后 key 过期，极晚重投又可能重复扣减。因此更准确的简历表述是“基于 `stockLogId` 增加消费去重，修复重复投递导致的重复扣库问题”，不要写成理论上严格的 exactly-once。

后续若要真正增强，可使用数据库消费记录唯一键，并让“写消费记录 + 扣库存”处在同一个 MySQL 事务中；或者至少在消费失败时删除 Redis 占位，并把 `SET NX EX` 合并成单条原子命令。

## 四、建议突出的一段真实排障经历

相比泛泛写“Consumer 幂等”，更有说服力的是写清实际问题：JMeter 500 线程压测后发现 Redis 扣减 56、MySQL 扣减 60，相差 4；根据同一订单应当只同步一次库存，定位到 RocketMQ 至少一次投递下的重复消费；随后以全局唯一 `stockLogId` 做消费去重，复测 Redis 与 MySQL 扣减量一致（`docs/库存不一致问题排查与修复.md:352`）。

这段经历同时回答了“怎么排查超卖或库存不一致”“MQ 为什么需要幂等”“压测如何验证业务正确性”三个问题，比只写一个技术名词更能体现工程能力。描述时仍应主动补充上一节提到的 Redis 去重边界，表现会更成熟。

## 五、推荐的简历描述

### 版本 A：与当前源码一致、现在即可使用

**高并发秒杀系统**  
**核心技术：** Spring Boot、MyBatis、Redis、Caffeine、RocketMQ、Docker、JMeter

基于 Spring Boot + MyBatis 构建秒杀下单系统，围绕热点商品读取、库存原子扣减、流量治理及 Redis/MySQL 库存同步进行优化，并通过 Docker 部署与 JMeter 并发测试验证核心链路。

· **分层流量治理：** 设计验证码、秒杀大闸与用户维度令牌控制请求准入，下单侧结合售罄标记、Guava RateLimiter 和 20 线程 + 100 容量有界队列，实现防刷、快速失败与过载保护。  
· **多级缓存：** 构建 Caffeine + Redis + MySQL 三级查询链路，本地缓存拦截 JVM 内热点访问，Redis 承担跨实例共享缓存；对照压测中 MySQL 读 QPS 约 90 → 2，Redis QPS 约 140 → 45。  
· **Redis 库存预扣：** 活动发布时预热库存，使用 Lua 将库存校验、扣减和售罄标记封装为原子操作，避免 Redis `INCR` 方案的判断与回补窗口，并在数据库事务回滚后通过事务同步回调重试回补 Redis。  
· **事务消息与一致性排障：** 使用 RocketMQ 事务消息和 `stock_log` 状态记录支持本地事务提交/回滚与 Broker 回查，异步同步 MySQL 库存；通过并发压测定位消息重投造成的重复扣库，以 `stockLogId` 增加消费去重并复测库存差异归零。定时对账目前为后续设计，未写成已实现能力。

### 版本 B：补齐原始压测证据后使用

如果重新压测确认 1200 QPS 是“业务成功 QPS”，可以把版本 A 的第二、三、四条压缩为下面的量化表达：

· **多级缓存：** 构建 Caffeine + Redis + MySQL 三级查询链路；500 并发公网对照压测中，MySQL 读 QPS 约 90 → 2，Redis QPS 约 140 → 45（降低约 68%）。  
· **Lua 原子扣库存：** 将库存预热到 Redis，使用 Lua 原子完成库存校验、扣减与售罄标记；在相同环境、相同成功断言下，业务成功 QPS 由 142 提升至 1200，P99 由 9500ms 降至 1650ms，且订单数未超过初始库存。  
· **事务消息与库存同步：** 使用 RocketMQ 事务消息、`stock_log` 事务回查、数据库回滚后的 Redis 回补及 `stockLogId` 消费去重，覆盖正常提交、事务回滚、Broker 回查与重复投递等路径；MySQL 瞬时库存写入 QPS 约 520 → 120。定时对账作为后续兜底方案设计，未宣称已落地。

量化版本中必须保留“500 并发、同环境、业务成功断言”三个限定词。它们分别回答测试负载、公平对照和失败请求是否被计入的问题。

## 六、面试时应主动说明的项目边界

第一，当前实现追求最终一致，但没有定时对账，所以不能声称覆盖 JVM 在 Redis 扣减后、事务回调注册前崩溃的极端窗口。第二，当前一人一单只有设计文档，没有 Redis 占位和数据库唯一索引实现。第三，HTTP 请求会等待本地订单事务完成，异步的是 MySQL 库存同步而非整个下单响应。第四，现有 Redis 幂等 key 方案解决了已发现的重复消费问题，但不是严格 exactly-once。

主动讲清这些边界不会削弱项目，反而能说明你真正理解分布式系统中的失败窗口、补偿机制和测试口径。
