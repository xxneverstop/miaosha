# **Miaosha 秒杀系统架构审视**

已对照当前 GitHub 仓库 [`xxneverstop/miaosha`](https://github.com/xxneverstop/miaosha?utm_source=chatgpt.com) 的 `master` 分支及 `docs/roadmap.md`，并参考 Redis、RocketMQ 官方文档。

**核心结论：**

- **你对 DECR 的理解基本正确**：直接 DECR，根据返回值判断抢购成功与否，确实可以避免把同一份库存重复卖出。Lua 不是防超卖的唯一方案。
- **Lua 仍然更适合完整秒杀业务**：优势不是“只有 Lua 才能原子扣减”，而是避免失败请求修改库存，并把多个业务约束组成一个不可分割的操作。
- `stock_log`**&#x20;已经是简化状态机的雏形**，但它还不是完整的交易状态机。
- **RocketMQ 事务消息属于合理的业界方案**，不必因为别人使用状态机和普通消息，就替换掉它。
- **当前项目最大的缺陷不在技术选型，而在业务链路的正确性和故障恢复能力**。这是比升级技术栈更需要优先处理的事情。

## **一、为什么不能直接 DECR？**

先明确：**可以直接 DECR，你指出的反例成立。**

假设 Redis 库存为 1，用户 A、B 同时抢购。

| 操作       | 用户 A | 用户 B |
| -------- | ---- | ---- |
| GET 库存   | 1    | 1    |
| DECR 返回值 | 0    | -1   |
| 最终判断     | 成功   | 失败   |

即使 A、B 的 `GET` 都返回库存充足，只要真正扣减后以 `DECR` 的结果作为准入依据，B 就不会成功。

所以：

`GET → DECR`**&#x20;存在并发竞争，不意味着必然超卖。关键是代码依据哪个结果判断成功。**

但这也说明，前面的 GET 对最终正确性没有帮助，可以取消。

### **真正的问题是 DECR 的失败语义**

Redis 的 `DECR` 不负责判断库存够不够，它只是减 1，允许结果为负数。

[image](https://www.google.com/s2/favicons?domain=https://redis.io\&sz=32)

Docs+1



因此，直接 DECR 的完整逻辑应该是：

```
DECR
 ├─ 结果 >= 0 → 扣减成功
 └─ 结果 < 0  → 扣减失败，需要 INCR 回补
```

此时出现了一个新问题：

```
库存 = 0

用户 B：DECR → -1
                   ↓
                服务宕机
                   ↓
             没有执行 INCR
                   ↓
              库存一直是 -1
```

这不会直接导致超卖，但会造成**库存错误、虚假售罄、后续补货数量失真**。

再考虑一次购买 3 件：

```
DECRBY stock 3

原库存 = 2
执行后 = -1
判断失败 → 再 INCRBY 3
```

仍然是先破坏库存，再补偿。

### **Lua 的价值到底是什么？**

**直接 DECR**

扣减库存

判断结果

失败则回补

更新售罄状态

涉及多个独立操作，中间可能失败。

**Lua 条件扣减**

检查库存

足够才扣减

更新售罄状态

整个脚本原子执行

库存不足时直接失败，不修改库存。

Redis 官方明确保证 Lua 脚本执行的原子性。

[image](https://www.google.com/s2/favicons?domain=https://redis.io\&sz=32)

Docs+1



对于常见的生产级秒杀，通常会有比减库存更多的要求，例如：

- 判断购买数量是否超过限购额度。
- 防止同一个请求重复预扣。
- 判断活动库存是否足够。
- 扣减库存并记录预留信息。
- 库存耗尽时同步设置售罄标记。

这些条件才是把逻辑封装成 Lua 的主要动机。

**最终判断：保留 Lua，但应该调整技术解释。**

不要在简历或面试里简单说“Redis GET 和 DECR 有并发问题，所以必须使用 Lua”。

更准确的说法是：

> Redis 的 DECR 本身是原子的，也可以根据返回值防止超卖。但直接 DECR 会造成负库存，需要额外回补。我采用 Lua 实现条件扣减，使库存不足时不发生修改，并保证库存扣减、售罄标记等 Redis 内部操作的一致性。

另外，**查询库存接口与扣库存接口可以分开**，前者供商品页面展示，后者内部使用 Lua 校验并扣减，二者并不矛盾。展示状态可以滞后，真实抢购准入必须以扣减时的结果为准。

## **二、**`stock_log`**&#x20;算不算状态机？**

**算状态机的雏形，但目前只是一个比较简单的事务状态记录。**

我检查了仓库中的 `stock_log` 表：

| `status` | 当前含义        |
| -------- | ----------- |
| 1        | 初始化，等待创建订单  |
| 2        | 本地订单事务成功    |
| 3        | 创建订单失败，标记回滚 |

它的用途主要是让 RocketMQ 回查时判断是否应该投递库存扣减消息。

但这里有一个重要区别：

`stock_log.status=2`**&#x20;不代表 MySQL 库存已经异步扣减完成。**

当前实际过程是：

```
stock_log.status = 1
        ↓
Redis 预扣库存
        ↓
MySQL order_info 写入订单
        ↓
stock_log.status = 2
        ↓
RocketMQ 消费者扣 MySQL item_stock
        ↓
目前没有记录库存同步完成的状态
```

因此它只跟踪了前半段。

我建议区分两个状态维度：

| 对象           | 应负责的状态                |
| ------------ | --------------------- |
| `order_info` | 订单待支付、已支付、已取消等业务生命周期  |
| `stock_log`  | 库存预留、订单事务结果、库存同步和补偿进度 |

最小改造可以保留已有 `status`，新增 `sync_status`，或用独立消费记录表跟踪 MySQL 库存同步结果。

**但有状态字段不等于完整状态机。** 真正的状态机还要定义合法状态转换、转换条件，以及重复执行时的处理规则，例如 `PENDING → SYNCED` 必须由数据库条件更新保证只成功一次。

而且 `stock_log` 当前缺少与 `order_info.id` 的直接关联，无法可靠地从某条库存流水追踪到对应的具体订单。

这部分值得改造，不必推倒重写。

## **三、当前 RocketMQ 事务消息选型是否合理？**

我的结论是：**选型合理，当前实现不够可靠。**

### **1. 为什么原教程要引入事务消息？**

检查当前 `MqProducer.java`，原始思路是：

```
RocketMQ 接收 Half Message
             ↓
执行本地订单事务
    ├─ Redis 预扣库存
    ├─ MySQL 写 order_info
    └─ MySQL 更新 stock_log.status=2
             ↓
      本地事务成功？
        ├─ 是 → COMMIT 消息
        └─ 否 → ROLLBACK 消息
             ↓
消费者异步更新 MySQL item_stock
```

它想解决的问题是：

**只有本地订单事务成功，才允许下游执行数据库库存同步。**

如果订单事务已经提交，但 RocketMQ 没收到消息提交确认，Broker 还可以通过 `stock_log` 回查事务结果。

这正是 RocketMQ 事务消息的典型使用目的。官方文档也将其用于协调本地事务与下游消息处理。

[image](https://www.google.com/s2/favicons?domain=https://rocketmq.apache.org\&sz=32)

RocketMQ+1



### **2. 事务消息与状态机并不冲突**

这三个机制解决的问题不同：

| 技术            | 主要解决什么           |
| ------------- | ---------------- |
| RocketMQ 事务消息 | 本地数据库事务与消息发布的一致性 |
| 状态机           | 业务执行进度、重试、失败、补偿  |
| 消费端幂等         | MQ 重复投递时，避免重复扣库存 |

生产系统完全可以同时使用三者。

同样，**普通消息 + Transactional Outbox** 也是成熟方案：MySQL 在一个事务中写业务记录和待发送消息，再由后台任务投递。

[image](https://www.google.com/s2/favicons?domain=https://microservices.io\&sz=32)

microservices.io+1



因此没有必要把“事务消息”和“状态机 + 普通消息”划分成谁先进、谁落后。

### **3. 当前代码到底存在什么问题？**

以下是代码审查发现的实际风险，而不是假设项目已经处理好了。

| 位置                 | 具体问题                                                | 后果                   |
| ------------------ | --------------------------------------------------- | -------------------- |
| `MqConsumer`       | Redis `SETNX` 去重后，再扣 MySQL 库存                       | 标记成功后宕机，可能永久漏扣       |
| `MqConsumer`       | 不检查 MySQL 库存 UPDATE 影响行数                            | 数据库没扣成功仍可能确认消息       |
| `MqProducer`       | `executeLocalTransaction()` 只捕获 `BusinessException` | 其他异常发生时，事务结果可能无法正确上报 |
| `MqProducer`       | `UNKNOWN` 被请求接口当作失败                                 | 本地订单可能成功，但客户端误以为失败   |
| `OrderServiceImpl` | Redis 预扣不受 MySQL 事务控制                               | Redis 扣成功后宕机，可能无法回补  |
| `stock_log`        | 只记录订单本地事务结果                                         | 不能证明下游库存同步成功         |

特别是最后两项，**事务消息本身解决不了**。它不提供 Redis、MySQL、RocketMQ 三者之间的全局 ACID 事务。

### **4. 到底要不要换成普通 MQ + 状态机？**

我不建议现在替换。

两套方案都是合理选项：

- **保留 RocketMQ 事务消息**：修复本地事务结果判断、消费端数据库事务幂等、流水状态与补偿机制。适合基于现有代码深化。
- **改成普通 MQ + Outbox**：通过 MySQL 本地消息表确保订单提交与消息记录一起成功，再由 Relay 发送。更容易体现通用消息可靠性设计，但要引入投递任务和新的故障处理逻辑。

两者都需要消费幂等、重试和异常恢复。

对 Miaosha 来说，**保留事务消息并把它真正实现正确，比为了贴合某一种技术偏好而全部重写更有意义。**

但如果将来采用“Redis 先预留库存 → MQ 异步创建订单”的架构，就需要重新设计预留记录和可靠消息衔接，不能简单地把当前事务消息换成普通消息。

## **四、整个 Miaosha 项目的设计是否贴近真实生产业务？**

这是我认为最应该重新审视的部分。

当前 Miaosha 最大的问题是：**很多技术组件来自旧教程的逐章性能优化，虽然每个技术都有其作用，但串起来之后，还没有形成完整、可靠的交易系统。**

我把审查结果分成三个优先级。

### **P0：必须修复的正确性问题**

| 当前设计        | 问题与建议                                |
| ----------- | ------------------------------------ |
| Lua 库存预扣    | 保留，但补充稳定的预留标识和可恢复机制                  |
| Redis 回补    | 当前 `INCRBY` 与清理售罄标记分离，且可能重复回补；改为幂等补偿 |
| MQ 消费去重     | 从 Redis `SETNX` 改为 MySQL 事务内幂等       |
| 多种库存模式      | 当前某些开关组合可能重复扣减或错误回补，必须明确合法组合         |
| `stock_log` | 补充消费结果及订单关联，并完善状态转换                  |
| 订单重复提交      | 需要稳定请求 ID 和数据库幂等约束，避免重试产生重复订单        |

这里还有一个明确的代码缺陷：

在当前 `mysql + mq-async-sync=false` 组合下，`ItemServiceImpl.decreaseStock()` 和 `OrderServiceImpl.createOrder()` 都可能扣减 MySQL 库存。它不是合理的性能对照模式，必须修正。

### **P1：生产业务设计不完整**

| 当前实现                       | 建议                                    |
| -------------------------- | ------------------------------------- |
| `order_info` 只有订单数据，没有订单状态 | 引入订单状态和结果查询                           |
| 缺少订单取消、超时释放库存              | 至少实现一个可测试的取消补偿流程                      |
| 商品库存与售罄状态混用                | 区分活动可售库存、商品展示状态和商品上下架状态               |
| 活动重复发布直接重置 Redis 库存        | 禁止交易中重复初始化；实现活动发布的幂等与生命周期控制           |
| 库存 Key 只按 `itemId` 区分      | 明确活动库存是否独立，必要时按 `promoId + itemId` 隔离 |
| 活动状态依赖缓存                   | 下单时校验真实活动时间与状态                        |
| 商品查询使用多级缓存                 | 区分商品静态信息缓存和实时可售状态                     |

还有一个业务层面的核心区别：

**真实秒杀的订单状态不应该只有“下单成功 / 下单失败”。**

至少要考虑：

```
抢购请求
  ↓
库存预留成功
  ↓
订单创建成功
  ↓
待支付
  ├─ 支付成功 → 已支付
  └─ 超时取消 → 释放库存
```

不一定要接真实支付平台，可以模拟支付确认与超时取消。但如果要把项目定位成较完整的生产式秒杀交易系统，这部分很重要。

### **P2：工程技术和性能设计优化**

| 当前技术或方案                 | 审查结论                                         |
| ----------------------- | -------------------------------------------- |
| Spring Boot 2.0.5、JDK 8 | 版本明显老旧，建议后续迁移到受支持的 Java LTS + Spring Boot 版本 |
| MySQL 5.7               | 已过常规支持阶段，建议升级                                |
| RocketMQ 4.3.0 客户端      | 应升级并验证客户端与 Broker 的版本兼容性                     |
| Guava RateLimiter       | 可以保留，但当前固定每实例 5 QPS，不能代表真正高吞吐设计              |
| 有界线程池                   | 方向正确，但 `Future.get()` 阻塞 HTTP 请求，实际上并未做到异步响应 |
| Caffeine + Redis        | 合理，但需要缓存失效、跨实例一致性设计                          |
| 秒杀令牌与大闸                 | 可以保留，但目前令牌可重复使用、重复申请会消耗大闸计数                  |
| 安全与运维                   | 活动发布接口缺少管理鉴权，Token 放在请求参数中；应修复后才考虑对公网暴露      |
| Kafka、微服务、K8s           | 当前没有充分理由引入，先不做                               |

Spring 官方已有明确的版本支持政策，MySQL 官方也确认 5.7 从 2023 年 10 月起进入 Sustaining Support 阶段。

[image](https://www.google.com/s2/favicons?domain=https://spring.io\&sz=32)

spring.io+1



有个容易忽略的事实：当前每实例 `RateLimiter.create(5)`，意味着下单入口被限制在约每秒 5 个准入请求。**在这种配置下，即使 Redis 能承载极高并发，也无法据此证明整个系统具有高下单吞吐。**

所以性能优化必须有真实业务负载和指标支持，而不是仅凭使用 Redis、Lua、MQ 就宣称高并发。

## **五、现有 Roadmap 需要怎么调整？**

我查看了当前 [`docs/roadmap.md`](https://github.com/xxneverstop/miaosha/blob/master/docs/roadmap.md?utm_source=chatgpt.com)。

总体方向正确：先完成环境、事务可靠性、消息幂等、对账及故障验证。

但它更像是一个**能够完成基础可靠性实验的 Roadmap**，还不是完整生产式秒杀业务的 Roadmap。

目前完整请求幂等、Redis 跨进程恢复等仍列为增强项。这种划分适合控制学习项目的工作量，但如果目标是生产级可靠性，就不能把它们一直作为可选内容。

我建议调整为：

1. **第一阶段：交易正确性**

   Lua 条件扣减、MySQL 事务幂等、MQ 消费正确性、重复请求处理
2. **第二阶段：业务生命周期**

   订单状态、库存预留、超时取消、售罄状态和活动管理
3. **第三阶段：最终一致性闭环**

   事务消息、异常重试、幂等补偿、跨进程恢复、对账与告警
4. **第四阶段：生产化工程**

   技术栈升级、安全鉴权、多实例部署、配置与监控
5. **第五阶段：性能工程与可靠性验证**

   热点库存压测、瓶颈分析、故障注入、P99、吞吐与恢复指标

可以保留现有 Roadmap 的第 0～6 步执行结构，但需要把以上内容映射进去，特别是提高请求幂等、订单状态和异常恢复的优先级。

## **六、最终应该选择怎样的架构？**

我建议你继续沿用当前的**单体 Java 后端 + Redis + MySQL + RocketMQ**，不要急着拆微服务。

但必须先确定一个业务目标：

| 目标               | 推荐方向                                      |
| ---------------- | ----------------------------------------- |
| 当前项目的可靠性改造与求职展示  | **保留事务消息 + 同步创建订单 + MQ 异步同步库存**，补齐状态与异常恢复 |
| 进一步研究极高峰值的异步秒杀架构 | Redis 原子预留 → 可靠入队 → 异步创建订单 → 状态查询与补偿      |

这两种都是成立的设计。区别在于是否让 HTTP 请求等待 MySQL 创建订单完成。

对于目前的 Miaosha，我更推荐第一种，先把一条链路真正做正确、做可靠、做出可复现的性能证据。

**最终总结：**

你不需要因为一次交流就推翻 Lua 和事务消息。这两项技术本身并没有选错。

真正需要改变的是项目设计思路：

从旧教程的 **“逐个引入缓存、限流、线程池、MQ 来提高性能”**，转向 **“先定义清楚秒杀业务和数据状态，再选择技术实现，并验证故障情况下能否恢复正确结果”**。

## **二、v2 最值得修改的三个地方**

### **1. Redis 预扣与 RocketMQ 事务消息的先后顺序**

这是我认为最重要的问题。

v2 在「最终必须能演示的完整故事」中设计：

```
Redis Lua 库存预留
         ↓
RocketMQ 事务消息
         ↓
MySQL 创建订单
```

但当前代码实际上是：

```
创建 stock_log
         ↓
发送 RocketMQ Half Message
         ↓
执行本地事务
    ├─ Redis Lua 预扣
    └─ MySQL 写入 order_info
         ↓
提交 RocketMQ 消息
```

**v2 改变了执行顺序，却没有充分解释为什么改。**

如果先 Redis 预扣，然后程序在发送 Half Message 前宕机：

```
Redis 库存已经减少
MySQL 没有订单
RocketMQ 没有消息
```

此时只能依靠预留流水和恢复任务处理。

这并非不能实现，但它意味着引入了新的可靠性责任。

**建议：先明确完整交易时序、事务边界和崩溃恢复协议，再确定是否改变原有执行顺序。** 不要把改变顺序当成默认优化。

### **2. 状态机应当区分不同对象的状态**

v2 提出的：

`RESERVED → ORDER_COMMITTED → DB_SYNCED`

基本合理，但 `COMPENSATED` 和 `UNKNOWN` 不应该简单地当作同一条线上的后续状态。

建议至少区分：

| 对象                | 管理什么             |
| ----------------- | ---------------- |
| Redis Reservation | 是否预留、确认、释放库存     |
| `stock_log`       | 库存操作与本地交易结果、关联编号 |
| `order_info`      | 订单的业务生命周期        |
| MySQL 消费记录        | 是否已执行数据库库存扣减     |
| 对账结果              | 正常、异常、状态未知、待人工核查 |

尤其是 **UNKNOWN 更适合作为核查结论，而不是一个可随意进入或退出的业务终态**。

真正实现时，还要为状态转换设置条件更新与幂等约束。

### **3. 业务闭环还不够完整**

v2 已经包含请求幂等、一人一单、一次性令牌、库存预留和补偿，这是非常值得保留的。

但是还应明确：

**订单创建成功后，到底如何完成或者结束？**

目前主要围绕“创建订单 → 扣减库存”设计。

对于更接近真实电商的系统，可以加入一个最小订单生命周期：

```
抢购成功
   ↓
创建待支付订单
   ├─ 模拟支付成功 → 订单确认
   └─ 超时未支付 → 取消订单
                         ↓
                    幂等释放库存
```

不需要接真实支付平台，但要能验证取消、释放库存、重复取消和支付取消竞争。

否则库存补偿主要覆盖技术异常，缺少正常业务取消场景。

## **一、当前代码和 v2 的执行顺序，哪个更优？**

**对于 Miaosha 当前使用 RocketMQ 事务消息的架构，我更推荐原有顺序。** 但两者都存在需要处理的故障窗口。

方案 A：当前代码

MySQL 初始化 stock_log

MQ Half Message

Redis Lua 预扣

MySQL 创建订单

COMMIT MQ

消费端扣 DB 库存

方案 B：v2 目标链路

Redis Lua 预扣

记录 Redis 预留

MQ Half Message

MySQL 创建订单

COMMIT MQ

消费端扣 DB 库存

简化主流程。v2 尚未给出完整时序，这里按其文档描述理解。

### **两种方案的取舍**

| 维度          | 方案 A：Half Message 先行     | 方案 B：Redis 预扣先行         |
| ----------- | ------------------------ | ----------------------- |
| MQ 与订单事务协调  | 更自然，符合 RocketMQ 事务消息执行模型 | 也可以，但 Redis 预扣发生在消息事务之外 |
| 高峰期削减 MQ 流量 | 需要额外的 Redis 快速预检查        | 更好，库存不足的请求不用发送 MQ       |
| 预扣后宕机       | 仍可能遗留 Redis 预扣           | 也可能，但 v2 设计了 Redis 预留流水 |
| 故障恢复        | 依赖订单流水、预留记录和回查           | 同样依赖预留流水、超时扫描和补偿        |
| 与当前代码契合程度   | 高                        | 需要调整交易时序                |

RocketMQ 官方事务消息的标准模型就是：先发送 Half Message，再执行本地事务，最后提交或回滚消息。

[image](https://www.google.com/s2/favicons?domain=https://rocketmq.apache.org\&sz=32)

RocketMQ+1



**但需要纠正一个容易产生的误解：**

Half Message 先发送，并不意味着后续 Redis 预扣就天然安全。

例如：

```
Half Message 已发送
        ↓
Redis 已扣库存
        ↓
服务突然宕机
        ↓
MySQL 订单事务未提交
        ↓
Redis 库存仍然减少
```

RocketMQ 回查可以判断数据库本地事务的结果，但不能自动恢复 Redis 库存。

所以 A 的优势是更贴合事务消息的协调模型，**不是天然具备比 B 更强的跨 Redis/MySQL 一致性**。

### **我推荐的最终顺序**

```
1. Redis 快速准入检查
   （无库存、无资格直接拒绝）
              ↓
2. 初始化可靠的请求/库存流水
              ↓
3. 发送 RocketMQ Half Message
              ↓
4. 执行本地交易流程
   ├─ Redis Lua 原子预留并记录 reservationId
   └─ MySQL 写 order_info、更新 stock_log
              ↓
5. 根据 MySQL 本地事务结果提交/回滚 MQ
              ↓
6. Consumer 在 MySQL 事务内幂等扣库存
              ↓
7. 状态查询、对账、异常补偿
```

这里第 1 步只是快速预检查，最终能否抢到仍由第 4 步的 Lua 决定。

这个方案兼顾了当前架构、事务消息和流量过滤。但必须把 Redis 预留记录、请求流水、MySQL 事务的失败状态与补偿规则设计完整。

**因此不建议直接按照 v2 改动交易顺序，应先把原有顺序写成明确的目标时序。**

## **二、状态机应该如何理解？Miaosha 需要做到什么程度？**

不用把状态机理解成某个复杂的框架。

**状态机就是给一笔业务规定：当前处于什么状态，接下来允许变成什么状态，以及什么条件才能改变。**

例如 `stock_log` 中一笔 S001：

**PENDING**

等待执行订单事务

**ORDER_COMMITTED**

MySQL 订单已提交

**DB_SYNCED**

数据库库存同步完成

**ORDER_FAILED**

订单事务明确失败

**COMPENSATED**

对应预留已安全回补

这只是简化示意；Redis 预留状态与 MySQL 库存同步状态实际应分开记录。

它相比单纯的状态字段，多了三个关键约束：

- **合法转换**：例如已确认的 `DB_SYNCED` 不应被普通重试改回 `PENDING`。
- **并发裁决**：补偿和成功确认同时发生时，只能有一方取得合法转换权。
- **可恢复性**：宕机后能够根据持久化证据判断应该继续执行、补偿还是标记待核查。

举个简单例子，MySQL 可以通过：

```
UPDATE stock_log
SET status = 2
WHERE stock_log_id = 'S001'
  AND status = 1;
```

利用影响行数判断状态是否成功改变。

但状态更新成功并不代表所有副作用都成功，因此还必须结合数据库事务、Redis 预留与幂等记录。

### **我建议 Miaosha 怎么做？**

**不要现在引入 Spring StateMachine 或独立状态机框架。**

保留 `stock_log`，明确它的事务状态；增加库存同步状态或独立消费流水；Redis Reservation 负责预留及补偿幂等。

这已经足够展示状态机、数据库事务、并发控制、消息重试与最终一致性能力。

## **三、是否有必要增加最小订单生命周期？**

结合你的整个项目目标，我改变之前的建议：

**不建议将支付成功、支付超时、取消订单等完整业务生命周期列为 Roadmap 必做项。**

原因很直接：

| 工作             | 对当前项目的收益           |
| -------------- | ------------------ |
| MQ 消费幂等与事务恢复   | 高，Java 后端核心能力      |
| Redis 库存预留与补偿  | 高，分布式一致性           |
| 状态机与并发裁决       | 高，可回答深入面试问题        |
| 故障注入和压测        | 高，可形成可信工程成果        |
| 模拟支付、支付超时、取消订单 | 中等，需要额外引入业务语义和状态竞争 |
| 更多商品、购物车、营销功能  | 低，容易偏离项目主线         |

虽然真实电商存在取消订单和释放库存，但你并不是要开发一个完整电商平台。

对于 Miaosha，更值得做的是：

**让创建订单失败后的 Redis 库存预留能够可靠、幂等地恢复。**

这已经包含状态转换、超时处理、并发竞争和最终一致性等核心问题。

不需要通过引入支付系统才能体现这些能力。

未来如果需要扩展，可以设计支付超时释放库存作为进阶场景，但当前没有必要。
