## 0. 项目定位与完成定义

### 一句话定位

**Miaosha 是一个基于现代 Java/Spring Boot 的高并发秒杀交易系统：在突发流量下实现准入与库存预扣，借助 RocketMQ 协调订单和库存同步，并通过事务幂等、补偿对账、可观测性及可复现测试保证可解释的可靠性。**

不是“把所有热门中间件装一遍”，也不是从头重写点评类业务系统。保留现有项目积累，聚焦以下四类可面试的工程能力：

1. **交易正确性**：Spring 事务、Redis Lua、MySQL 条件更新、MQ 重投与消费幂等、请求幂等。
2. **分布式可靠性**：库存预留、可重入补偿、状态回查、故障恢复、对账和未知状态处置。
3. **性能工程**：限流、削峰、多级缓存、热点行分析、同步/异步方案对照与负载下正确性。
4. **交付工程**：现代依赖、隔离环境、数据库迁移、测试金字塔、CI、监控和可复现部署。

### 最终必须能演示的完整故事

```text
用户获取一次性资格令牌
          ↓
Redis 分布式限流 / 活动校验
          ↓
Redis Lua 原子检查库存、购买资格、写预留流水
          ↓
RocketMQ 事务消息 + Spring 数据库事务写入订单
          ↓
消费端：同一数据库事务内“幂等裁决 + 扣 DB 库存”
          ↓
订单与库存状态查询 / 收敛对账 / 安全补偿
          ↓
有指标、有故障测试、有压测证据
```

> 上述是**目标链路**，不是当前代码现状。保留当前“订单同步创建、库存异步同步”的基本架构；不为了制造异步下单亮点而改变业务语义。Redis 预留与 MQ/数据库的跨资源边界仍须保守设计，不能宣称天然强一致或无条件 exactly-once。

### 基础完成门槛（全部完成才算可写成成熟项目）

- [ ] 从干净环境按文档启动完整依赖，真实下单及查询正常；SQL 迁移与数据隔离可重复执行。
- [ ] 订单数据库事务、MQ 消费幂等、库存行数检查、补偿重复执行全部有自动化测试。
- [ ] 同一业务请求的重试不会产生第二笔有效订单；一人一单规则仅作用于秒杀活动，数据库有最终约束。
- [ ] Redis 库存预扣有流水关联；**已确认失败**的预留可安全重试补偿；证据不足的状态输出 UNKNOWN/人工核查，不能盲目加库存。
- [ ] 对账能区分在途、成功、失败、未知；有真实故障注入并保存恢复/未恢复结果。
- [ ] 已完成选定的现代化版本迁移，或明确记录兼容性阻塞与实际可运行的过渡版本；不能把未升级的依赖写成新版本。
- [ ] 自动构建、集成测试、迁移验证以及可复现的压测报告齐备。
- [ ] README、架构图、设计取舍和至少 3 个“问题→方案→验证→边界”的面试故事与代码一致。

## 1. 当前源码基线：已有功能 vs 已知缺口

| 范围 | 已有的代码基础 | 需要做的工作 |
|---|---|---|
| 秒杀准入 | 图形验证码、用户登录令牌、活动令牌、大闸、Guava 限流、有界线程池 | 令牌一次性消费、分布式限流、并发拒绝与重复申请语义 |
| 库存 | MySQL / Redis INCR / Redis Lua 三种对照模式，Lua 防负库存 | 收敛为受支持模式；Redis 原子预留流水、补偿幂等、售罄标记一致性 |
| 订单事务 | `createOrder()` 当前已有 `@Transactional(rollbackFor = Exception.class)` | **验证而非重复添加注解**；回滚/提交时序、行数断言、订单号压力验证 |
| RocketMQ | 事务消息、本地事务回查、异步消费者 | Producer 异常/UNKNOWN 处理；Consumer 的 Redis 去重与 DB 扣减并不原子 |
| 对账与恢复 | `stock_log`、回滚后 Redis 回补日志 | 逐笔关联、状态核查、已确认失败的可重入补偿；未知状态保留证据 |
| 测试 | 离线配置测试、部署脚本自检、历史 JMeter 资料 | 真实 MySQL/Redis/MQ 集成测试、故障注入、可复现对照实验 |
| 工程 | Maven 单模块、Docker 脚本、有限 Compose、配置模板 | 完整开发环境、健康检查、数据库版本迁移、CI 与监控 |
| 依赖 | Java 8 / Spring Boot 2.0.5 / MySQL 5.7 / Redis 5 / MQ Client 4.3 | 分阶段现代化，不与交易语义改造混成一个大提交 |

**确认过的具体问题**

- `MqConsumer` 先执行 Redis `setIfAbsent`，随后独立执行 MySQL `decreaseStock`；若扣减失败但去重已生效，重投可能跳过处理。
- `MqProducer` 将部分不确定发送或本地事务状态折叠为 `false`；`executeLocalTransaction` 主要捕获业务异常，需检查其他异常和回查收敛。
- `PromoServiceImpl` 发布活动会直接覆盖 Redis 库存，令牌可重复申请/使用，仍缺少受控重置与请求最终幂等。
- `OrderServiceImpl` 的 Redis 回补是数据库回滚后的本线程重试；如果库存已增加但后续清理失败或响应未知，盲重试有重复回补风险。
- 历史压测指标不等于当前版本的真实性能；当前 `RateLimiter.create(5)` 是每实例固定 5 个许可/秒，压测时必须显式处理这个限制。

上述结论是静态代码审阅结果；后续阶段以自动化测试、真实依赖运行和版本提交补齐证据。

## 2. 技术栈决策：必要升级、值得引入、不引入

### 2.1 版本与组件选择

| 分类 | 旧基线 | 决策 | 原因和迁移边界 |
|---|---|---|---|
| Java | 8 | **目标 Java 21 LTS** | 现代语言/JVM/工具链；先测现有依赖和编译器插件 |
| Spring Boot | 2.0.5 | **分步迁移，目标评估 4.1.x 稳定补丁版** | 建议 2.7 → 3.5 作为迁移检查点，再评估 4.1；要验证 Jakarta、Jackson、自动配置及第三方兼容。若 4.1 的 MQ/相关依赖阻塞，3.5 只作为有记录的过渡版本，不长期宣称“最新受支持” |
| MyBatis | 老 Starter 1.3.1 | **继续使用 MyBatis**；选与 Boot 匹配的 Starter | 无需为了技术栈名称改用 MyBatis-Plus。Boot 3.x 对应 MyBatis Starter 3.x，Boot 4.x 对应 4.x，具体锁定兼容补丁 |
| MySQL | 5.7 | **8.4 LTS** | 旧版本已经结束常规支持；核查驱动、SQL 方言、字符集、时间/排序规则、认证方式 |
| MySQL 驱动/连接池 | Connector/J 5.1、Druid 1.1 | **新版 MySQL Connector/J + HikariCP** | 沿用 Boot 默认连接池；除非有可解释理由保留 Druid |
| Redis | 5.0 | **7.4 系列固定补丁版本** | 不引入 Cluster；验证 Lua、序列化、持久化与恢复 |
| RocketMQ | Client 4.3、Broker 4.9.4 | **保留 MQ，逐项升级** | 先修业务正确性；核实新版客户端、Spring Boot、Broker 及事务消息 API 的兼容组合；不得只改 Broker 镜像或 Starter 版本就声称迁移完成 |
| 本地缓存 | Caffeine 2.x | **保留并按 Boot 依赖管理更新** | 热点读优化与 L1/L2 缓存策略有直接价值 |
| 序列化/时间 | Fastjson 1.x、Joda-Time | **逐步改 Jackson、`java.time`** | 安全性、可维护性和 Boot 迁移兼容性；做字段/日期序列化回归 |
| 测试 | JUnit 4，几乎无业务集成测试 | **JUnit 5 + Testcontainers + MockMvc + JaCoCo** | 用真实依赖证明事务、MQ 和 Lua 行为；覆盖率只作为信号，不以百分比替代断言 |
| SQL 变更 | 手动初始化 SQL | **Flyway** | 版本化增量迁移、可重建数据；原 `DROP TABLE` SQL 只在隔离初始化场景使用 |
| 指标 | 业务日志为主 | **Actuator + Micrometer（可接 Prometheus/Grafana）** | 事务成功率、限流、补偿、库存差额和 P95/P99 可观测；资源不足先实现指标端点与保存快照 |
| 交付 | Docker 脚本、部分 Compose | **完整测试 Compose + GitHub Actions** | 健康检查、数据卷、独立配置、测试工件和基础发布/回退 |

> 版本号不是一次性变更指令。迁移启动时查询官方支持矩阵，固定实际补丁版本和镜像摘要，记录依赖清单及 CVE 审查。**不要在同一个 PR 同时重写交易逻辑、升级 Boot 和替换 MQ 客户端**。

### 2.2 新技术选型取舍

| 技术/能力 | 结论 | 具体理由 |
|---|---|---|
| **RocketMQ 事务消息 + 消费幂等** | **主线必做** | 现有基础最贴近交易可靠性，能深入解释故障窗口 |
| **Testcontainers、Flyway、GitHub Actions** | **必做** | 体现真实可重复的工程质量；比新增一个大中间件更有价值 |
| **Redis 分布式限流** | **必做（最小版）** | 当前 Guava 限流是每实例局部控制；实现活动/IP 或用户维度配额，作为对照实验 |
| **库存预留 + 对账 + 幂等补偿** | **必做（有边界的完整闭环）** | 把“只有 Redis 扣减”升级为有依据的状态机和恢复策略 |
| **Kafka** | **不引入** | 与 RocketMQ 重复；学习 Kafka 可以做独立实验，不把两套 MQ 堆在同一交易项目 |
| **分库分表、ShardingSphere** | **暂不引入** | 未有真实容量瓶颈；先用单库热点行、索引和锁等待数据判断 |
| **Spring Cloud、Nacos、Sentinel、K8s** | **暂不引入** | 不是解决本项目核心痛点的最低成本方案 |
| **Outbox** | **可选架构对比，不作为必做的第二套可靠投递** | 既有 RocketMQ 事务消息先实现可靠；若要引入 Outbox，必须明确替代/比较的失败模型和演示收益 |
| **双实例部署** | **推荐加分项** | 比微服务拆分更有价值，可验证分布式限流、幂等和缓存失效问题 |
| **Redis Cluster、MQ 集群** | **后置** | 单机资源与维护负担不匹配，基础可靠性不依赖搭集群 |

## 3. 执行顺序与阶段门槛

```text
S0  固定源码基线、环境、核心测试入口
       ↓
S1  修事务与 MQ 消费正确性
       ↓
S2  业务边界：一次性令牌、请求幂等、一人一单
       ↓
S3  库存预留、可信对账与可重入补偿
       ↓
S4  Java / Boot / MySQL / Redis / MQ 分阶段现代化
       ↓
S5  分布式限流、监控与基准性能优化
       ↓
S6  故障注入、隔离压测、部署与 CI 验收
       ↓
S7  README / 证据包 / 简历与面试
```

**工作规则**：每一阶段先设计测试、再做最小改动、最后留下运行证据；阶段结束先冻结可运行基线，不把未完成工作混到下一阶段。最小 CI 从 S0 开始并贯穿后续阶段，非等到 S6 才做。S4 的数据库升级可先在独立测试环境试验，但正式切换不与 S1–S3 业务修改合并。

### S0 — 环境与回归基线（P0）

**目标**：得到一套任何人可重复运行的真实环境，先证明旧链路现状。

实施：

1. 确认当前 Git HEAD、本地未提交改动、JDK 8/Maven、Docker Engine、CPU/内存和数据归属；备份现有配置，**不使用 `git reset` 清理工作区**。
2. 复用现有 Docker 脚本；补充一套专用于开发/测试的完整 Compose（App、MySQL、Redis、RocketMQ，Nginx 可选），依赖需健康检查、容器间地址可达、必要数据卷持久化。
3. 将环境变量与密钥隔离；开发库、CI 库和压测库不得共享，初始化脚本只能重置专用测试库。
4. 打通注册/登录、活动预热、获取令牌、真实下单、核对订单与库存的自动冒烟脚本。
5. 创建最小 GitHub Actions：编译、已有单测、无密钥工件；引入 JUnit 5/Testcontainers 的准备可以提前，但不要一次重写所有测试。

**交付物**：`docs/development.md`、完整测试 Compose、`.env.example`、`scripts/smoke-*`、最小 CI、`docs/evidence/S0/`。

**验收**：从干净隔离数据启动并执行一笔真实下单；日志能关联 `stockLogId` 和订单；数据重启/重建符合预期；文档明确什么数据允许清除。

### S1 — 交易与消息的正确性（P0）

**目标**：保证“数据库事务整体回滚”和“MQ 重投不会多扣或漏扣”。

实施：

1. 对已有 `@Transactional(rollbackFor = Exception.class)` 编写业务异常/运行时异常回滚测试，包括订单、销量、流水及同步 DB 扣减分支；核实代理边界和事务提交状态。
2. 将 Consumer 的**数据库消费流水（`stockLogId` 唯一）+ DB 库存条件扣减**放入同一 MySQL 事务，通过独立 Spring 事务 Bean 调用；写入成功才确认 MQ 消费。数据库 0 行更新必须明确进入错误处理，不伪装成功。
3. 核查 Producer 在业务异常、运行时异常、网络不确定、事务回查中的状态转换；区分 `COMMIT`、`ROLLBACK`、`UNKNOWN`，不能把未知直接等同于失败或已取消。
4. 给库存扣减/回补方式建立矩阵；只允许经过验证的组合启动：`mysql + sync`、`lua + sync`、`lua + async`。Redis INCR 模式仅在专项实验中保留。每种模式说明真实扣减点、MQ 是否启动和回补责任。
5. 修当前回补的重复执行风险：一次库存回补与售罄标记清理要原子、可重入；响应未知后禁止无凭据盲加。订单号生成器验证唯一性、顺序锁和长度上限，证实瓶颈后再改。

**重点源码**：`OrderServiceImpl`、`MqProducer`、`MqConsumer`、`ItemServiceImpl`、相关 Mapper、数据库增量迁移。

**验收**：

- [ ] 同一个 `stockLogId` 重投 100 次，DB 最终只扣一次；重启消费者仍成立。
- [ ] 消费去重写入后故障、库存修改后故障，整笔 DB 事务回滚，重试成功。
- [ ] Spring 业务异常导致订单、销量、流水一致回滚；RocketMQ 状态可复查。
- [ ] Redis 回补重复调用、响应未知、局部失败时，不会重复加库存。
- [ ] 所有合法模式遵循库存变化不变量；非法模式启动失败并给出错误原因。

### S2 — 请求幂等和购买业务规则（P0）

**目标**：对外提供清晰的下单语义，区分“用户重复购买”和“同一请求重试”。

实施：

1. **请求幂等**：定义客户端稳定 `requestId`，建立 `requestId → stockLogId → orderId/状态` 关联。DB 唯一约束作为最终裁决；重试返回已完成结果或可查询状态，不允许把请求超时直接当下单失败。
2. **一人一单**：定义同用户同活动仅有一笔有效秒杀订单的规则。Redis Lua 在准入阶段快速判断，数据库唯一键/约束作最终保护；普通商品订单不被误限制。明确失败、取消及退款是否释放购买资格；本期只实现已建模的订单状态，不虚构完整支付域。
3. **一次性资格令牌**：令牌校验与消费使用原子操作；重复获取、消费后网络超时、限流拒绝后的令牌归属必须明确。不能让一次性令牌阻断对**同一 `requestId` 的结果查询/安全重试**。
4. **活动状态与库存预热**：直接使用实时活动时间判定；禁止交易中重复发布覆盖 Redis 库存。活动初始化引入受控幂等/冻结条件。
5. 如当前同步下单没有可靠订单结果查询，新增最小只读查询 API；不能把“已接受”与“已创建订单”混为一个状态。

**验收**：

- [ ] 同一请求并发重放/超时后重试不会生成第二笔有效订单；结果可查询。
- [ ] 同一用户不同 `requestId` 重复抢同一活动，只能成功一笔。
- [ ] 不同用户正确竞争库存，库存不足不会写有效订单。
- [ ] 正在进行的活动拒绝危险的预热重置；开始/结束边界测试通过。

### S3 — 库存预留、对账与有边界的故障恢复（P0）

**目标**：不止“发现不一致”，而是**能可靠恢复已确认失败的交易**，并明确未知状态处理。

实施：

1. 建立最小状态模型：`RESERVED / ORDER_COMMITTED / DB_SYNCED / COMPENSATED / UNKNOWN`。与现有 `stock_log` 状态和 MQ 事务状态保持明确映射；不得混用“订单提交”和“库存已同步”。
2. 在一次 Redis Lua 中完成：校验、预扣、登记稳定的预留流水（关联 `stockLogId/requestId`）；使用稳定 ID 与原子状态更新让重复执行能够识别原动作。设定保留期限，清楚说明 Redis 丢失数据时无法凭空恢复全部历史。
3. 使用 MySQL 订单、消费记录和活动/库存基线作为最终核查依据。对已确认回滚的预留执行幂等补偿；补偿与迟到提交存在竞争时，以持久化裁决/条件更新防止“已成功却回补”。
4. 实现最小对账任务或管理命令：识别 `PENDING` 超时、缺失 DB 同步、已确认失败未补偿、Redis/DB 聚合差额。只读核查优先；只有证据充分且规则明确的状态才自动处置。
5. 缺少订单、消息延迟、Redis Key 过期均不单独构成“可补偿”的证明；保留 `UNKNOWN` 清单、事件日志与人工恢复步骤。不要直接 `SET Redis库存 = MySQL库存`。

**验收**：

- [ ] 预扣后 DB 明确回滚 → 自动/重复补偿只生效一次。
- [ ] 补偿与提交并发竞争，不出现“成功订单对应库存被加回”。
- [ ] DB 库存同步延迟与失败可以被识别、重试或标记待处理。
- [ ] 故障后可列出单笔流水、订单/库存状态和处理依据；未知项不被误修。
- [ ] 在停止入口、等待事务及消息收敛后，无取消/补货的隔离轮次满足：

```text
初始 Redis 库存 - 结束 Redis 库存
  = 初始 MySQL 库存 - 结束 MySQL 库存
  = 本轮成功提交的订单购买数量 SUM(amount)
```

> 该等式仅适用对应 Redis 预扣模式、相同测试窗口、无补货/取消且已收敛的活动；普通 MySQL 模式不套用。**不承诺 Redis 丢失全部持久化数据或脑裂场景下自动无损恢复**。

### S4 — 技术栈现代化（P0，独立迁移分支）

**目标**：让项目具备现代 Java 技术栈基础，同时不牺牲已验证的交易语义。

推荐顺序：

1. **数据库单独升级**：用新 MySQL 8.4 测试库迁移 SQL/驱动，验证表结构、索引、字符集、日期、连接配置、账户权限；先备份再切换，Flyway 接管增量变更。
2. **Java/Spring 分步升级**：完成旧版回归基线 → Java 21 编译环境准备 → Spring Boot 2.7 兼容整理 → Boot 3.5 过渡验证 → 在兼容性可控时迁到 Boot 4.1.x。迁移同时修 `javax.*`→`jakarta.*`、Jakarta Validation、Jackson/序列化、Servlet、配置、Mapper 等。
3. **依赖去旧**：尽量删除已不必要的 Joda-Time、Fastjson 1.x、Druid 老版本；使用 `java.time`、Jackson、HikariCP。对 JSON、时间、金额精度和 Redis 序列化做兼容回归，避免损坏现有库存 Key。
4. **Redis 和 RocketMQ 升级**：先固定/验证 Redis 7.4 镜像；再选择兼容的 MQ 客户端与 Broker 组合验证事务半消息、回查、重投、消费确认、重启恢复。对有风险的 MQ API 更换单独提交，不与 Boot 主迁移一起开展。
5. 迁移后执行 S1–S3 的完整集成回归、压测基线复跑和依赖漏洞扫描。

**升级决策门槛**：如果 Boot 4.1 与必要 MQ 组件存在不可接受的兼容风险，先保留**实际已验证的 Boot 3.5 过渡版本**，记录不满足长期 OSS 支持目标的技术债和独立升级任务；不要通过跳过测试宣布成功。Boot 4.2 刚发布，不把“追新版本号”作为独立收益。

**验收**：从干净环境通过迁移、启动、真实下单、事务消息回查、重复消费及补偿测试；能给出旧/新环境对照、迁移记录和依赖树。

### S5 — 可观测性、限流与性能工程（P1，但对最终项目必做）

实施：

1. 将本地固定 `5 QPS` Guava 限流改成可配置参数，保留为单实例对照；新增 **Redis Lua 分布式令牌桶或滑动窗口的一种**，明确活动/用户/IP 维度、突发容量、拒绝语义和降级策略。不要两种算法都做成“必选功能”。
2. 保留 Caffeine + Redis 两级读缓存，但补齐空值缓存、热点缓存重建保护和更新失效策略中**能用实际读压测证明有收益**的部分；不以引入布隆过滤器作为必达门槛。
3. 新增 Actuator/Micrometer 指标：业务下单成功/失败分类、令牌发放/限流、库存预扣及回补、事务 MQ 状态、消费重试与积压、对账差额、数据库连接池、JVM/GC、接口 P95/P99。日志统一 `requestId/stockLogId/orderId`；指标标签不能包含高基数的用户 ID、订单 ID。
4. 如果部署资源允许，用 Prometheus/Grafana 做一张交易链路仪表盘；资源不足时保留 `/actuator/prometheus` 采样和可复现的统计脚本，不在单台小服务器上硬堆监控集群。
5. 性能优化必须先找瓶颈：库存热点行、订单号序列锁、线程池排队、DB 连接池、MQ lag、Redis RTT；只优化测得存在的瓶颈。

**验收**：分布式限流双实例下仍保持预定全局配额；过载拒绝率和成功量独立统计；至少一次优化具有前后版本、相同条件、原始指标的对照证据。

### S6 — 可靠性实验、压测与交付验收（P0）

**正确性实验矩阵**（至少覆盖）：

| 场景 | 必须断言 |
|---|---|
| 订单插入后业务异常、运行时异常 | MySQL 订单/销量/流水按事务回滚，Redis 补偿按裁决执行 |
| 相同 MQ 消息连续重投 100 次 | DB 库存只减一次，数据库消费记录唯一 |
| 去重插入后、库存修改前/后故障 | 同一 DB 事务回滚，重试后正确落地 |
| MQ Broker/Consumer 暂不可用 | 订单与 DB 库存不同步状态可识别，恢复后收敛或明确待核查 |
| Redis 已预扣，进程突然退出 | 保留可检查状态；已确认失败的补偿有效，无法裁决则 UNKNOWN |
| 补偿请求重复/响应丢失 | 不会重复增加库存 |
| 同一 `requestId` 并发与超时重试 | 不重复落单，能查询稳定结果 |
| 令牌多次使用、活动重复发布 | 不重复放行、不覆盖在途库存 |

**性能实验矩阵**：

- A：`mysql + sync`；B：`lua + sync`；C：`lua + async`。A/B 比较预扣策略，B/C 比较库存同步位置，严格记录两组是否走 MQ 事务流程。不可比时不得写“Lua 提速 X 倍”。
- 每组做**库存充足/独立有效用户的容量测试**和**少库存/突发流量的过载测试**。固定测试环境、流量、活动、连接池、限流、代码版本。
- 记录 `HTTP QPS`、**业务成功订单 TPS**、售罄/限流/错误占比、P50/P95/P99、CPU/内存/GC、数据库锁等待、Redis 延迟、MQ lag/收敛时长。
- 统计窗口结束后等待消息收敛再核对订单、Redis/DB 库存及异常清单；**只达到高 HTTP QPS 但大量拒绝、库存错误或积压无法收敛不算成功**。
- 历史 `142 → 1200 QPS` 仅作为待复核的旧记录，报告里不得无版本依据沿用。

**交付与环境**：

- `benchmarks/` 保存 JMeter `.jmx`、测试数据准备/隔离重置、核对脚本、结果 `.jtl`、环境快照、图表生成方法。
- GitHub Actions 执行单测、数据库集成测试与构建；大规模压测单独手动触发，不打共享/生产资源。
- Docker Compose 测试环境可独立启动。云上有条件时演示单实例部署、日志查看、App 镜像回退以及数据库迁移前备份；双实例为加分项，不把 Kubernetes 作为验收要求。

**验收**：每个性能结论都能追溯到 Git 提交、负载脚本、机器规格、原始数据与库存核验；所有可靠性故障要标注 `PASS / FAIL / UNKNOWN`，不把“检测到错误”当作“已修复错误”。

### S7 — 形成简历与可讲述的工程成果（P0）

交付：

- 根 `README.md`：一句话项目定位、架构图、快速启动、核心技术点、可复现实验入口、能力边界。
- `docs/architecture.md`：一次请求的主流程与失败分支、数据事实源和状态机简图。

建议优先准备 3 条简历故事：

1. **分布式交易可靠性**：修复 MQ 消费端非原子幂等与事务异常路径，证明重复投递只生效一次。
2. **库存一致性与故障恢复**：用 Lua 预留流水、幂等补偿与对账处理真实故障窗口，报告可恢复与未知边界。
3. **高并发性能工程**：对照 MySQL/Redis Lua、同步/异步库存同步和分布式限流，量化吞吐、尾延迟、拒绝率与收敛时间。

不把“用了 Kafka、做了分库分表、支持百万 TPS”等没有源码和实验支撑的内容写进简历。

### 约束与优先级

1. **先正确，再升级，再优化**。任何性能优化都不能破坏 S1–S3 的正确性测试。
2. **不同时大规模引入两个同类系统**。保留 RocketMQ，就不再为展示技术栈而引 Kafka；保留 MyBatis，就不为了“更现代”而改写 ORM。
3. **单体不是缺点**。保持 Maven 单模块或少量必要模块；只有真实模块边界和复用需要时才拆分，禁止为了“微服务”而微服务。
4. **高并发不等于高 QPS 截图**。业务成功率、P99、最终库存状态、消息积压收敛同样是指标。
5. **避免扩大业务范围**。支付、物流、优惠券榜单、候补通知、复杂管理后台不是本路线核心。
6. **硬件约束优先**。本地跑依赖与测试，已有小型云主机做可复现部署；复杂集群和大型观测平台不作为完成门槛。
7. **每项新能力必须闭环**：设计文档、源码、测试、执行结果、已知边界；缺一项不能写“已完成”。

## 5. 现在从哪里开始

**当前最优先不是改 Spring Boot 大版本，也不是引 Kafka。** 按以下次序推进：

1. 确认当前 `master` 与本地未提交变更，复用环境脚本跑通一次真实下单；把当前缺陷固定成失败回归测试。
2. 先修 **Consumer 数据库事务内幂等**、MQ 未知状态处理和 Redis 幂等回补；在 S1 验收前，不做性能优化。
3. 完成请求/购买双重幂等、库存预留和最小对账恢复，让业务语义达到可以验证的稳定状态。
4. 对现代化依赖创建独立迁移分支，先从 MySQL 8.4 与 Java/Spring 的兼容试验开始，完成之后用同一套测试回归。
5. 最后对限流、缓存及 MQ 同步策略做可信压测，输出能直接引用到简历和面试中的结果。

**最终判断标准不是“项目用了多少高级框架”，而是“在压力、失败、重试、重启和升级之后，交易为什么仍然正确，证据在哪里”。**
