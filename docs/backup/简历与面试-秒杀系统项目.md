## 一、多级缓存（本地缓存 → Redis → MySQL）

**描述**：设计三级缓存查询链路。商品详情优先命中 JVM 本地缓存（Caffeine，100 条容量、LRU 淘汰、60 秒 TTL），未命中查询 Redis 分布式缓存（10 分钟 TTL），最后回源 MySQL。查询顺序由近到远，任一命中即回填上层缓存。

**效果**：接口响应时间从直接查库的 ~50ms 降至本地缓存命中的 ~1ms，缓存命中率 95%+，数据库读压力降低约 20 倍。

---

## 二、Redis 缓存库存 + 原子扣减，消除数据库行锁瓶颈

**描述**：将秒杀库存从 MySQL 行锁方案改造为 Redis 预热 + INCR 原子扣减。活动发布时将库存同步到 Redis（key=`promo_item_stock_{id}`），扣减时用 `INCR -N` 原子操作，利用 Redis 单线程模型天然无锁竞争。返回值 >0 成功、=0 触发售罄标记、<0 触发库存回补。

**效果**：单商品库存扣减 TPS 从 ~500（MySQL 行锁串行）提升至 50000+（Redis 内存原子），提升约 100 倍，彻底消除数据库行锁瓶颈。

---

## 三、RocketMQ 事务消息 + 库存流水表，保证 Redis 与 MySQL 最终一致性

**描述**：引入 RocketMQ 事务消息解决 Redis 扣库存与 MySQL 落单的分布式一致性问题。核心流程：先发半消息（消费者不可见）→ 执行本地事务（Redis 扣库存 + 插入订单 + 更新 stock_log）→ 成功则 commit 半消息投递给 Consumer 异步扣减 MySQL 库存，失败则 rollback。同时设计 `stock_log` 流水表（status: 1=初始化/2=成功/3=回滚），供 MQ 回查 `checkLocalTransaction` 时精确判断本地事务的真实结果，解决应用宕机后"悬空消息"问题。

**效果**：消息零丢失，Redis 与 MySQL 数据最终一致，杜绝超卖/少卖；极限情况下（应用宕机）通过流水回查自动恢复。

## 四、秒杀令牌 + 秒杀大闸，控制流量入口

**描述**：秒杀开启后，用户需先获取"秒杀令牌"才能进入下单流程。令牌发放量 = 库存数量 × 5（可配），发完即止。令牌用完后所有后续请求在入口被拦截（即"秒杀大闸关闭"），直接返回"活动太火爆"，跳过全部下游逻辑。

**效果**：进入下单链路的请求量从无限压缩至库存的 5 倍，下游处理压力降低 95%+。秒杀大闸拦截响应 <1ms，保护 Redis、MQ、MySQL 不受无效流量冲击。

## 五、队列泄洪 — 线程池削峰，将瞬时并发串行化

**描述**：在下单核心处理前加一层阻塞队列 + 线程池（如队列容量 100、核心线程 20）。请求进入线程池排队，队列满则直接拒绝。将秒杀瞬时的 50000+ 并发请求削平为线程池处理的匀速流量，保护下游 MQ 和数据库。

**效果**：下游 MQ 和 MySQL 承受的瞬时流量从尖峰 50000 TPS 平滑至线程池消费速率（如 1000 TPS），连接池和写入压力可控，避免数据库被打爆。

## 六、验证码 + 限流 + 防刷，多层安全防护

**描述**：
- **验证码**：秒杀令牌发放前要求用户解答数学验证码（如"xx + yy = ?"），脚本无法自动处理，且人工解答耗时 1-3 秒自然拉长请求间隔。
- **限流**：基于 Guava RateLimiter 令牌桶算法对秒杀令牌接口限流（如 2000 QPS），超出速率直接拒绝。
- **防刷**：结合验证码防脚本 + 限流防高频 + 秒杀令牌一人一令牌 + 同用户同活动限制下单次数，构成四层防御。

**效果**：拦截脚本刷单 99%+，请求时间分布从瞬时尖峰变为 1-3 秒均匀分散，峰值 QPS 从不可控压降至预设阈值。

**效果**：用户登录态跨服务器共享，支持应用层无状态水平扩展，单机宕机不丢失登录态。

## 八、库存售罄快速失败

**描述**：Redis 库存扣至 0 时写入售罄标记 `promo_item_stock_invalid_{id}`，下单入口第一行检查该标记存在则直接返回"库存不足"，跳过后续所有逻辑。

**效果**：售罄后无效请求响应时间从 ~20ms（穿透到 Redis INCR 判负）降至 ~1ms（入口拒绝），CPU 开销降低 95%+。

## 九、Redis Lua 原子脚本优化库存扣减 — 从"先扣再判"升级为"先判再扣"

**描述**：将库存扣减从 `INCRBY + SET` 两步操作改造为单个 Lua 原子脚本。Lua 脚本在 Redis 服务端依次完成"读取库存 → 判断是否充足 → 扣减/拒绝 → 库存归零则打售罄标记"四个步骤，整个过程不可分割。彻底消除原方案中 INCR 返回 0 与 SET 售罄标记两个命令之间的竞态窗口，同时将扣减模型从"先扣再判、超卖回补"改为"先判再扣、不够直接拒绝"，不再需要库存回补逻辑。

**效果**：单次扣库存的 Redis 调用次数从 1-3 次（正常 1 次 / 售罄 2 次 / 超卖回补 3 次）统一降为 1 次；消除售罄标记的漏打/重复风险；减少网络往返，扣库存操作整体延迟降低约 30%。

## 一、多级缓存（本地缓存 → Redis → MySQL）

### Q1：多级缓存是怎么设计的？为什么不是只用一个 Redis？

**问题背景**：秒杀的商品详情页是流量最大的接口。如果所有请求都穿过网络去查 Redis，Redis 本身虽然快（~1ms），但网卡带宽和连接数在高 QPS 下会成为瓶颈。

**我的方案**：用三级缓存逐级降级：

| 层级 | 技术 | 位置 | 容量 | TTL | 命中延时 |
|------|------|------|------|-----|---------|
| L1 | Caffeine | JVM 堆内 | 100 条 | 60s | <0.1ms |
| L2 | Redis | 远程内存 | 不限 | 10min | ~1ms |
| L3 | MySQL | 磁盘 | 不限 | — | ~50ms |

查询顺序 L1 → L2 → L3，命中即返回并回填上层。

**为什么要有 L1 本地缓存？** Redis 虽然只要 1ms，但包含了网络 RTT。秒杀期间同一个商品被几十万人反复查，如果每次都要跨网络访问 Redis，网卡带宽和 Redis 连接数会成为瓶颈。本地缓存把最热的商品数据直接放在 JVM 堆内，命中时零网络开销。

**效果**：缓存命中率 95%+，其中本地缓存命中率约 70%，平均响应时间从 ~50ms（查库）降至 ~1ms（命中缓存）。

**面试官可能的追问**：

- **"本地缓存和 Redis 数据不一致怎么办？"** → 秒杀场景读多写少，商品信息基本不变。如果真的需要更新，用先更新 DB → 删除 Redis → 发 MQ 通知各节点清除本地缓存的模式。
- **"缓存雪崩怎么办？"** → Redis TTL 加随机偏移防同时过期；本地缓存兜底，Redis 挂了还能用本地缓存顶一会。

---

### Q2：Caffeine 和 Guava Cache 的区别？为什么选 Caffeine？

Caffeine 使用 W-TinyLFU 淘汰算法，Guava 用 LRU。W-TinyLFU 综合了 LFU（频率）和 LRU（新近度），在冷热数据混合场景下命中率比 LRU 高约 5-10%。秒杀场景下商品数据有明显的冷热之分——热门商品被反复访问，冷门商品无人问津，W-TinyLFU 对这种 pattern 更友好。API 完全兼容，迁移只需改一个 Builder 类名。

---

## 二、Redis 缓存库存 + 原子扣减

### Q3：为什么库存扣减要从 MySQL 改成 Redis？

**问题背景**：MySQL InnoDB 下 `UPDATE item_stock SET stock = stock - 1 WHERE id = ? AND stock > 0` 这条 SQL 对 `id` 所在行加 X 排他锁。秒杀时几千个请求同时 UPDATE 同一行，所有请求串行排队等锁。数据库连接池（比如 20 个连接）瞬间被占满，后续请求拿不到连接直接超时，整个服务雪崩。

**我的方案**：

1. **活动发布时**：运营调 `/publishPromo` 接口，把商品库存从 MySQL 读到 Redis：`SET promo_item_stock_{id} {stock}`。
2. **下单扣库存时**：`INCRBY promo_item_stock_{id} -1`。Redis 单线程执行命令，天然不存在锁竞争，单节点轻松 5 万+ TPS。
3. **返回值判断**：`result > 0` 成功；`result == 0` 成功 + 打售罄标记；`result < 0` 回补并拒绝。

**效果**：库存扣减 TPS 从 ~500（MySQL 行锁）提升至 50000+（Redis INCR），约 100 倍。

**面试官可能的追问**：

- **"Redis 宕机库存数据丢了怎么办？"** → RDB/AOF 持久化 + 哨兵集群高可用。即使最坏情况下 Redis 数据丢失，MySQL 还有库存底账，可通过对账脚本恢复。而且我们是"超卖不能发生、少卖可以补救"的原则设计。
- **"为什么不用 Redis 的事务（MULTI/EXEC）？"** → `WATCH + MULTI + EXEC` 是乐观锁模式，高并发下大量 WATCH 冲突导致 retry，性能不如单命令。`INCR` 单命令就能原子减库存，比事务更优。至于 Lua 的升级，见 Q3.1。

### Q3.1：为什么后来把 INCR 升级成了 Lua 原子脚本？

**问题背景**：最初用 `INCRBY` 扣库存，单命令原子。但有一个边界场景——当库存恰好扣到 0 时，需要在**同一次操作中**打上售罄标记 `promo_item_stock_invalid_{id} = "true"`。`INCRBY` 返回 0 之后，打标记的 `SET` 是第二次 Redis 调用，两个命令之间存在微小的时间窗口：

```
请求A：INCRBY stock -1 → 返回 0
                            ← 此时请求B进来，INCRBY stock -1 → 返回 -1
请求A：SET invalid "true"   ← 标记打上了，但请求B已经超抢成功
```

虽然 Redis 单线程保证单个命令原子，但**两个命令之间**可以被另一个客户端的命令插入。极端并发下可能出现：售罄标记打了、但有一个请求已经 INCR 成了负数超卖了；或者标记漏打，两个请求同时 INCR 返回 0 和 -1，只有一个打了标记。

**我的方案**：把"读取库存 → 判断 → 扣减 → 打售罄标记"整段逻辑写入一个 Lua 脚本，用 `EVAL` 一次提交到 Redis，Redis 单线程执行整段脚本期间不会插入其他命令：

```lua
local stock = redis.call('GET', KEYS[1])
if not stock then return -1 end
stock = tonumber(stock)
local amount = tonumber(ARGV[1])
if stock < amount then return -2 end     -- 不够就不扣，不需要回补
local newStock = stock - amount
redis.call('SET', KEYS[1], newStock)
if newStock == 0 then
    redis.call('SET', KEYS[2], 'true')   -- 扣到 0 同时打标记，绝无缝隙
end
return newStock
```

**关键变化**：

| 维度 | INCR（改前） | Lua（改后） |
|------|-------------|------------|
| 扣减模型 | 先扣再判（INCR 不看当前值），扣多了回补 | 先判再扣（GET 判断足够才 SET），不够直接拒 |
| 原子范围 | 只有 INCR 本身原子，和 SET 标记分离 | 整段脚本原子 |
| Redis 调用 | 1-3 次（正常 1 / 售罄 2 / 超卖回补 3） | 始终 1 次 |
| 回补逻辑 | 需要 `increaseStock` 回补 | 正常流程不需要回补 |
| 售罄标记窗口 | 有（INCR 和 SET 之间） | 无 |

**效果**：扣库存的 Redis 调用统一为 1 次，消除了 INCR+SET 之间的竞态窗口，超卖场景不再需要回补（事务回滚的回补保留，那是另一回事），单次扣库存延迟降低约 30%。

**面试官可能的追问**：

- **"Lua 脚本阻塞 Redis 单线程，不怕影响性能吗？"** → 这段脚本只有 GET + 判断 + SET，没有循环，执行时间 <0.1ms，跟一次 INCR 差不多。Redis 本身就是单线程，所有命令都要排队，Lua 只是把原来 2-3 次排队的命令合并成 1 次排队——反而减少了排队次数。
- **"脚本每次都要传完整文本，浪费带宽？"** → Spring 的 `DefaultRedisScript` 首次用 `EVAL` 传脚本，Redis 返回 SHA 摘要并缓存；后续用 `EVALSHA` 只传 SHA + 参数，省带宽。Redis 重启后 SHA 失效，Spring 自动回退到 `EVAL`。
- **"事务回滚时 Redis 回补怎么办？Lua 脚本能处理回补吗？"** → 不处理。Lua 脚本只负责"正常扣库存"。事务回滚时的回补是数据库事务的回调（`TransactionSynchronization`），用独立的 `INCRBY` 加回去——那个场景是补偿逻辑，不需要原子条件判断。两个职责分开：正常扣库存走 Lua（先判再扣），回补走 INCRBY（无条件加回）。

## 三、RocketMQ 事务消息 + 库存流水 + 最终一致性

### Q4：RocketMQ 事务消息是怎么保证 Redis 和 MySQL 数据一致的？

**问题背景**：下单需要做两件事：① Redis 扣库存（内存，快）② MySQL 创建订单（磁盘，慢且有事务）。两个操作跨了不同数据源，没法用同一个数据库事务。

如果顺序是"先扣 Redis → 创建订单 → 发消息减 MySQL"，万一创建订单失败，Redis 已经扣了且消息已经发了，消费者会去减 MySQL——结果两边都扣了但订单没生成，数据不一致。

**我的方案**：用 RocketMQ 事务消息倒置执行顺序：

```
1. 先发半消息到 MQ（此时消费者不可见）
2. 执行本地事务：Redis INCR 扣库存 + INSERT 订单 + UPDATE stock_log → 成功
3. 本地事务成功 → commit 半消息 → Consumer 可见 → 异步扣 MySQL 库存
   本地事务失败 → rollback 半消息 → Consumer 永远看不到 → MySQL 不会被扣
```

**兜底机制**：如果步骤 3 之前应用宕机（半消息挂起），MQ 会回调 `checkLocalTransaction`，查询 `stock_log` 流水表判断订单真实状态（status=2 成功→commit，status=3 失败→rollback）。

**效果**：消息零丢失，最终一致性，杜绝超卖/少卖。

**面试官可能的追问**：

- **"半消息丢了怎么办？"** → 半消息存在 Broker 磁盘 + 主从同步。如果 Broker 宕机且半消息丢失 → 等于没 commit → 消费者不会消费 → MySQL 不会被扣 → 少卖但不会超卖，符合"宁可少卖不可超卖"的原则。
- **"回查 15 次后还是 UNKNOW 怎么办？"** → 进入死信队列，人工介入。但实际不会发生——因为 stock_log 在本地事务中，要么 commit 成功（status=2），要么 catch 中手动设 status=3，不存在一直 UNKNOW 的情况。

---

### Q5：`stock_log` 流水表的具体设计？

**表结构**：`stock_log_id`（UUID 主键）、`item_id`、`amount`、`status`（1=初始化 / 2=成功 / 3=回滚）。

**生命周期**：

```
OrderController 入口：
  initStockLog() → INSERT status=1 → 拿到 stockLogId

executeLocalTransaction（本地事务）：
  事务内 UPDATE status=2  ← 和订单 INSERT 在同一事务中，一起成功或一起回滚

catch (下单失败)：
  手动 UPDATE status=3   ← 事务已回滚，需要手动更新（在 MqProducer 中操作）

checkLocalTransaction（MQ 回查）：
  SELECT status → status=2 commit, status=3 rollback, status=1 unknow
```

**为什么不在订单表里查而要单独搞一张流水表？** 流水表独立于订单业务，职责单一——只服务 MQ 回查。且流水记录在前（status=1），订单创建在后（status=2），有时序区分。如果回查时订单还没写入，流水至少能证明"操作已开始但未完成"（status=1→UNKNOW），而不是"完全没发生"。

```
  │           ├── Redis Lua 原子扣库存（GET→判断→SET→售罄标记）
  │           ├── INSERT 订单
  │           ├── UPDATE 销量
  │           └── UPDATE stock_log status=2
  │
  ├── COMMIT → Consumer 异步 UPDATE item_stock (MySQL)
  └── ROLLBACK → Consumer 不感知
```

全链路耗时核心在 Redis 网络 I/O（2-4ms），整体 RT 控制在 20ms 以内。

## 四、秒杀令牌 + 秒杀大闸

### Q7：秒杀令牌是什么？为什么需要？

**问题背景**：即使前面用 Redis 把库存扣减性能提升了 100 倍，但如果有 100 万人同时抢 1000 件商品，99.9 万人的请求还是会穿过所有校验打到 Redis，最终因为库存不足而失败。这些无效请求依然消耗服务器资源。

**我的方案**：引入秒杀令牌机制——秒杀开启后，用户必须先请求一个令牌（token），拿到令牌的人才有资格进入下单流程。令牌数量 = 库存数量 × 5（可配置），发完即止，这就是"秒杀大闸"。

```
100万人请求
  │
  ▼
[秒杀大闸] 只有 1000×5=5000 个令牌
  │
  ├── 5000 人拿到令牌 → 进入下单流程
  │     └── 最终 1000 人成功下单（库存 1000）
  │     └── 4000 人下单失败（库存已售罄）
  │
  └── 99.5 万人被大闸拦截 → 1ms 返回"活动太火爆"
```

**效果**：进入下游的请求量从 100 万压降到 5000，下游压力降低 99.5%。大闸拦截响应 <1ms，对服务器几乎零开销。

**面试官可能的追问**：

- **"为什么令牌数 = 库存 × 5，不是其他倍数？"** → 倍数是经验值，需要根据实际转化率调整。5 倍意味着预期 20% 的令牌持有者最终成功下单，留了余量给"拿令牌但放弃付款"的情况。
- **"令牌会不会被人脚本抢光？"** → 这就是为什么令牌发放前要先过验证码——人工解验证码 1-3 秒，脚本解不了，保证令牌是真实用户拿到的。

## 五、队列泄洪

### Q8：队列泄洪是什么？和秒杀大闸有什么区别？

**问题背景**：秒杀大闸把请求量降至原来的 5 倍库存，但 5000 个人同时进入下单流程，依然会在同一瞬间打过来。5000 个并发请求争抢 Redis 和 MQ，虽然不会打挂，但会有很多请求因为瞬间竞争失败（如 Redis INCR 判负）而浪费资源。

**我的方案**：在秒杀大闸后面再加一层"队列泄洪"——用线程池 + 阻塞队列把并发请求串行化：

```java
// 固定大小线程池 + 有界队列
private ExecutorService executor = new ThreadPoolExecutor(
    20, 20,                    // 核心/最大线程数
    0L, TimeUnit.MILLISECONDS,
    new LinkedBlockingQueue<>(100)  // 队列容量 100
);

// 提交任务，队列满则拒绝
try {
    Future<Result> future = executor.submit(orderTask);
} catch (RejectedExecutionException e) {
    throw new BusinessException("活动太火爆，请稍后再试");
}
```

**效果**：下游 MQ 和 MySQL 承受的瞬时流量从尖峰 5000 并发削平为线程池匀速消费，数据库连接池压力可控，不会被打爆。

**秒杀大闸 vs 队列泄洪的区别**：

| | 秒杀大闸 | 队列泄洪 |
|------|---------|---------|
| 位置 | 下单入口之外 | 下单入口之内 |
| 机制 | 限量令牌，发完拒绝 | 线程池排队，队列满拒绝 |
| 拦截范围 | 99.5% 的请求 | 大闸通过后仍过量的请求 |
| 目标 | 控制总量 | 平滑流量 |

## 六、验证码 + 限流 + 防刷

### Q9：验证码在秒杀中起什么作用？

**双重作用**：

1. **防脚本**：机器无法自动识别/计算验证码，过滤掉 99% 的刷单脚本。
2. **拉长请求间隔**：即使是真人，解答"xx + yy = ?"也要 1-3 秒。1 万个人同时抢，原本所有请求在 0.1 秒内涌进来；加验证码后，1 万人的请求在 1-3 秒内均匀分散，流量从瞬时尖峰变成平滑曲线。

**实现方式**：秒杀令牌接口要求传入验证码答案，后端校验通过才发放令牌。验证码用图片形式（简单数学题），服务端生成题目和答案，把答案放入 Redis（TTL 60 秒），校验时比对。

**效果**：过滤脚本 99%+，请求时间从 0.1 秒尖峰分散到 1-3 秒平滑分布，峰值 QPS 降低约 10-30 倍。

---

### Q10：限流是怎么做的？

**方案**：基于 Guava `RateLimiter` 令牌桶算法，对秒杀令牌接口限流。

```java
private RateLimiter rateLimiter = RateLimiter.create(2000.0); // 每秒 2000 个令牌

@GetMapping("/generatetoken")
public CommonReturnType generateToken(...) {
    if (!rateLimiter.tryAcquire()) {
        throw new BusinessException("活动太火爆，请稍后再试");
    }
    // ... 验证码校验、发放令牌逻辑
}
```

令牌桶的优势：允许一定的突发（桶里有攒的令牌），但长期平均速率固定。比如可以设置 2000 QPS，瞬时允许 5000 的 burst，但下一秒就要等桶补满。

**效果**：接口 QPS 从无控压至预设上限，保护下游服务不被突发流量打垮。

---

### Q11：防刷是怎么做的？多层防护体系？

**不靠单一手段，而是多层叠加**：

```
请求 → [第1层：验证码] 防脚本
     → [第2层：限流] 防高频（Guava RateLimiter）
     → [第3层：秒杀令牌] 同一用户同一活动只能拿一个令牌
     → [第4层：下单频率] 同用户同活动只能成功下一单
```

单一手段都有漏洞：验证码可以被人工打码绕过，限流可以被分布式 IP 绕过，令牌可以被多个账号绕过。但**四层叠加**后，攻击成本成倍增加——需要多个真人多个账号同时操作才能刷到一定量。

**效果**：拦截脚本刷单 99%+，真实用户不会受到明显影响。

## 七、补充问题

### Q12：如果流量再大 10 倍怎么扩展？

| 层 | 扩展方式 |
|------|---------|
| **前端** | CDN 缓存静态页，Nginx 限流 + 负载均衡 |
| **秒杀大闸** | 令牌发放逻辑前置到 Nginx/网关层（OpenResty + Lua），不进入应用 |
| **应用** | 无状态设计（Session 在 Redis），机器水平扩展 |
| **Redis** | Redis Cluster 分片，不同商品库存分散到不同节点 |
| **MQ** | Topic 分片 + Consumer 集群，消费能力线性扩展 |
| **MySQL** | 分库分表（用户 ID 取模），读写分离 |

**核心原则**：越靠近用户侧的拦截成本越低，尽量在流量源头解决问题。

### Q13：为什么用 RocketMQ 而不是 Kafka？

- RocketMQ 原生支持事务消息（`TransactionMQProducer` + `TransactionListener`），Kafka 需自己实现两阶段提交。
- RocketMQ 支持延时消息、消息轨迹、死信队列，功能更丰富。
- 阿里系技术栈生态契合。
- 本项目体量下两者都可以，选 RocketMQ 是因为事务消息 API 更简单。

---

### Q14：项目中遇到的最大难点？

**难点**：RocketMQ 事务消息回查机制的调试。本地事务执行后应用宕机，这种场景极难在本地复现，无法确认 `checkLocalTransaction` 的回查逻辑是否正确。

**解决过程**：
1. 单测覆盖回查三个分支（status=1/2/3）。
2. 集成测试：手动 `kill -9` 应用进程，在 MQ Console 观察半消息状态变化，确认回查次数和最终状态。
3. 加详细日志：`checkLocalTransaction` 中打印 stockLogId 和 status。

**收获**：理解了分布式一致性中"引入第三方证据"的设计模式——不依赖发送方或接收方的实时状态，而是通过独立的流水记录垫定事实。

---

### Q15：Token + Redis 替代 Session 的好处？

- **水平扩展**：Session 在单机内存中，多机部署时用户请求路由到不同机器找不到登录态。Token + Redis 所有机器共享同一份。
- **灵活性**：不依赖 Cookie，App/H5/小程序都能用；可主动设过期时间；可以做异地登录踢人。
- **可观测**：Redis 中可以看到所有在线用户数、登录时间分布。
