## 一、流量削峰——秒杀令牌

### 为什么要引入秒杀令牌？

**改动前的问题**：当前项目下单流程是：用户点击「下单」→ `OrderController.createorder()` → 校验库存 → 创建订单。所有的流量都直接打到下单接口上，在秒杀场景下，瞬时百万并发直接冲击下单链路，Redis 库存扣减虽然快，但后续的订单入库、事务消息发送等逻辑依然会因线程资源耗尽而崩溃。

**方案选型思路**：
| 方案 | 优点 | 缺点 | 是否采用 |
|------|------|------|----------|
| 直接硬抗（扩容） | 简单 | 成本高，流量无上限时扛不住 | ❌ |
| Nginx 限流 | 入口层拦截 | 粒度粗，无法感知业务状态（如库存已售罄） | ❌ 作为补充 |
| 秒杀令牌 | 业务层精确控制，只有拿到令牌的请求才能进入下单链路 | 增加一次网络调用 | ✅ 采用 |

**核心思想**：在真正下单之前增加一层「令牌发放」环节——只有拿到令牌的请求才有资格进入下单队列。令牌可以被库存售罄状态、活动时间、大闸计数等多重条件拦截。

**改动B**：实现 `generateSecondKillToken` 方法（**重点手写代码**）

```java
@Override
public String generateSecondKillToken(Integer promoId, Integer itemId, Integer userId) {

    // 第1步：判断是否库存已售罄
    if (redisTemplate.hasKey("promo_item_stock_invalid_" + itemId)) {
        return null;
    }

    // 第2步：校验活动是否存在
    PromoDO promoDO = promoDOMapper.selectByPrimaryKey(promoId);
    PromoModel promoModel = convertFromDataObject(promoDO);
    if (promoModel == null) {
        return null;
    }

    // 第3步：判断活动状态（复用时间判断逻辑）
    if (promoModel.getStartDate().isAfterNow()) {
        promoModel.setStatus(1);
    } else if (promoModel.getEndDate().isBeforeNow()) {
        promoModel.setStatus(3);
    } else {
        promoModel.setStatus(2);
    }
    // 只有进行中的活动才发放令牌
    if (promoModel.getStatus().intValue() != 2) {
        return null;
    }

    // 第4步：校验商品和用户是否存在
    ItemModel itemModel = itemService.getItemByIdInCache(itemId);
    if (itemModel == null) {
        return null;
    }
    UserModel userModel = userService.getUserByIdInCache(userId);
    if (userModel == null) {
        return null;
    }

    // 第5步：秒杀大闸计数 -1（详见"秒杀大闸"章节）
    long result = redisTemplate.opsForValue().increment("promo_door_count_" + promoId, -1);
    if (result < 0) {
        return null;
    }

    // 第6步：生成 token 并存入 Redis（5分钟有效期）
    String token = UUID.randomUUID().toString().replace("-", "");
    redisTemplate.opsForValue().set(
        "promo_token_" + promoId + "_userid_" + userId + "_itemid_" + itemId, token);
    redisTemplate.expire(
        "promo_token_" + promoId + "_userid_" + userId + "_itemid_" + itemId, 5, TimeUnit.MINUTES);

    return token;
}
```

> 🔴 **关键链路代码，需要手写**。这个方法是流量削峰的第一道防线，它串联了：库存售罄检查 → 活动校验 → 大闸计数 → 商品/用户校验 → Token 发放。

### 讲解：秒杀令牌的设计思想

**令牌的本质**：令牌是一个「入场券」。用户必须先通过 `generatetoken` 接口申请令牌（此时会经过售罄检查、活动状态检查、大闸计数检查），拿到令牌后才能携带令牌去调用 `createorder` 下单。

**为什么不在下单接口内部做这些检查？**

- 下单接口的内部检查（如 `decreaseStock`）是在 Redis 库存扣减时才做的，而库存扣减是原子操作，失败了还要回补。
- 把检查前置到令牌发放环节，可以在不触碰库存原子操作的前提下过滤掉大部分无效请求。
- 令牌发放是无状态的（只读 Redis），不涉及数据库写操作，性能远高于下单接口。

**改动前**：用户 → 直接下单（所有流量冲击下单链路）  
**改动后**：用户 → 获取令牌（过滤无效请求）→ 携带令牌下单

## 二、流量削峰——秒杀大闸

### 为什么要引入秒杀大闸？

**问题**：即使有了令牌机制，如果不限制令牌发放总量，仍然会有远超库存数量的请求拿到令牌进入下单队列。比如库存只有 100 件，但可能有 10 万人拿到了令牌——这 10 万人都会在线程池队列里排队等下单，最终 99.9% 的请求都会因为库存不足而失败，浪费了大量线程资源和数据库连接。

**方案选型**：
| 方案 | 描述 | 效果 |
|------|------|------|
| 不做限制 | 来多少发多少令牌 | 队列无限膨胀，OOM |
| 令牌数 = 库存数 | 只有 100 个令牌 | 太严格了，有些用户拿到令牌不一定下单（犹豫、网络延迟等） |
| 令牌数 = 库存 × N | N 倍库存的令牌，通过经验值平衡 | ✅ 采用，N = 5 |

**核心思想**：在令牌发放环节增加一个 Redis 计数器（大闸），每发一个令牌计数器 -1，减到 0 以下就不再发令牌。初始值设为库存的 N 倍（比如 5 倍），这样既保证了足够的流量进入下单环节（不会因为过于严格而「饿死」库存），又控制了总量不至于让队列无限增长。

### 涉及文件与改动明细

#### 2.1 `PromoServiceImpl.java` — `publishPromo` 增加大闸初始化

```java
public void publishPromo(Integer promoId) {

```

> 🔴 **关键链路代码，需要手写**。`stock * 5` 的 5 是经验值，表示允许 5 倍于库存的请求量进入下游。

#### 2.2 `PromoServiceImpl.java` — `generateSecondKillToken` 中的大闸计数扣减

**已在 1.2 节的第5步中包含**，这里再次强调：

```java
// 获取秒杀大闸的 count 数量（每调用一次 -1）
long result = redisTemplate.opsForValue().increment("promo_door_count_" + promoId, -1);
if (result < 0) {
    return null;   // 大闸关闭，不再发令牌
}
```

> 🔴 **关键链路代码**。使用 Redis `increment` 原子操作，保证并发安全。

---

### 讲解：秒杀大闸的设计思想

**大闸本质**：一个 Redis 计数器，key = `promo_door_count_{promoId}`。活动发布时初始化为 `库存 × 5`，每发放一个令牌 -1。

**为什么用 Redis 做计数器而不是本地变量？**

- 秒杀服务可能是多实例部署的，本地计数器无法跨实例共享。
- Redis `increment` 是原子操作，天然支持并发安全。

**为什么是 5 倍而不是其他倍数？**

- 倍数越大 → 进入下游的流量越多 → 库存竞争越激烈 → 无效请求越多
- 倍数越小 → 可能令牌发完了但库存还没卖完（因为有人拿到令牌不下单）
- 5 是一个经验值，实际需要根据业务场景调整（用户下单转化率）

**可能存在的遗留问题**：

- 大闸计数在活动发布时初始化，如果活动很热门，大闸可能在短短几秒内就被消耗完，后面的真实用户反而拿不到令牌。解决方案：可以动态调整大闸倍数，或者结合限流做分层控制。

## 三、流量削峰——队列泄洪

### 为什么要引入队列泄洪？

**问题**：即使有了令牌+大闸，进入下单链路的请求仍然可能瞬间并发很高。`createOrder` 涉及数据库操作（订单入库、销量更新、库存流水更新），数据库的写入能力是有限的。如果瞬间大量请求同时执行数据库写入，会导致：

- 数据库连接池耗尽
- 事务等待超时
- 数据库死锁

**方案选型**：
| 方案 | 描述 | 效果 |
|------|------|------|
| 数据库排队 | 依靠数据库自身的行锁排队 | 连接数爆了，雪崩 |
| MQ 异步削峰 | 下单请求全部发 MQ，消费者慢慢处理 | 用户体验差（下单后不知何时成功） |
| 线程池队列 | 用 Java 线程池的有界队列做缓冲 | ✅ 采用：20 个线程 + 有界队列 |

**核心思想**：在 Controller 层引入 `ExecutorService`（固定 20 个线程的线程池），所有下单请求通过 `executorService.submit()` 提交，利用线程池的有界队列（默认是 `LinkedBlockingQueue`）实现自然排队。当线程池满载时，新请求会在队列中等待，而不是直接涌向数据库。

**改动B**：改造 `createorder` 的下单执行逻辑（**重点手写代码**）

> **改动前**（当前代码）：直接同步调用
> 
> ```java
> String stockLogId = itemService.initStockLog(itemId, amount);
> if (!mqProducer.transactionAsyncReduceStock(userModel.getId(), itemId, promoId, amount, stockLogId)) {
>     throw new BusinessException(EmBusinessError.UNKNOWN_ERROR, "下单失败");
> }
> ```

> **改动后**：通过线程池提交，`Future.get()` 同步等待结果
> 
> ```java
> // 同步调用线程池的 submit 方法
> // 拥塞窗口为 20 的等待队列，用来队列化泄洪
> Future<Object> future = executorService.submit(new Callable<Object>() {
>     @Override
>     public Object call() throws Exception {
>         // 加入库存流水 init 状态
>         String stockLogId = itemService.initStockLog(itemId, amount);
>         // 再去完成对应的下单事务型消息机制
>         if (!mqProducer.transactionAsyncReduceStock(userModel.getId(), itemId, promoId, amount, stockLogId)) {
>             throw new BusinessException(EmBusinessError.UNKNOWN_ERROR, "下单失败");
>         }
>         return null;
>     }
> });
> 
> try {
>     future.get();     // 同步阻塞等待结果
> } catch (InterruptedException e) {
>     throw new BusinessException(EmBusinessError.UNKNOWN_ERROR);
> } catch (ExecutionException e) {
>     throw new BusinessException(EmBusinessError.UNKNOWN_ERROR);
> }
> ```

> 🔴 **关键链路代码，需要手写**。这是队列泄洪的核心实现。`executorService.submit()` 将任务放入线程池队列，利用线程池的有限线程数限制并发写入数据库的请求数。

---

### 讲解：队列泄洪的设计思想

**队列泄洪本质**：用 Java 线程池替代无限制的 Tomcat 工作线程。Tomcat 默认 200 个工作线程，秒杀场景下 200 个线程同时写数据库，数据库扛不住。通过线程池将写入并发控制在 20，其余请求在队列中等待。

**`Future.get()` 的作用**：虽然在 Controller 层用了线程池，但 HTTP 请求是同步等待的——用户发出下单请求后，浏览器会等待响应。`Future.get()` 阻塞当前 Tomcat 线程直到下单任务完成，这就是「同步转异步再转同步」的模式。

**可能存在的遗留问题**：

- 线程池队列无界（`Executors.newFixedThreadPool` 默认使用 `LinkedBlockingQueue` 无界队列）。如果大闸没拦住足够多的请求，队列会无限增长导致 OOM。可以考虑用 `new ThreadPoolExecutor(nThreads, nThreads, 0L, TimeUnit.MILLISECONDS, new LinkedBlockingQueue<Runnable>(1000))` 设置队列上限。
- Tomcat 线程在 `Future.get()` 上阻塞，如果线程池处理很慢，Tomcat 线程会被耗尽，导致整个服务不可用。这是需要权衡的点。

## 四、防刷限流——验证码

### 为什么要引入验证码？

**问题**：秒杀令牌 + 大闸 + 队列泄洪解决了正常用户的流量问题，但无法防御脚本/机器人。黄牛可以用脚本在 1 秒内发起数万次 `generatetoken` 请求，迅速消耗完大闸计数，导致正常用户拿不到令牌。

**方案选型**：
| 方案 | 描述 | 效果 |
|------|------|------|
| IP 限流 | Nginx/IP 级别限制 | 容易被代理 IP 绕过 |
| 用户行为分析 | 分析点击轨迹 | 实现成本高 |
| 图形验证码 | 在令牌发放前增加人机验证 | ✅ 简单有效，成本低 |

**核心思想**：在用户获取秒杀令牌之前，先要求用户输入图形验证码。验证码由后端生成并缓存到 Redis，用户提交时与 Redis 中的值比对。这样每个令牌申请都需要人工操作，大幅增加脚本刷单的成本。

#### 4.2 `OrderController.java` — 新增验证码生成接口

**改动A**：新增 `generateverifycode` 接口（**重点手写代码——验证码缓存逻辑**）

```java
@RequestMapping(value = "/generateverifycode", method = {RequestMethod.GET, RequestMethod.POST})
@ResponseBody
public void generateverifycode(HttpServletResponse response) throws BusinessException, IOException {
    // 校验用户登录状态
    String token = httpServletRequest.getParameterMap().get("token")[0];
    if (StringUtils.isEmpty(token)) {
        throw new BusinessException(EmBusinessError.USER_NOT_LOGIN, "用户还未登陆，不能生成验证码");
    }
    UserModel userModel = (UserModel) redisTemplate.opsForValue().get(token);
    if (userModel == null) {
        throw new BusinessException(EmBusinessError.USER_NOT_LOGIN, "用户还未登陆，不能生成验证码");
    }

    // 调用工具类生成验证码
    Map<String, Object> map = CodeUtil.generateCodeAndPic();

    // ===== 以下是需要手写的核心逻辑：验证码缓存 =====
    // 将验证码存入 Redis，key = verify_code_{userId}，10 分钟有效期
    redisTemplate.opsForValue().set("verify_code_" + userModel.getId(), map.get("code"));
```

### 讲解：验证码的设计思想

## 五、防刷限流——限流实现

### 为什么要引入限流？

**问题**：验证码能防脚本，但不能防「热心用户」的疯狂点击。秒杀开始瞬间，大量真实用户可能快速连续点击下单按钮，产生大量 `createorder` 请求。每个请求都会在线程池中排队，消耗 Tomcat 线程（因为 `Future.get()` 阻塞），最终导致 Tomcat 线程耗尽。

**方案选型**：
| 方案 | 描述 | 效果 |
|------|------|------|
| 前端防抖 | 按钮点击后置灰 | 只能防普通用户，懂技术的可以绕过 |
| Nginx limit_req | Nginx 层限流 | 粒度粗，无法区分不同接口 |
| Guava RateLimiter | JVM 级别的令牌桶限流 | ✅ 简单易用，单机 300 QPS |
| Sentinel / Hystrix | 分布式限流框架 | 功能强大但引入复杂度高 |

**核心思想**：在 `createorder` 接口入口处使用 Guava `RateLimiter` 限流器（令牌桶算法），每秒只放行固定数量的请求（例如 300），超过的直接返回「活动太火爆」错误。

### ⚠️ 关键辨析：秒杀令牌 vs 限流令牌桶

很容易产生一个疑问：**既然有了秒杀令牌（第九章），为什么还需要 Guava 的令牌桶再做一层限流？** 两个都叫「令牌」，但干的活完全不同：

| | 秒杀令牌 (seckill token) | RateLimiter 令牌桶 |
|---|---|---|
| **在哪** | `/generatetoken` 接口 | `/createorder` 接口 |
| **管什么** | **谁能进**——有资格下单吗？ | **进多快**——现在能处理吗？ |
| **粒度** | 业务级别，按活动/库存/用户控制 | 基础设施级别，按 QPS 控制 |
| **限制的是** | **总量**（大闸 = 库存 × 5，发完即停） | **速率**（每秒 300 个，匀速放行） |
| **类比** | 演唱会卖了 500 张票 | 门口每秒只放 300 人进场 |

**为什么两层都要有？** 假设库存 100 件，大闸 = 500：

```
t=0s   秒杀开始瞬间，500 个用户同时拿到秒杀令牌
       ↓
       500 个合法请求同一秒打向 /createorder
       ↓
       如果没有 RateLimiter：
       ├── 线程池只有 20 个线程在干活
       ├── 剩余 480 个请求全部堆在无界队列里
       ├── Tomcat 的 200 个工作线程全部在 Future.get() 上阻塞
       └── 服务雪崩
       如果有 RateLimiter(300)：
       ├── 第 1 秒：300 个放行，200 个直接返回「活动太火爆」
       ├── 第 2 秒：300 个放行...
       └── 匀速泄洪，系统稳定
```

**本质区别**：大闸控制的是「一共放多少人进来」，RateLimiter 控制的是「每秒放多少人进来」。卖 500 张票不等于 500 人同一秒到门口——但如果他们真的同一秒到了，门口就得有速率控制防止踩踏。两者缺一不可。

#### 5.3 ⚠️ 不需要恢复 `TransactionSynchronizationManager`

**文件位置**：`src/main/java/com/imooc/miaoshaproject/service/impl/OrderServiceImpl.java`

第十章中恢复了一段在第九章被注释掉的代码：

```java
// 这段代码在第十章课程中被恢复了，但你不需要加
TransactionSynchronizationManager.registerSynchronization(new TransactionSynchronizationAdapter() {
    @Override
    public void afterCommit() {
        boolean mqResult = itemService.asyncDecreaseStock(itemId, amount);
    }
});
```

**为什么不需要恢复？**

你的当前项目已经用了**事务型 RocketMQ**（`mqProducer.transactionAsyncReduceStock(...)`），它的流程是：

```
发送半消息 → executeLocalTransaction(创建订单) → commit/rollback
                                                    ↓
                                              MQ Consumer 同步数据库库存
```

事务型消息在 `commit` 后，消费者会自动完成数据库库存同步。`afterCommit` 里再发一条**普通**异步消息做同样的事，属于重复，而且更不可靠：

| 对比维度    | 事务型 RocketMQ（你已有） | `afterCommit` + 普通 MQ |
| ------- |:-----------------:|:---------------------:|
| 一致性保证   | ✅ 强保证，支持回查        | ❌ 回调抛异常消息就丢了          |
| 库存同步可靠性 | ✅ 消费者可重试          | ❌ 无重试/回查机制            |
| 是否重复    | —                 | ⚠️ 和事务消息消费者做同样的事      |

**结论：保持你当前项目的事务型消息即可，不要加 `TransactionSynchronizationManager`。** 课程第十章恢复它只是为了展示另一种方式，工程上事务型消息是更优解，两者不应并存。

---

### 讲解：限流实现的设计思想

**Guava RateLimiter 原理**：采用令牌桶算法，以固定速率（300/s）向桶中放入令牌，请求到来时尝试获取一个令牌，获取成功则放行，否则拒绝。

**为什么选 Guava RateLimiter 而不是其他方案？**

- 它是一个 JVM 级别的单机限流器，不需要额外的中间件。
- 对于秒杀场景的学习目的足够用。
- 生产级别推荐 Sentinel 或网关层限流。

**RateLimiter 放在哪个位置？**

- 放在 `createorder` 的最开头，在 token 校验之前。
- 放这里的原因是：即使请求已经有秒杀令牌，也要限制整体的下单速率，保护下游的线程池和数据库。

**可能存在的遗留问题**：

- Guava RateLimiter 是单机限流，多实例部署时每个实例各自限流 300 QPS，总 QPS = 实例数 × 300。需要根据实例数调整单机限流值。
- `tryAcquire()` 不带超时参数，立即返回。也可以用 `tryAcquire(long timeout, TimeUnit unit)` 等待一小段时间。

- `decreaseStock` 扣减的是 `promo_item_stock_{itemId}`
- `increaseStock` 回补的是 `item_validate_{itemId}`
- 两个 key 不同 → 回补无效，库存永远不会恢复

**改后**：

- 两个方法操作同一个 key → 回补正确

## 总结：整体链路图

```
用户请求流程（最终版 — 第十章）：

  浏览器                          后端服务                         中间件
  ──────                          ──────                         ──────
  点击「下单」                                                      
      │                                                             
      ├──① GET /order/generateverifycode ──→ 生成验证码图片          
      │                                      verify_code_{uid} ──→ Redis
      │                                                             
      │  显示验证码图片给用户                                         
      │  用户输入验证码                                               
      │                                                             
      ├──② POST /order/generatetoken ──→ 校验验证码 (Redis)          
      │    (携带 verifyCode)             校验售罄标识 (Redis)         
      │                                   校验活动状态 (DB+缓存)      
      │                                   大闸计数 -1 (Redis)         
      │                                   生成 promoToken ──→ Redis  
      │                                                             
      │  拿到 promoToken                                             
      │                                                             
      └──③ POST /order/createorder ──→ RateLimiter 限流检查          
           (携带 promoToken)            校验 promoToken (Redis)      
                                        线程池队列泄洪                 
                                        │                            
                                        └→ initStockLog (DB)        
                                           transaction MQ ──→ RocketMQ
                                           订单入库 (DB)              
                                           更新库存流水 (DB)          
                                           MQ Consumer 异步同步 DB 库存        
```

**四层防护体系**：

1. **验证码** — 防脚本/机器人
2. **秒杀令牌 + 大闸** — 控制进入下游的请求总量
3. **限流 (RateLimiter)** — 控制下单接口的 QPS
4. **队列泄洪 (线程池)** — 控制数据库写入的并发度
