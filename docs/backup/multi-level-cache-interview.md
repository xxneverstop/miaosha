# 秒杀项目多级缓存面试讲稿

## 先给结论

这个项目的商品详情读链路采用的是 **Caffeine 本地缓存 → Redis 分布式缓存 → MySQL 数据库**。它本质上是 Cache-Aside（旁路缓存）模式：请求按从近到远的顺序读取，某一层命中就返回；Redis 未命中才回源 MySQL，并把结果逐层回填。

需要特别区分两件事：

- 商品详情多级缓存解决的是高并发读问题，核心目标是降低延迟、保护 Redis 和 MySQL。
- 秒杀库存的 Redis Lua、售罄标记和 RocketMQ 最终一致性属于交易链路，不是商品详情多级缓存的一层。库存 Redis 是高并发扣减载体，MySQL 仍然保存最终业务数据。

---

## 问题一：这个项目的多级缓存是怎样设计的？

### 30 秒电梯版

这个项目的商品详情查询用了三级读链路：先查 JVM 内的 Caffeine，未命中再查 Redis，Redis 也没有才查 MySQL。当前源码里 Caffeine 最多缓存 100 条，写入 5 分钟后过期；Redis 商品详情缓存 30 分钟。MySQL 回源后先写 Redis，再写 Caffeine；如果 Redis 命中，也会回填 Caffeine。这样绝大多数热点请求不出 JVM，少量请求访问 Redis，只有冷数据或缓存过期时才访问数据库。

### 详细展开版

我把这套设计理解成“把越热的数据放得离应用越近”。

第一层是 Caffeine，它在每个应用实例自己的 JVM 内存里。商品详情接口先根据 `item_{id}` 查本地缓存。当前实现初始容量是 10，最大保存 100 个 key，采用写后 300 秒过期。它最大的价值不是把 1 毫秒变成 0.1 毫秒，而是命中时完全没有网络 I/O，不占 Redis 连接，也不消耗 Redis 的单线程命令处理能力。

第二层是 Redis。Caffeine 没命中时，再去 Redis 查询同一个商品 key。当前商品详情接口给 Redis 设置的 TTL 是 30 分钟。Redis 是所有应用实例共享的，所以即使某个 JVM 刚启动、本地缓存还是空的，也可以从 Redis 拿到数据，不需要直接打到数据库。

第三层是 MySQL，它是最终的数据来源。只有 Caffeine 和 Redis 都没有数据时才回源 MySQL。查询成功以后，先把商品写入 Redis，再放进本地缓存。后续请求就会逐步在更靠前的层命中。

这个接口还提供了三个压测开关：`none` 表示每次直接查询 MySQL，`redis-only` 表示只使用 Redis，`multi-level` 表示使用 Caffeine、Redis、MySQL三级链路，当前默认是 `multi-level`。因此这个项目不是只在概念上讲缓存，而是可以用相同接口做对照压测。

项目文档中的一次 500 并发公网压测显示：MySQL 读 QPS 从大约 90 降到 2；加入 Caffeine 后，Redis QPS 从大约 140 降到 45，推算约 68% 的请求被本地缓存拦截。不过这组测试受 3 Mbps 公网带宽限制，所以面试时我更强调“数据库和 Redis 压力下降”，不会夸大接口绝对 QPS。

还要注意，项目里另有 `item_validate_{id}` 和用户校验缓存。它们是下单或发放秒杀令牌时使用的 Redis 校验缓存，不属于商品详情的 Caffeine 三级链路。把用途不同的 key 分开，可以分别设置 TTL，但也带来多份数据的一致性问题。

### 追问防御

**追问 1：为什么先写 Redis，再写 Caffeine？**

因为 Redis 是多实例共享层，本地缓存只属于当前实例。回源后先建立共享缓存，再建立当前节点的近端缓存，其他节点随后也能从 Redis 取到数据。这里不是分布式事务，真正的一致性仍要靠更新策略和 TTL 兜底。

**追问 2：Caffeine 的 100 条容量够吗？**

它适合当前秒杀项目“少量商品极热”的访问模型，100 条主要覆盖热点集合。正式系统不能拍脑袋固定，应根据对象大小、JVM 堆、命中率和淘汰次数调整，必要时按权重限制内存，而不是只限制条数。

**追问 3：MySQL 算缓存的第三层吗？**

严格说 MySQL 不是缓存，而是最终数据源。面试中可以说“三级读取链路”，更准确的表达是“两级缓存加数据库回源”。

## 问题二：为什么要设计多级缓存？

### 30 秒电梯版

多级缓存不是为了堆技术，而是让不同存储各自解决一个瓶颈：MySQL 保证持久化，但扛不住秒杀热点读；Redis 速度快、所有实例共享，但每次访问仍有网络、连接和序列化成本；Caffeine 在 JVM 内命中最快，可以把热点请求挡在进程内。三者组合后，Caffeine 保护 Redis，Redis 保护 MySQL，MySQL负责最终数据。

### 详细展开版

秒杀有一个很明显的流量特征：商品数量不一定多，但同一个热门商品会被大量用户反复查看。这是典型的读多写少、热点集中的场景。

如果所有请求都查 MySQL，问题不只是磁盘慢。每次请求还会占用数据库连接，执行 SQL，解析结果并进行对象组装。高并发下连接池和数据库 CPU 会先成为瓶颈，商品详情这种非核心读取还可能拖慢下单事务。

加 Redis 后，大部分请求不再访问 MySQL，数据库得到了保护。但 Redis 不是“免费”的：应用每次仍要跨网络访问 Redis，还要占用连接池，进行序列化和反序列化。一个热点 key 被几十万次读取时，Redis 节点、网卡和连接数也会承受压力。

所以再加 Caffeine。热门商品直接存在当前 JVM 中，同一实例收到的重复请求可以在进程内完成读取。它把热点流量在入口处分散到各个应用节点，而不是全部汇聚到一个 Redis 集群。

不过多一级缓存也会增加代价：数据副本更多，更新和失效更复杂；每个 JVM 的本地缓存互相不知道对方的状态；监控和容量规划也更难。因此，多级缓存适合热点明显、读多写少、允许短时间最终一致的商品详情数据，不应无差别地给所有业务数据都加本地缓存。

我对这个设计的总结是：多级缓存是在性能、成本和一致性之间做分层取舍。越靠前越快，但容量更小、共享性更差；越靠后越权威，但访问成本越高。

### 追问防御

**追问 1：哪些数据不适合放本地缓存？**

强一致、频繁变化、对象很大或用户高度私有化的数据不适合。例如支付状态和订单最终状态不能因为本地缓存过期较慢而读到旧值。商品标题、图片这类读多写少的数据更合适。

**追问 2：本地缓存是不是越大越好？**

不是。缓存越大越占 JVM 堆，会增加 GC 压力，而且大量冷数据并不能提高命中率。应该围绕热点集合、对象大小和命中率定容量。

**追问 3：可不可以继续加 Nginx 或 CDN？**

静态资源和可公开缓存的页面片段可以继续前移到 CDN 或 Nginx。但这个项目当前源码实现的核心是 Caffeine 和 Redis，面试时我会把 CDN/Nginx 作为可演进方向，而不会说成已经落地。

## 问题三：只使用 MySQL，或者只使用 Redis 行不行？

### 30 秒电梯版

都可以运行，但适用场景不同。低流量系统只用 MySQL最简单，一致性也最好；秒杀高并发下只用 MySQL会遇到连接、CPU 和热点查询瓶颈。只用 Redis 作为缓存层也可以，而且比直接查库快很多，但所有请求仍然跨网络汇聚到 Redis。至于完全不要 MySQL、只拿 Redis 当业务数据库，在这个项目里不合适，因为订单、商品和最终库存需要可靠持久化、事务和查询能力。

### 详细展开版

先说只用 MySQL。它的优点是架构简单、数据只有一份，一致性最好，开发和排查成本最低。如果访问量不大，或者数据变化非常频繁、要求强一致，只用 MySQL完全合理。架构设计应该从简单方案开始，而不是一上来就加缓存。

但秒杀场景的问题在于并发量和热点非常集中。大量商品详情查询会争抢数据库连接和计算资源。即使给 SQL 加索引，也只是降低单次查询成本，无法消除每个请求都要进入数据库的事实。读流量还会影响真正需要数据库事务的下单链路，所以项目需要 Redis 来保护 MySQL。

再说只用 Redis 缓存，也就是“Redis → MySQL”。这是一个能工作的中间方案。它解决了大部分数据库压力，而且 Redis 由多节点共享，不会出现每个应用节点各存一份、互相不可见的问题。对于热点不高、规模不大的系统，Redis-only 往往已经够用。

它的不足是所有请求仍然要跨网络访问 Redis。在秒杀热点下，Redis 的 QPS、网卡、连接池和序列化会成为新的集中瓶颈。Caffeine 的意义就是把最热的一部分请求分散到每个应用实例本地。因此，不是 Redis 不快，而是当流量足够大时，需要避免“每个请求都去找 Redis”。

最后说完全只用 Redis、不使用 MySQL。Redis 可以开启持久化和高可用，但这个项目的订单、商品、用户、库存流水等数据需要长期可靠保存，还涉及事务、唯一约束、关系查询和审计。Redis 更适合承担热点缓存、原子库存预扣、令牌和售罄标记；MySQL 仍应承担最终业务数据。当前库存方案也是 Redis Lua 处理高并发扣减，再通过事务消息同步 MySQL，追求最终一致，而不是把 MySQL删掉。

所以我的选择标准不是“哪个技术更高级”，而是流量和一致性要求：低流量先用 MySQL；读压力上来后加 Redis；Redis 本身也成为热点路径时，再给少量热点数据加本地缓存。

### 追问防御

**追问 1：用了 Redis，MySQL 还需要读写分离吗？**

要看真实监控。如果缓存命中率高，商品详情读已经很少到 MySQL，读写分离可能收益有限。应该先看数据库 QPS、慢查询和连接池，再决定是否增加架构复杂度。

**追问 2：Redis 宕机怎么办？**

生产环境应有 Redis Sentinel 或 Cluster、超时和熔断降级。不能在 Redis 故障时把全部流量直接放到 MySQL，否则会发生缓存故障带来的数据库雪崩。可以保留短时间本地热点数据，并对回源限流。

**追问 3：本地缓存能不能替代 Redis？**

不能完全替代。多实例的本地缓存彼此隔离，重启会丢失，也很难同步失效。Redis 提供共享缓存和统一的数据视图，本地缓存只适合做热点加速层。

## 问题四：多级缓存如何处理数据一致性？

### 30 秒电梯版

这套商品详情缓存适合 Cache-Aside：读时逐层查询并回填；写时先更新 MySQL，再删除 Redis，并通知所有应用节点删除 Caffeine。删除失败要重试或通过 MQ、订阅机制补偿，TTL 只负责兜底，不能代替主动失效。由于商品详情读多写少，可以接受很短的最终一致窗口；库存和订单则不能依赖这套详情缓存保证正确性。

### 详细展开版

多级缓存最大的难点不是读取，而是一个商品在 MySQL、Redis 和多个 JVM 中有很多副本。更新时只改数据库，其他副本就会继续返回旧数据。

我会采用 Cache-Aside 的更新策略：业务事务先更新 MySQL，事务成功后删除 Redis，同时让每个应用实例清理自己的 Caffeine key。这里选择删除而不是直接更新缓存，是因为删除逻辑更简单，也能避免并发写时把旧值覆盖回缓存。

单机本地缓存的失效不能只靠调用当前实例的方法，因为请求可能落在其他实例。正式方案可以在数据库更新成功后发送 MQ 消息，或者通过 Redis Pub/Sub 等机制广播失效事件，各节点收到事件后删除本地 key。消息失败需要重试或补偿；Caffeine 和 Redis 的 TTL 是最后一道兜底。

即使采用“更新 DB 后删除缓存”，仍有并发窗口。例如读线程先读到旧数据库值，写线程随后完成更新并删除缓存，读线程最后又把旧值写回缓存。常见做法是根据业务容忍度选择延迟双删、带版本号的数据、串行化热点更新，或者让 CDC/消息系统统一驱动失效。这个项目的商品信息更新很少，可以先采用主动删除加短 TTL，而不是为了理论强一致引入过重方案。

另外要明确：展示库存和真实可售库存不是一回事。商品详情里的 `stock` 即使短时间显示旧值，也不能参与下单正确性判断。真正的秒杀扣减必须走 Redis Lua 的原子校验、扣减和售罄标记，并由 MQ 同步 MySQL。这样即使详情缓存旧了，也不会导致超卖。

### 追问防御

**追问 1：为什么不是先删缓存再更新数据库？**

如果先删缓存，数据库还没更新时并发读可能查到旧数据并重新写入缓存，脏数据会保留一个 TTL。通常先更新数据库，成功后再删缓存更稳妥。

**追问 2：删除 Redis 成功，但某个 JVM 没删成功怎么办？**

通过失效消息重试、消费幂等和 TTL 兜底。若业务要求更高，可以给缓存值带版本号，节点拒绝覆盖成旧版本。

**追问 3：能不能做到缓存与数据库强一致？**

可以做得更强，但成本很高。缓存本来就是用一致性换性能。商品详情通常接受短时间最终一致；订单和库存正确性则交给数据库事务、Lua 原子操作、流水和 MQ 机制保证。

## 问题五：缓存穿透、击穿、雪崩怎么处理？

### 30 秒电梯版

穿透是查询不存在的数据，缓存和数据库都挡不住；可以做参数校验、短 TTL 空值缓存或布隆过滤器。击穿是单个热点 key 失效时大量请求同时回源；可以用互斥重建、单飞或逻辑过期。雪崩是大量 key 同时失效或 Redis 整体故障；可以给 TTL 加随机抖动、分批预热、限流降级和建设 Redis 高可用。当前项目这些治理还不完整，是后续优化重点。

### 详细展开版

缓存穿透针对的是不存在的商品 id。当前代码在缓存未命中后直接查 MySQL，没有负缓存。如果有人不断请求随机 id，请求会每次穿过 Caffeine 和 Redis 到达数据库。可以先校验 id 格式和访问权限；数据库确认不存在后缓存一个特殊空值，并设置几十秒到几分钟的短 TTL。数据规模很大时可以加布隆过滤器，但布隆过滤器只能判断“大概率不存在”，不能代替数据库。

缓存击穿针对的是一个非常热门的商品。它的 Redis key 刚好过期时，几百个并发请求会一起发现 miss，然后同时查询 MySQL并回写。当前读取代码没有互斥重建，所以存在这个风险。可以对单个 key 做互斥锁或 single-flight，让一个线程回源，其他线程短暂等待；也可以使用逻辑过期，由后台线程刷新，读请求暂时返回旧值。选择哪种方式取决于业务能不能接受短暂旧数据。

缓存雪崩通常有两类：一批 key 在同一时间过期，或者 Redis 整体不可用。当前商品 Redis TTL 是固定 30 分钟，如果大量商品同一批预热，就可能集中到期。可以在基础 TTL 上增加随机抖动，分批预热，并对数据库回源设置并发上限。Redis 故障时还要做高可用、超时、熔断和限流，不能让所有流量无保护地落到 MySQL。

多级缓存能缓解但不能彻底解决这些问题。Caffeine 命中时确实能挡住一部分请求，但每个应用实例的本地缓存也可能同时过期或重启。如果过期策略完全一致，多个实例仍可能一起访问 Redis，甚至一起回源数据库。因此过期时间、预热和重建机制要放在整条链路上设计。

### 追问防御

**追问 1：空值缓存有什么副作用？**

如果这个 id 随后真的被创建，短时间内仍会读到不存在。因此空值 TTL 要短，创建成功后还要主动删除对应空值。

**追问 2：互斥锁会不会降低性能？**

只在热点 key 重建时使用，而且锁粒度是单个 key。它牺牲少量 miss 请求的延迟，换取数据库不被并发回源打垮。

**追问 3：布隆过滤器能完全防穿透吗？**

不能。它可能误判“存在”，所以仍可能回源；而且新增、删除数据时要维护过滤器。它适合挡住大量明显不存在的 key。

## 问题六：结合当前源码，还有哪些具体问题？

### 30 秒电梯版

当前方案已经完成了主要读链路，但工程治理还需要补齐：没有主动失效接口，固定 TTL 会放大雪崩风险，不缓存空值会发生穿透，冷启动并发 miss 会击穿数据库，Redis 异常没有明确降级，Caffeine 没开启命中率统计。另外源码和旧文档的 TTL 不一致，用户缓存 key 还有拼写不一致导致实际 key 不过期的问题。面试时我会实事求是地说“核心方案已落地，治理项是下一步优化”。

### 详细展开版

第一，当前商品详情只有查询和回填，没有看到对应的缓存删除能力。`CacheService` 只暴露 get 和 set，没有 invalidate。现在商品接口主要是创建，没有更新接口，所以问题暂时不明显；一旦加入商品编辑、活动变更，就必须补上“更新数据库后删除 Redis，并广播清理本地缓存”。

第二，商品对象里同时带了库存和活动状态，而这两类数据会变化。Redis 商品详情最长缓存 30 分钟，可能展示旧库存，活动开始或结束状态也可能滞后。正确做法是把稳定的商品基础信息和变化快的数据拆开缓存，活动状态也可以根据开始、结束时间实时计算。展示库存只能作提示，不能作为下单依据。

第三，没有缓存空值，也没有单 key 的并发重建保护。非法 id 会造成缓存穿透；热门商品过期会造成击穿。可以补参数校验、短 TTL 负缓存和 single-flight/互斥重建。

第四，TTL 都是固定值，没有随机抖动。批量预热或同一时刻写入的 key 可能集中失效。可以采用“基础 TTL + 随机秒数”，并让不同层的过期时间错开。

第五，本地缓存只按条数限制，不按对象大小限制。100 个小对象问题不大，但如果以后缓存更大的对象，应该评估 JVM 堆占用，必要时按权重淘汰。同时当前没有启用 Caffeine 的 `recordStats()`，命中率主要通过 Redis QPS 差值推算，缺少直接监控。

第六，Redis 故障时当前读取代码会直接抛出访问异常，并没有清晰的熔断、限流回源或返回旧值策略。生产环境还需要 Redis 高可用、超时配置、降级方案和数据库回源保护。

第七，缓存 key 的命名和 TTL 存在工程问题。商品详情使用 `item_{id}`，下单校验使用 `item_validate_{id}`，两份 ItemModel 可能在不同时间过期并产生不一致。用户校验缓存更明显：当前源码写入的是 `user_calidate_{id}`，设置过期却使用 `user_validate_{id}`，拼写不一致导致真正写入的 key 没有 TTL，这是应该修复的 bug。

第八，代码与旧文档已经发生漂移。当前源码的 Caffeine TTL 是 300 秒，商品 Redis TTL 是 30 分钟；旧压测报告仍写 60 秒和 10 分钟。面试时必须以当前源码为准，并在重新压测后更新文档，否则面试官根据代码追问时很容易前后矛盾。

第九，Caffeine 构建器旁的注释说“按 LRU 淘汰”不够准确。Caffeine 的默认策略不应简单等同于纯 LRU。面试中更稳妥的说法是“Caffeine 会基于容量和访问特征淘汰低价值条目”，除非准备好深入解释 W-TinyLFU，否则不要为了显得高级而主动挖算法细节的坑。

### 追问防御

**追问 1：这些问题是不是说明方案不能用？**

不是。核心的 Caffeine → Redis → MySQL 读链路已经有效降低下游压力，但从课程或实验项目走向生产，还需要补齐一致性、异常降级、监控和防穿透等工程能力。

**追问 2：你会优先修哪三个？**

优先修用户缓存 key 的 TTL bug；其次补商品缓存主动失效和跨节点通知；最后补空值缓存、热点 key 重建保护和 TTL 抖动。这三类分别解决明确 bug、数据正确性和数据库稳定性。

**追问 3：怎么验证优化真的有效？**

用同一商品、相同并发和相同数据集对比 `none`、`redis-only`、`multi-level`，同时采集接口 QPS/P99、Caffeine 命中率、Redis QPS、MySQL 查询 QPS和连接池占用。还要单独做冷缓存、热点 key 过期、非法 id 和 Redis 故障测试，不能只测缓存已经预热好的理想情况。

## 最后一分钟总结版

这个项目的多级缓存，本质上是两级缓存加数据库回源：Caffeine 负责把最热请求挡在 JVM 内，Redis 负责跨实例共享并保护 MySQL，MySQL负责最终持久化。它适合商品详情这种读多写少、热点明显、允许短暂最终一致的数据。

只用 MySQL不是不行，而是秒杀流量下成本太高；只用 Redis 缓存也能工作，但所有请求仍有网络和集中式热点；完全用 Redis 替代 MySQL则不符合订单、库存流水等核心数据的持久化与事务要求。

真正有含金量的地方，不只是会说“Caffeine → Redis → MySQL”，而是知道它带来的新问题：多副本一致性、穿透、击穿、雪崩、Redis 故障降级、本地缓存容量与监控。当前项目的读取主链路已经落地，但主动失效、并发重建、空值缓存和监控仍需要完善，而且要以当前源码的 5 分钟/30 分钟 TTL 为准，及时修正文档漂移。
