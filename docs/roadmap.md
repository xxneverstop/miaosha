## 1. 目标与推进方式

先明确程序和依赖放在哪里，跑通本机开发与隔离测试，最小 CI 并行推进，再修复交易链路，最后用故障实验和压测验证。云端部署按需后置。最终形成一条可重复的工作路径：修改代码 → 自动检查 → 生成版本工件（JAR 或部署包） → 在已选测试环境验证 → 保留证据。

```text
第 0 步：确定环境、资源和发布路径
    ↓
第 1 步：先跑通本机开发与隔离测试，基础 CI 并行推进
    ↓
第 2 步：修复订单事务与 MQ 消费正确性
    ↓
第 3 步：修活动边界，明确请求重试的能力范围
    ↓
第 4 步：最小数据关联、只读对账和异常清单
    ↓
第 5 步：故障验证与对照压测
    ↓
第 6 步：整理简历、面试材料和复现实验入口
```

每一步都有交付物和验收门槛。对应测试随改动一起补，第 5 步负责系统性实验，不是把所有测试都推迟到最后。第 0 步确定本机方案、第 1 步跑通本机下单后即可进入第 2 步；基础 CI 可并行建设，云端部署与自动回滚不阻塞交易正确性修复。

### 任务等级与基础版本停止条件

- **【已有基础】**：结构规整、配置模板、配置类、打包入口及现有自检。复用并验证，不再从零建设，也不因此标记真实环境已经跑通。
- **【必做】**：本机可复现环境、最小 CI、订单事务、DB 消费幂等、合法库存模式、已有回补重试缺陷处理、基本活动边界、只读核查、可信实验与证据整理。
- **【增强】**：完整 HTTP 请求幂等与结果查询、一人一单、完整 Redis Reservation 与跨进程恢复、云端 CD、多实例/独立 Consumer。默认后置；选定一项后单独验收，未做不算完成。

基础版本在上述必做项验收、原始实验工件和面试材料齐全后停止新增功能。增强项按实际目标最多先选一项，完成后再决定是否继续；基础版不因增强项未做而无限延期。最小 CI 必须留下实际运行结果，但可以在第 1～5 步期间并行补齐，不作为开始第 2 步的门槛。

**默认延期完整请求幂等和跨进程恢复时，只承诺数据库消费幂等、已修复路径的正确性与异常可核查；不承诺 HTTP 超时重试不重复下单，也不承诺预扣后宕机自动恢复。**

## 3. 第 0 步：确定开发、部署、测试环境与资源配置

### 3.1 要解决什么

把“数据库在哪、App 跑在哪、依赖怎么启动、数据是否保留、测试会不会影响其他环境、改完如何发布”一次说明白。**这一步负责选择和登记，第 1 步才实际搭建、启动和跑业务。**

### 3.2 推荐的默认布局

先复用现有机器和工具，不以购买新服务器或增加托管服务为前提。默认布局如下，资源不足时在本步骤调整并记录理由。

| 场景 | App 在哪里运行 | MySQL / Redis / MQ 在哪里运行 | 主要用途 |
| --- | --- | --- | --- |
| 日常开发 | Windows 本机 IDE 或 JDK 8 + Maven | 本机 Docker，Linux 容器 | 调试、修改、快速验证，不依赖云端才能开发 |
| 本机集成测试 | 本机测试进程或测试 App | 一套专用、可重建的本机容器与测试数据 | 验证 SQL、Lua、事务和消息；起步串行运行 |
| CI 自动检查 | GitHub Actions 的受控 Linux Runner（任务执行机），JDK 8 + Maven | 需要集成测试时启动独立临时容器 | 每次改动自动检查，不接日常开发库或云端业务库 |
| 云端演示与部署验证 | 一台已有 Linux 主机上的 App 容器 | 同主机 Docker 网络中的 MySQL、Redis、NameServer、Broker；按需 Nginx | 验证真实部署、恢复和发布；与本机数据分开 |
| 性能实验 | 被测 App 在固定的测试环境 | 固定版本和资源的测试依赖 | 第 5 步再确定；负载生成器尽量使用独立机器 |

如果本机无法承载依赖，备选是“本机 App + 一套专用云端开发依赖”，通过私网、VPN 或隧道访问。需要单独记录网络时延与地址变化，不能直接复用有日常数据的数据库或把这个结果等同于纯本机性能。

若启用云端部署，起步考虑允许短暂停机的单实例发布；是否允许、允许多久须在本步确认。暂不启用时只登记待确认项，不等待云端权限才能推进本机开发。多实例、独立 Consumer、Kubernetes 和复杂发布平台放在主路线完成之后。

以下是实施前的登记要求，**“待确认”不能自动视为已经选定或配置成功**。可公开的用途和版本写在本节，实际连接与凭据保存在各环境自己的私有配置中。

| 登记项 | 默认方向 | 第 0 步需要确认并留下的结果 |
| --- | --- | --- |
| 开发机 | 当前 Windows 工作区 | CPU、内存、可用磁盘、Docker 虚拟机资源上限；明确 JDK 8 的 `JAVA_HOME` |
| 容器运行环境 | Docker Desktop 的 Linux 容器，或已可用的同类 Docker 环境 | Engine 能连接，Bash 入口可用；Git Bash 与 WSL 的使用边界清楚 |
| 云主机 | 优先复用已有 Linux 主机 | 主机别名、CPU/内存/磁盘/带宽、架构、SSH 方式、数据归属、停机窗口；尚未确认 |
| 开发/测试数据库 | 不同于历史或共享数据的专用库 | 库名、账号权限、初始化方式、重置范围、备份与恢复责任 |
| Redis 与 RocketMQ | 开发与云端分离，测试可重建 | 实例、数据库号/Key 范围、Topic、消费组、数据卷与日志位置 |
| 端口与网络 | 本机映射端口、容器内部端口分别登记 | 端口冲突、绑定地址、云端防火墙、Broker 通告地址及各客户端可达性 |
| 版本 | 先沿用当前兼容组合 | 记录 JDK/Maven、Docker/Compose、镜像的具体版本及摘要，避免浮动标签悄悄变化 |
| 配置与访问凭据 | 每个环境自己的 `.env`，云端配置留在服务器 | 谁维护、如何交接、哪些字段需填写；此前日志中暴露的访问凭据须处理 |
| CI/CD | 优先使用仓库所在的 GitHub Actions | Runner 可用性、依赖下载源、工件保存位置、部署账号与人工触发权限 |

当前基线是 Spring Boot 2.0.5、Java 8、MySQL 5.7、Redis 5.0、RocketMQ 客户端 4.3.0 / 服务端脚本 4.9.4。这里只作为兼容性起点，不代表这些历史版本适合直接对公网提供生产服务。先固定、验证，再单独评估版本升级；不要和交易正确性改造同时全面升级。

地址约定以当前端口为起点：本机访问 App `18091`、MySQL `13306`、Redis `16379`、NameServer `19876`、Broker `10911`；容器内部依次使用 App `18091`、MySQL `3306`、Redis `6379`、NameServer `9876`、Broker `10911`。Nginx 当前宿主机端口为 `81`。这些端口是否可用仍需核定，云端不默认向公网开放数据库和中间件。

特别确认 RocketMQ：NameServer 能连接不代表 Broker 能连接，`brokerIP1` 通告地址必须能被实际 App 和测试客户端访问。不能让本机 App 得到只在容器网络内可达的 Broker 地址。

### 3.4 配置与数据隔离约定

- 保留 `src/main/resources/application.yml` 作为基础配置，根 `application.yml` 作为部署覆盖；沿用 `.env.example`，各环境维护自己的私有 `.env`，无需立刻引入配置中心。
- 明确本机 App、容器 App、CI Runner 的连接地址；分服务 App 当前固定走容器 DNS，不直接套用本机的 `localhost` 或宿主机映射端口。
- 测试初始化、重置只能操作专用测试资源。原 `sql/miaosha.sql` 含 `DROP TABLE`，不得作为日常部署时自动执行的迁移脚本。
- 当前容器名、消费组等存在固定值，起步采用一套专用依赖串行验证。仅换库名或 Topic 不足以承诺多套环境并行；需要并行时先完整隔离端口、容器、数据卷、Redis Key、Topic 和消费组。
- 云端保留状态的目录/卷与应用发布包分开；应用升级不能顺带重建数据库、删除 MQ 消息或清空 Redis。

### 3.5 确定最小 CI/CD 路径

CI 指自动构建和测试，CD 指把经过检查的版本部署到目标环境。【必做】最小 CI 负责测试、构建和保存无密钥工件；【增强】云端 CD 先验证人工部署与回退，再考虑自动化，不强制引入镜像仓库。

```text
提交 / PR
  → CI：JDK 8 构建与测试
  → 保存无密钥部署工件 + Git 提交号 + 校验值
  → 【选做云端 CD】人工选择已通过版本，部署测试环境
  → 冒烟与业务断言成功：保留该版本
  → 失败：保留日志，恢复上一版 App
```

第 0 步先确认本机方案、CI 平台和工件约定；云端权限尚未具备则登记为后续项。第 1 步启动最小 CI 建设，第 2～4 步持续追加相应测试，第 5 步完成基础版实验。云端 CD 和重型实验自动化可以后置，实验本身可以先受控手动执行。

- CI 工件只包含 JAR、Dockerfile、无密钥编排/覆盖配置和需要的版本化脚本。**当前 `package.bat` 会把真实 `.env` 复制到 `target/deploy/`，不能把这个目录原样上传成公开 CI 工件。**
- 服务器保留自己的私有配置与持久化数据。第一版可以上传无密钥版本包，再在服务器构建 App 镜像；工件始终关联 Git 提交号，避免覆盖同名文件后无法追踪。
- 云端发布只替换 App，保留上一版工件/镜像和日志。数据库增量变更单独审阅，不能承诺“回滚 App 自动回滚数据库”。
- 流水线部署凭据只在受控部署任务中使用，不交给不受信任 PR；测试和构建日志不打印环境变量全集或密码。

## 4. 第 1 步：先跑通本机环境，基础 CI 并行推进

### 要做的事

1. **【已有基础】** 复用 JDK 8 配置、两份 application 配置、环境变量模板、打包和分服务脚本。在选定机器上填写实际参数、检查工具版本和端口，不重新建设配置层。
2. **【必做：本机基线】** 选一条可重复启动完整依赖的路径。现有脚本足够时先复用；只有确需统一入口时才补齐 Compose，不把全服务编排重写作为开始业务修复的前提。明确脚本与 Compose 不混用容器和数据卷。
3. **【必做】** 为所选入口补有超时的就绪检查，明确 MySQL、Redis、MQ 的数据保留方式；需要保留状态的依赖挂载持久化卷。测试环境允许重建时，提供受限重置与初始快照。准备用户、商品、库存及有效活动，普通部署不自动执行重建表脚本。
4. **【必做】** 跑通基础查询、登录、申请令牌和一次真实下单，检查 JSON 业务状态及订单/流水/库存事实。验证码调用方式与当前开关一致。
5. **【必做：可并行】** 新增最小 GitHub Actions CI：JDK 8 编译、现有配置测试、后续逐步补集成检查，保存无密钥工件。当前 Windows 部署自检使用支持 Git Bash 的 Runner，不冒充 Linux 可直接运行。CI 账号/权限问题单独登记，不阻塞第 2 步；基础版结束前补齐运行证据。
6. **【增强：云端 CD】** 云资源确认后再验证指定版本部署、冒烟与上一版 App 回退；先跑通人工路径，再决定是否自动化。不把云端 CD 的完成列为本机基线门槛。

### 主要落点与交付

主要涉及 `.env.example`、两份 `application.yml`、`docker-compose.yml`、`Dockerfile`、`scripts/`、测试目录，以及待新增的 `.github/workflows/`。已有 `package.bat` 和部署自检继续复用；确有跨平台差异时明确各自用途。

交付可照着执行的本机启动/停止/日志/重建/测试说明、可重置的隔离数据及一次真实下单记录；CI 工件与运行记录并行补齐。只有选做云端 CD 时才追加部署/回滚记录。第 0 步的资源登记在真实启动后补上实际结果。

### 验收

- [ ] 从明确记录的干净状态启动，不依赖手工修改源码中的地址和密码。
- [ ] 本机 App 可调试，依赖可连接；真实完成一次下单，订单与库存增量核对成立。
- [ ] 重启/重建依赖的数据结果符合约定，应用升级不删除持久化数据。
- [ ] 本机基线通过后进入第 2 步；最小 CI 单独登记待完成项，并在基础版结束前提供无密钥构建/测试工件。
- [ ] 【增强项单独验收】若启用云部署，保留一次“指定版本部署 → 冒烟 → 回退上一版”的真实记录；未启用不标记完成。

**进入第 2 步的标准：本机能按说明启动并完成一次下单，开发与隔离测试有稳定入口。CI、云端 CD 的进度分别记录；一次成功下单仅证明环境连通，不能替代第 2～4 步的正确性验证。**

## 5. 第 2 步：修复订单与 MQ 的正确性

### 要做的事

本阶段以下任务均为 **【必做】**，不以完整 Redis Reservation 或云端部署完成为前提。

1. 明确 `BusinessException` 等受检异常的事务回滚规则，覆盖写入订单、销量、流水后失败的路径；分别测试业务异常和运行时异常。
2. 把消费去重记录与 MySQL 库存扣减放进同一个数据库事务，用唯一键裁决重复消费。Consumer 通过独立 Spring Bean 调用事务服务，成功提交后才确认消费。
3. 检查所有扣库存 SQL 的影响行数。更新 0 行必须进入明确失败/重试/待处理状态，不能当作消费成功。
4. 区分“本地订单已提交”和“DB 库存已同步”。完善生产者失败与 UNKNOWN 回查处理，不把状态不确定直接当作失败；正常事务代理返回无需每单增加一次重复查库。
5. 固定合法库存模式、各资源的扣减和回补职责；不支持的配置启动时报错。普通同步开关当前不移除 Producer / Consumer 的启动依赖，不得据此宣称无 MQ 模式。
6. 修复当前回补重试缺陷：`INCR` 成功、删除售罄标记失败或响应未知时，不能整体盲重试造成重复加库存。优先按 `stockLogId` 对明确回滚的回补去重，并原子处理库存/售罄标记；无法确认执行结果时保留待核查证据，不继续猜测后重复加库存。这项基础修复与完整预留/跨进程恢复分开。
7. 验证订单号唯一性、长度边界和锁等待。当前序列 SQL 已有 `FOR UPDATE`，读改写处于外层订单事务；私有 `REQUIRES_NEW` 不生效不能直接推出发号不安全。只有验证暴露实际问题时才调整发号方式，不预设必须新增独立服务。

目标模式最少说明如下；名称对应代码中的 `stock-mode` 和 `mq-async-sync`，表内是改造后的目标，不是当前已安全实现的组合。

| 模式 | 订单阶段 | 消费阶段 | 回滚要求 |
| --- | --- | --- | --- |
| `mysql + false` | DB 库存只扣一次 | 不再扣库存 | DB 回滚，不凭空回补 Redis |
| `lua + false` | Redis 一次、DB 一次 | 不再扣库存 | DB 回滚后按真实预扣处理 Redis 补偿 |
| `lua + true` | Redis 预扣一次 | DB 事务内幂等扣一次 | 主路径；先修已有回补，完整预留恢复另作增强 |

历史 `redis` INCR 模式只在确需对照时保留和单独验证；`mysql + true` 等未支持组合不能静默运行。模式定义也要说明是否仍经过事务消息，避免实验标签误导。

### 主要落点与验收

涉及 `OrderServiceImpl`、`ItemServiceImpl`、`MqProducer`、`MqConsumer`、相关 Mapper，以及新增消费流水、事务服务、增量 SQL 和集成测试。表和服务的最终名称在本阶段实现时确定，复用已有分层即可。

- [ ] 同一 `stockLogId` 重投 100 次，DB 库存只扣一次。
- [ ] 去重记录写入后或扣库存后抛异常，消费记录与库存一起回滚，重试能完成。
- [ ] 订单写入后抛 `BusinessException`，订单/销量/流水按设计回滚，MQ 状态可解释；回补局部失败/响应未知时不发生盲目重复加库存，并留下可核查状态。
- [ ] DB 更新 0 行不能被确认成功消费；暂时错误与永久错误有重试/告警/人工处理边界。
- [ ] 所有支持模式扣减次数正确，MySQL 模式不发生 Redis 凭空加库存；订单号唯一性与锁等待验证有记录。

**通过标准：重复消费只生效一次，数据库事务失败不留下部分修改，已有回补不因盲重试重复加库存。跨 Redis / MySQL 的进程崩溃窗口仍属已知边界，第 4 步先做只读核查，不提前宣称自动恢复或全面最终一致。**

## 6. 第 3 步：修复活动边界，明确请求幂等范围

### 要做的事

1. **【必做】** 为活动初始化设置可验证的幂等边界，交易过程中拒绝重置 Redis 库存；仅冻结入口并确认在途收敛后允许受控重置。
2. **【必做】** 下单按当前时间校验活动开始/结束，避免依赖缓存中的状态快照。固定测试业务规则，主演示路径建议 `amount=1`；正常订单不因活动约束被误拒绝。
3. **【必做】** 在接口说明、测试和压测中写清请求重试语义。默认基础版不建设完整请求状态机，HTTP 超时后重复提交仍可能产生重复订单；不能用 MQ 消费幂等代替请求幂等，也不新增自动重试掩盖结果未知。
4. **【增强：请求幂等】** 需要承诺重试不重复下单时，定义稳定 `requestId`，建立 `requestId → stockLogId → orderId` 关联，数据库裁决重复请求，并返回原结果/可查询状态。令牌消费、排队拒绝和失败重试一起设计，不能只新增一个 ID 字段就算完成。
5. **【增强：一人一单】** 仅在明确启用该业务规则时增加数据库购买唯一事实。它限制不同请求的第二次购买，与同一请求重试去重是两个问题，普通订单不受活动唯一约束误伤。

### 主要落点与验收

基础改动主要涉及 `OrderServiceImpl`、`PromoServiceImpl`、相关入口与活动边界测试。只有选做请求幂等/一人一单时才扩大到请求结果查询、唯一约束等接口和 SQL；第 4 步按对账需要补最小订单/流水关联。

- [ ] 重复发布不覆盖进行中的库存；活动开始/结束边界不依赖陈旧缓存状态。
- [ ] 测试数量与购买规则明确，普通订单不因活动约束被误拒绝；请求重试限制已进入接口说明与实验配置。
- [ ] 【仅选做请求幂等时】同一请求并发/超时重试只生成一笔有效订单，可查询原结果；令牌、拒绝与失败重试语义一致。
- [ ] 【仅选做一人一单时】同一用户同一活动只能成功一次，普通订单不受误伤；请求去重与购买限制分开验证。

**基础通过标准：活动生命周期不被重复初始化或陈旧缓存破坏，购买与重试边界写清。未实现请求幂等时，不验收、不宣称“HTTP 重试不会重复下单”。**

## 7. 第 4 步：只读对账与异常核查，完整恢复作为增强

### 要做的事

1. **【必做】** 为每轮测试记录初始库存、订单/流水/消费记录基线，明确单活动、商品、时间范围和无其他流量的条件，避免把历史种子订单算进本轮结果。
2. **【必做】** 补齐对账确需的最小订单↔流水↔消费关联及必要时间字段，区分订单已提交和库存已同步。复用已有 ID；活动可从订单关联取得时不重复维护字段。受控实验可先用基线差值，但不能据此承诺逐笔定位所有 Redis 预扣。
3. **【必做】** 实现只读核查：本轮成功订单 `SUM(amount)`、成功消费数量、MySQL/Redis 库存变化，以及长期 PENDING、回补失败、待同步等异常。区分正常、在途、明确异常、未知待核查，保留证据和人工处置说明。
4. **【必做】** 未确认终态前不自动修复。超时、暂时查不到订单、Redis marker 过期不能单独证明失败，不直接执行 `SET Redis库存 = DB库存`。第 2 步已修的现有回补问题必须保持回归覆盖，不因本阶段只读而放松。

### 【增强】完整 Redis 预留与跨进程恢复

基础版与第 5、6 步完成后，确需增强时再单独选择：在同一 Lua 中预扣并写 Reservation，设计预留/成功确认/已补偿终态、保留时间和持久化语义；用数据库条件更新或锁定同一流水保护提交与补偿裁决，防止成功后回补或补偿后迟到提交。普通补货、失败回补分开处理。

选择该增强项后，必须验证重复补偿只生效一次、提交与补偿竞争安全、预扣后进程退出可定位，以及 Redis 数据丢失/证据过期时的未知处置。没有这套机制，基础版只能记录聚合差异和能够查证的流水，不能承诺所有遗留预留均可识别或自动恢复。

### 主要落点与验收

基础涉及订单/流水/消费记录的最小关联、只读对账服务或命令和集成测试。交付本轮基线、核查报告与未知清单；需要自动巡检时再补最小调度，完整预留/补偿状态机不属于基础门槛。

- [ ] 本轮订单、流水、消费与库存基线可重复取样，历史数据不会污染结果。
- [ ] 订单成功但消费滞后、DB 消费失败、已有回补失败等情况能输出差额/关联证据；缺乏证据的部分明确标为未知。
- [ ] 在途、异常和未知分开，核查入口不修改库存、不把未查到订单直接当失败。
- [ ] 对 Redis 预扣路径，冻结入口、事务与消息收敛后，在无补货/取消的单活动测试中满足：

```text
本轮初始 Redis 库存 - 当前 Redis 库存
  = 本轮初始 MySQL 库存 - 当前 MySQL 库存
  = 本轮已提交成功订单的购买数量之和
```

基线取本轮快照，按 `SUM(amount)` 核对，不能无条件用订单条数替代购买数量。`mysql + false` 不扣 Redis，只核对 MySQL 与订单；存在补货、取消、共享库存时需要额外流水和公式，不套用上述简化不变量。若未知差额未收敛，报告失败与待核查项，不标记上述等式验收通过。

**基础通过标准：差异有基线和关联证据，能识别在途与未知，核查不误改库存。只读核查不等于幂等补偿平台，也不等于跨 Redis / MySQL 强一致；增强项按独立故障标准验收。**

## 8. 第 5 步：故障验证与对照压测

### 要做的事
